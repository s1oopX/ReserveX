## 〇、根决策(Q1,重写 docs-old 定稿 M2)

**抢号只动 Redis + 普通消息 + 补偿 + 对账。**

- **为何弃事务消息**:RocketMQ 事务消息解决的是「本地 DB 事务 ↔ 消息发送」一致性,而本项目的关键原子边界在 **Redis ↔ MQ**,事务消息管不到这一段,仍要靠补偿+对账兜。事务消息没买到 Redis↔MQ 可靠性,却逼出"同步落主表",牺牲项目最大招牌「抢号只动 Redis,DB 异步刷扛写峰值」——性价比差。
- **为何敢只动 Redis**:Redis `occupy:{rno}` 预占记录本身就是可恢复的 outbox(详见 02)。`pending-reservation-scanner` 扫超时未落库预占补投 MQ,落库失败超时则用 §04 10.2a 原子撤销 Redis。可靠性由「可重试 + 可补偿 + 可对账」给到。
- **诚门口径**:B 方案在 **Redis 持久化丢失(AOF 丢)场景下可靠性降一档**——bucket 余量只在 Redis,DB 存 `occupied` 异步滞后,Redis 崩+AOF 丢只能回 DB `occupied` 近似重建。但该场景在单机 AOF 下小概率,而代价(牺牲招牌亮点)不对称,故仍选 B。

> 与 docs-old 定稿 M2(事务消息)冲突 → **M2 作废,M8(不暴露 PENDING)仍成立**。落库窗口期(典型<1s,极端分钟级)DB 无记录,前端用 Redis `occupy` 兜(见 D1)。

## 二、B 方案派生决策 D1–D8(含 6 处自审修正)

### D1 落库窗口期数据源 = A:occupy 承载满展示载荷

`occupy:{reservation_no}` Hash 塞:`slot_id / slot_date / slot_hour / valid_until / bucket_no / user_id / id_card_masked / create_ts`。

- 窗口期预约成功页 + 「我的预约/详情」全程 Redis 渲染;DB 落库后字段一致无缝切。
- **为何敢 denormalize**:slot 字段发布后锁定(九约束:已放号禁改桶数、容量只增,slot_hour/valid_until 发行即定),user 脱敏字段注册后不变 → **staleness 风险为 0**。
- 备选 synthetic(occupy 只存四主键+slot_meta 合成):单源真理但成功页每次多 2 lookup,且 staleness 实为 0 故无收益,弃。

### D2 pending-scanner 枚举 = A:ZSet 索引

- Lua 内 `ZADD pending:persist {create_ts} {reservation_no}`;消费成功 `ZREM`;scanner `ZRANGEBYSCORE 0 (now-30s)` 精确捞超时者。
- ☑ **修正**:10.2a 补偿撤销最后一行**必须补 `ZREM pending:persist {rno}`**,否则 ZSet 泄漏、scanner 脏扫。
- scanner 捞到 rno 后先 `EXISTS occupy` 判定:存在→补投 MQ;不存在(已过期/已回滚)→显式 `ZREM` 清理。

### D3 穿透 bug + slot:meta = A:应用层前置校验

- **修复 docs-old §10.1 缺陷**:不判 slot 状态导致未放号/已过期/不存在的 slot_id 被误报「约满」或「可约」。其中**已过期能抢号 = 真 bug**(M1 不返还但桶还在 → 抢到进不了园)。
- slot:meta Hash 缓存 + 应用层前置校验(已放号 且 未过期才进 Lua),非法返回「未放号倒计时/已结束」。
- **理由修正**:否决 Lua 内校验的真实理由是「业务分支清晰(三种返回带倒计时)、不把状态校验与原子扣减耦合进同一脚本」,非「Lua 短小」(HGET 成本可忽略,那借口站不住)。
- slot:meta 低频元数据 → 主动维护(放号/增容刷新)+ 单飞重建兜底 + 空值缓存 NULL(与 slot:full **不可复用同 key**,语义/存活期均不同)。
- ⚠️ 单飞**只用在 slot:meta 重建**;桶余量/`slot:full`/`dup` **不套单飞**(它们是原子写对象,套锁破坏 Lua 原子性)。

### D4 限流分层 = A:本地 + Redis 双层(简历密度优先,需诚实标注)

- 本地 Guava RateLimiter:**接口级 + STAFF 核销级**(零 Redis 开销削峰)。
- Redis RRateLimiter:**用户级 + 场次级**(必须全局精准两维)。
- **诚实标注**:demo 单实例下,纯本地 Guava(D4-C)+ ZSet 风控路径更短(少 1 Redis round-trip)。选 A 的真实动机是**简历展示 RRateLimiter**,非单实例 perf 最优。多实例水平扩时 A 才技术占优(本地各自不精准可接受,用户/场次级靠 Redis 全局)。
- ⚠️ 隐患:限流与抢号争同一台 Redis。A 方案下抢号路径仍有"取令牌+Lua"2 round-trip → 在 05 标注为已知开销,非瓶颈(令牌桶取令牌远轻于 Lua)。

### D5 部署实例数 = 支持多实例,demo 单实例

- 抢号无状态可水平扩(Lua 原子无需应用层锁);放号靠 Redisson 选主保留分布式亮点。
- 压测单实例,简历诚话语术:「瓶颈在 Redis 单线程,不在应用;多实例选主放号已验证」。
- D4-A 与 D5 单实例的张力见 D4 诚实标注。

### D6 消费者事务边界 = 分阶段(修正:非原子四表)⚠️

- ~~早先版本误写「四表本地事务原子」~~ reservation **分库**(user_id → ds0/ds1),route/event/slot_bucket.occupied 在 **单库** reservex_single,**跨库不能一个本地事务原子**。
- **分阶段**(☑ 第八轮细化为五阶段,完整口径见 02 §五):
  0. **阶段0(前置读)**:`HGETALL occupy:{rno}` 定 `target_status`(cancelled→2 / expired→3 / 否则 0)。**必须在阶段1 之前**——原文档写"阶段2 读标记→阶段1 改写"时序不成立。
  1. `INSERT reservation`(分库表,`status = target_status`);**主键冲突 → 不 ACK 跳过,继续阶段2**(上次可能跑完阶段1 就 crash)。
  2. 单库本地事务(`@Transactional("singleTxManager")`):`state_log` Try(☑ 新增写入点,03 §6.1)∪ `id_card_route` ∪ `reservation_event` ∪ `slot_bucket.occupied+1`。
  3. **阶段3 收尾(顺序不可换)**:写 `consumed_event` → 复查 `occupy.cancelled` → `ZREM pending` → `DEL occupy`。
  4. 投递 ReminderTrigger + TimeoutExpire。
- route 唯一冲突(DuplicateKey)→ 先 CAS 清阶段1 孤儿 reservation(`0→2`)→ 转发 compensate-rollback 执行 10.2a → 当前消息 ACK。
- 基础设施异常 → 抛异常 → 重投 + DLQ,**绝不自主 10.2a**(04 §三·补)。
- ☑ **`consumed_event` 一律"成功后写"**(阶段3 步骤1),不是"先写"——先写会在阶段1 崩时永久丢预约(02 §5.1)。唯一例外是 reminder-consumer(界外调用,发邮件前写)。
- `occupied` 少 +1 / route 缺失由对账补(对账本就比对 db_occupied vs redis_occupied, dup 第一道在)。

## 三、统一口径(编码通用参考)

### 3.1 两类回滚必须区分(最易出错)

| 类型 | 触发 | Redis 桶 | dup | occupy | 待落库索引 |
|---|---|---|---|---|---|
| **A 创建失败补偿** | **仅** route 唯一冲突(消费者业务失败 ACK 后驱动,见 04 §三) | **+1 回补** | **删**(没约成应允许重试) | 删 | ZREM pending |
| **B 取消/过期** | 预约已成立后作废 | **不动**(不返还) | **不删**(配额消耗不可改约) | 删(消费者落库后已 DEL;B 类读 DB 不读 occupy,无需额外清) | 已在 B 路径,与 pending 无关 |

> ⚠️ A 类触发**只限 route 冲突**(业务已判定不可成立且原消息已 ACK 不会再重投)。基础设施异常(DB 超时/网络)**不触发 10.2a**——走重投+DLQ+人工,自主放弃会与 pending-scanner 补投竞态致幽灵预约(04 §三·补)。route 冲突时消费者须先 CAS 清阶段1 孤儿 reservation(`status 0→2`)再发 CompensateRollback,防 B 向对账误重建。

A 用 Lua(04 §10.2a);B 纯 DB CAS(03 状态机)。docs-old 把二者混在一个 Lua,**作废**。

### 3.2 occupied 语义

`slot_bucket.occupied` = **累计成功预约数(含取消/过期,不返还故不减回)**,非"当前有效占用"。真实有效入园数用 `status=VERIFIED` 统计,与 occupied 解耦。对账统一比对全部 slot,无需"跳过已结束 slot"特例。

### 3.3 状态码

| TINYINT | 语义 | 含义 |
|---|---|---|
| 0 | RESERVED | 预约成功待入园 |
| 1 | VERIFIED | 已核销入园 |
| 2 | CANCELLED | 主动取消 |
| 3 | EXPIRED | 超时未核销 |

不暴露 PENDING(M8);落库窗口由 Redis occupy 兜。简历仍写「参考 TCC 思想自研两阶段状态机」。

## 四、实施阶段(沿用 docs-old 规划四阶段)

### 6.2·补4 第十二轮:运行期承载(☑ 追加 3 项 P0)

### 6.3 七条新增的全局纪律(比单点修补更重要)

1. **窗口期的所有"终态意图"都只用 occupy 标记表达**(`cancelled` / `expired`);**occupy 的删除权只属于两处:消费者落库成功、10.2a 回滚。** 取消不删、timeout 不删、scanner 不删。(消除了 02/04/06 三处口径不一)
2. **幂等表写入时机的判据**:问一句"这个动作重复执行一次,有没有唯一键/CAS 会把它变成 no-op?" 有 → **成功后写**(幂等表只是加速跳过);没有(尤其界外调用)→ **动作前写**(幂等表就是唯一防线)。
3. **任何"桶余量从 0 变正"的路径都必须 `DEL slot:full`**:10.2a 补偿 / 10.3 放号 / 增容,一个不能漏。
4. ☑ **每个 `NOT NULL` 列都要问"所有写入路径都拿什么填它"**(第九轮新增)。`qr_nonce` 就是反例:扫码路径填得上,手工核销路径填不上——**一条路径填不上的 `NOT NULL` 不是约束,是编译期就该发现的 bug**。同理每个"唯一键"都要问"失败/重试路径会不会因为撞它而连日志都写不下"。
5. ☑ **每个跨边界传递的值都要问"到对面还是同一个值吗"**(第十一轮新增)。三条边界各有一个默认值是错的:**JSON 边界**(Long → JS 数字,超 `2^53` 静默改写)、**容器/驱动边界**(时区默认 UTC,差 8h)、**Redis 读法边界**(通配扫描 vs 按 `bucket_count` 精确拼 key)。判据:**这一层的缺陷不会让功能测试变红**——所以必须靠"逐位比对真值"的用例专门去抓(09 §6.7),而不是等业务用例发现。
6. ☑ **每个"承诺了资源隔离/容量保护"的句子都要问"那个池/阈值在哪个配置项里"**(第十二轮新增)。凡是 docs 里写了"独立线程池""连接池占用率告警""削峰靠消费线程池"却指不出 yml 具体项的,都是**空承诺**——与 `state_log` 曾经"有表无写入点"完全同构。配套判据:**每个中间件的默认值都要问一句"默认值对本项目是对的吗"**。三个反例:Redis 默认 `maxmemory` 无上限(→ OOMKilled 而非降级)、Spring `@Scheduled` 默认池 **1**(→ 一个慢任务停掉全部定时任务)、Docker `stop_grace_period` 默认 **10s**(→ 小于停机窗口,每次重启都 SIGKILL)。**默认值不是中立的,它是别人替你做的决定**。
7. ☑ **每个"从零起一次"的步骤都要有可执行定义**(第十三轮新增)。判据:**假设接手者拿到的是一台干净机器和这份 docs,他能不能只靠文档把系统起起来?** 凡是文档里出现"初始化脚本""种子数据""超管账号""前端产物""topic 创建"这类名词却指不出具体文件与内容的,都是缺口。这一档缺陷**在功能测试里根本跑不到**——因为测试环境是手工搭好的,而缺口在"搭"这一步。空库初始化只在明确可丢弃的独立 Compose project 上验;已有业务卷由 `mysql-migrate` 执行不可变迁移,禁止删除。**这条纪律的另一半是:凡是"红线清单里有但代码里没断言"的条目,迟早会被违反** —— 动工时应把 48 条红线过一遍,标出哪些能做成启动断言(如四把密钥两两不等、`maxmemory-policy=noeviction`、`daily-per-idcard != 1`)、哪些能做成集成测试、哪些只能靠人眼。

### 6.3·补 判据升级:缺陷按"会不会让测试变红"分四档

> 这是十三轮下来最可复用的一条方法论,比任何单点修补都值钱:

| 档 | 特征 | 例子 | 抓法 |
|---|---|---|---|
| **会变红** | 状态不对、字段为空、接口 404 | 前十轮绝大多数 P0 | 普通功能/集成测试 |
| **永远绿(值被改错)** | HTTP 200、无异常,值在跨边界时被改写 | 第十一轮三条(ID 精度 / 时区 8h / `KEYS` 读法) | **拿真值逐位比对**(09 §6.7) |
| **低并发也绿(资源不够)** | 功能全对,只在峰值/长跑/重启时形变,且现象指向错误方向 | 第十二轮三条(内存策略 / 池大小 / 停机) | **峰值 + 长跑 + 主动杀进程**(09 §6.8) |
| ☑ **根本跑不到(缺口在"搭"这一步)** | 测试环境是手工搭好的,缺陷藏在初始化路径里;表现是**换台机器就起不来**,而所有业务代码都对 | 第十三轮四条(模板表 / `init.sql`+超管 / AES IV 与密钥版本 / 登录读路径) | **在可丢弃的独立 Compose project 上空库一键起**(09 §6.9) |

> 推论:**验收顺序必须与这四档对应**——先在干净环境把系统起起来(第四档),再跑功能用例,再跑逐位比对用例,最后跑峰值/长跑/故障注入。只做第一档就宣布"可交付"是十三轮里最一致的教训;而第四档必须排在**最前**,因为它是其余三档的前置条件——起不来就什么都测不了。

### 6.4 明确认下的新降级点(诚实边界扩充)

| 降级点 | 认什么 | 为何认 |
|---|---|---|
| **提醒邮件永久漏发** | 先写幂等表后发邮件,发送失败则该提醒永不重发 | 取舍是"宁可漏发一封,不可重复轰炸";提醒是非核心任务,漏发=体验降级。两者都保需引入邮件发送状态机,v1 不做(06 §3.3) |
| **补偿链路是冷路径** | dup TTL 修好后 route 冲突在正常运行中不可能触发,10.2a 只在病理态执行 | 正确性上是好事(说明第一道防线够硬),工程上必须靠**故障注入**保证代码跑过(09 §6.1 三种构造法) |
| ☑ **单一本地时区,跨时区不可扩** | 全链路钉 `Asia/Shanghai`(08 §7.2),日期语义即本地自然日 | 配额键 `dup:{slot_date}` 与 `id_card_route` PK 的"天"就是本地自然日;UTC 存会把一个本地日裂成两个 `slot_date`,**配额键直接失真**。代价:真要多时区园区需重构日期语义,单区业务不预付这个成本 |
| ☑ **Redis 内存到顶 = 抢号不可用**(不是丢数据) | `noeviction` 下写命令返 OOM,抢号整体降级为 `SERVICE_DEGRADED`(08 §7.3) | 这是**主动选的方向**:宁可"抢不到但有报错、可重试、可告警",不可"库存被静默逐出"。代价是内存打满时抢号完全不可用(而非部分可用),换来的是库存永不无声丢失。前兆靠 `used_memory/maxmemory >70%` 告警 |
| ☑ **v1 舱壁只隔离旁路,不隔离主链路** | 抢号/核销仍共用 Tomcat 线程池,只有邮件/对账/定时是独立池(08 §7.4) | 主链路是同步短请求(2 次 Redis round-trip),给它套 `@Async` 池只会多一次线程切换 + 队列排队,反而抬高 p99;主链路的隔离由**限流维度 + Redis key 命名空间**承担(05 §五)。代价:抢号洪峰会挤占核销的 Tomcat 线程 —— v1 用"核销走本地 Guava 限流优先级"缓解,真要物理隔离得拆 worker(v2,D8 已留边界) |
| ☑ **`id_card_hash` 的 pepper 不可轮换** | pepper 泄露则身份证 hash 可被彩虹表反推,而**换不了** | pepper 进了 `id_card_route` 的 PK(M6 一证一天一约要求 hash 跨用户可比),轮换 = 全表 hash 作废 + PK 重建。**这是"业务不变量赢过密码学最佳实践"的代价**,只能靠"与 AES 密钥同级保护:仅环境变量、不入 git、不进日志"缓解(03 §2.1) |
| ☑ **JWT access 仍有 Redis 登录映射** | JWT 负责签名与 30min 过期；Sa-Token Simple 模式同时保存 token mapping/session，注销、改密和封禁会即时撤销 | 这是已运行验证的真实实现，不再宣称“无状态 access”。代价是每次鉴权依赖 Redis；收益是旧 access 不会在注销后继续有效(08 §4.6) |
| ☑ **initdb 只负责首次初始化** | `docker-entrypoint-initdb.d` 只在空数据目录执行一次;已有卷由一次性 `mysql-migrate` 服务按顺序执行不可变 SQL 迁移 | 每个已应用文件记录 SHA-256 checksum,历史内容变化会阻断启动;新增变更只追加迁移。空库验收使用可丢弃的独立 Compose project,不删除业务卷(08 §4.1 / 09 §6.9) |

### 6.5 动工顺序

见 **09 §七·补 MVP 验收顺序**(0–10 阶段,每阶段有可验证产出)。编码时手边常备两张表:**08 §十 编码红线清单(48 条)** 与 **03 §十 字段对齐自检表**;写 controller 前先落 **07 §3·补 的 `Result<T>` + 错误码枚举 + ObjectMapper(Long→String)**。

**阶段 0 必须在明确可丢弃的独立 Compose project 上做一次空库初始化验收**,并在那一次里验完四件地基(顺序无所谓,但都要在写业务代码之前):

1. **起得来** —— `http://localhost` 看到前端页面(不是 404)、三库表齐、超管可登录且行落在 `ds1`(08 §4.1 / 09 §6.9 用例 1–3);
2. **密钥对** —— 四把密钥两两不等的启动断言真的会拒绝启动(08 §4.2 / 09 §6.9 用例 4);
3. **时区对** —— 容器 / MySQL / JVM 三处 `Asia/Shanghai` 一致(08 §7.2 / 09 §6.7 用例 4);
4. **Redis 前提对** —— `maxmemory-policy=noeviction` 且 `appendfsync=always`(08 §7.3 / 09 §6.8 用例 1/4)。

> 后两条不先验,后面所有时间判据与"库存放 Redis"的前提都建在错的地基上;前两条不先验,换台机器就起不来而查不出原因。**这四条是唯一"必须早于所有业务代码"的验收项。**
