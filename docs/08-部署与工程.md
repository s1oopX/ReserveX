### 4.1 `init.sql` 的内容与顺序(☑ 第十三轮 P0 补:原只有一句注释)

⚠️ **原缺口**:compose 挂载 `init.sql`、工程结构写「建库 + 建表 + 预置超管」、09 阶段 0 的验收是「三库表齐、**超管可登录**」——三处都把这个文件当既存事实,但**它建哪些库、超管怎么来、密码哪儿定、role 怎么写**全未定义。而它是**动工的第 0 步**:这个文件不确定,阶段 0 就无法验收,后面九个阶段全部悬空。

**拆成两个文件**(MySQL 按文件名字典序执行,故用数字前缀):

**`01-schema.sql`** — 建库 + 建表,纯 DDL,可重复执行:

```sql
CREATE DATABASE IF NOT EXISTS reservex_ds0    DEFAULT CHARSET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
CREATE DATABASE IF NOT EXISTS reservex_ds1    DEFAULT CHARSET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
CREATE DATABASE IF NOT EXISTS reservex_single DEFAULT CHARSET utf8mb4 COLLATE utf8mb4_0900_ai_ci;

-- ds0 / ds1:**结构完全相同**,各建 user + reservation(03 §二/§五)
--   ⚠️ 两库必须逐字一致:字段/索引/默认值有任何差异 → 按 user_id mod 2 落到不同库的
--      同一业务在两库表现不同,而分片是随机的,故现象是"部分用户功能异常"(最难查的一类)
--   落地建议:一份 `sharded-tables.sql` 用 `USE reservex_ds0;` / `USE reservex_ds1;` 各引一次,
--      而不是手抄两份 —— 手抄两份必然在某次改字段时漏改一边。
-- single:建 03 §三/§四/§六/§七 的 13 张表
--   email_route / phone_route / id_card_route
--   slot_template / slot / slot_bucket
--   state_log / reservation_event
--   consumed_event / reconcile_log / verification_log / audit_log / stuck_reservation
```

**`02-seed.sql`** — 种子数据,只有三类,**每类都要能重复执行不出错**:

| 类 | 内容 | 幂等写法 | 为何必须有 |
|---|---|---|---|
| **超管账号** | `user` 一行,`role='ADMIN'` + `email_route`/`phone_route` 各一行 | `INSERT IGNORE`(PK/route PK 挡重复) | 09 阶段 0 验收项;**没有超管就没有任何人能建模板 → 整条发布链路无法启动**(鸡生蛋) |
| **场次模板** | `slot_template` 四行,来自 yml 的 `template-hours: [9,11,14,16]` + `default-*` | `INSERT IGNORE`(`uk_hour` 挡重复) | 03 §4.0:yml 那几项**降级为种子**,此处是它们唯一的使用点 |
| **无别的** | 不预置 slot、不预置测试用户 | — | slot 由生成任务按模板产出(06 §4.3),预置会与 `uk(slot_date,slot_hour)` 打架;测试用户由 09 §一 的脚本批量注册,走真实注册链路才能验证跨库两写 |

**超管账号的四个坑(逐条钉死)**:

1. **`user_id` 不能随机**:seed 是 SQL,拿不到 Snowflake。**固定写 `1`**(Snowflake 起始远大于 1,永不冲突),`1 mod 2 = 1` → 必须插进 **`reservex_ds1`**。⚠️ 插错库的后果:登录第 2 跳按 `user_id=1` 路由到 ds1 查不到 → 「超管不存在」,而 route 表里明明有 —— 看起来像"孤儿 route",实际是 seed 插错了库。**这是阶段 0 最容易卡住的一条。**
2. **密码不能是明文常量**:`password` 列存 BCrypt 串。做法:`ADMIN_INIT_PASSWORD` 环境变量 + **应用启动时的 `@PostConstruct` 引导**(而非 SQL 里写死 hash)——SQL 里写死 hash 等于把一个固定密码永久钉进 git。
   - **落地口径**:`02-seed.sql` 只插 `email_route`/`phone_route` 占位与 `user` 行(`password` 存一个**不可能匹配任何输入**的哨兵值如 `'!'`),应用启动时检测该哨兵 → 用 `ADMIN_INIT_PASSWORD` 算 BCrypt 写入 → 记 `audit_log(action='ADMIN_BOOTSTRAP')`。
   - **首次登录强制改密**:`ADMIN_INIT_PASSWORD` 来自 `.env`,团队可见。改密页 v1 可复用「忘记密码」页(07 §四 公共页)。
3. **`role='ADMIN'` 只能由 seed/引导写**:与红线「注册接口 `role` 写死 `USER`」(07 §3·补·3)呼应 —— **系统里第一个 ADMIN 必须由部署产生,不能由任何 HTTP 接口产生**,否则接口本身就是提权漏洞。此后的 STAFF/ADMIN 由超管在「STAFF 管理」页创建。
4. **超管也要有 `id_card_ciphertext`/`id_card_hash`(NOT NULL)**:但超管不需要真身份证。**填一个保留占位值**(如 `id_card_hash = SHA-256(pepper||'ADMIN-RESERVED-0001')`),且该 hash **不进 `id_card_route`** —— 超管不预约。⚠️ 这里正是 README 纪律 #4「每个 NOT NULL 列都要问所有写入路径拿什么填它」的又一个实例:seed 路径与注册路径填法不同,不问就会在跑 `01-schema.sql` 后卡在插入失败。

> ⚠️ **`docker-entrypoint-initdb.d` 只在数据目录为空时执行一次**。改了 schema 后重启 compose **不会重跑**——现象是"我改了 DDL 但表还是老的"。开发期重置:`docker compose down -v`(删卷)再起。**这条要写进 README 的开发说明**,否则每个第一次接手的人都会踩。
>
> ⚠️ **生产不该用 initdb 做 schema 管理**。v1 演示形态接受;演进方向是 Flyway/Liquibase(`backend` 启动时执行迁移),届时 `01-schema.sql` 变成 `V1__init.sql`。**这一条要认下**,别把 initdb 说成"数据库版本管理方案"。

### 4.2 `.env` 与密钥清单(☑ 第十三轮 P0 补:compose 引用 8 个变量,原 docs 定义 0 个)

⚠️ **原缺口**:compose 用 `${AES_KEY}` 等做密钥注入(方向正确),但**从未列出完整变量清单、生成方式、长度要求**。后果:`docker compose up` 时未定义的 `${X}` 被**静默替换为空字符串**——AES 用空 key 会启动即报错(还算好),而 `MYSQL_ROOT_PASSWORD` 为空则 MySQL 容器**直接拒绝启动**且报错信息与密钥无关,排查方向全错。

**`.env`(与 `docker-compose.yml` 同目录,`.gitignore` 必须含它;仓库里放 `.env.example` 只写变量名不写值)**:

| 变量 | 用途 | 要求 | 轮换 |
|---|---|---|---|
| `MYSQL_ROOT_PASSWORD` | MySQL root | 任意强口令 | 改后需 `down -v` 或手工改库内用户 |
| `REDIS_PASSWORD` | Redis `requirepass` | 任意强口令 | 改后重启 redis + backend |
| `AES_KEY` | `id_card_ciphertext` AES-256-GCM | **32 字节**(base64 后 44 字符) | ✅ 支持:加新 key + 改 `aes.key-id`,旧行按 `id_card_key_id` 继续可解(03 §2.1) |
| `ID_HASH_PEPPER` | `id_card_hash` 的 pepper | ≥32 字节随机 | ❌ **不可轮换**(进了 `id_card_route` PK,03 §2.1 已认下) |
| `QR_HMAC_KEY` | QR 载荷 HMAC-SHA256 | ≥32 字节随机 | ✅ 支持:`qr.accepted-key-ids` 双 key 并存(07 §3.4.1) |
| `JWT_SECRET` | Sa-Token JWT 签名 | ≥32 字节随机 | ✅ 支持但**轮换即全员掉线**(access 无法验签);低成本,提前公告即可 |
| `QQ_SMTP_PASSWORD` | SMTP 授权码 | 邮箱服务商给 | 随时 |
| `ADMIN_INIT_PASSWORD` | 超管首登密码 | 强口令 | 首次登录后立即改(§4.1) |

- **四把密钥必须互不相同**(`AES_KEY` / `ID_HASH_PEPPER` / `QR_HMAC_KEY` / `JWT_SECRET`)。理由已在 07 §3.4.1 与 03 §2.1 各说一半,此处合并成一条:**它们的泄露后果、轮换成本、可轮换性三者全不同**——AES 泄露=历史身份证可解且可轮换;pepper 泄露=hash 可彩虹表攻且**不可**轮换;QR key 泄露=可伪造任意二维码但轮换零成本;JWT secret 泄露=可伪造任意用户身份(含 ADMIN)。共用一把 = 用最坏的那条约束绑住全部,且**一处泄露即全线失守**。
- **启动断言**(与 `daily-per-idcard != 1` 同一处 `@PostConstruct`):四者两两相等 → **fail-fast 拒绝启动**;任一为空或长度不足 → 同样拒绝。这比"文档里写了但没人查"可靠。
- ⚠️ **`.env` 里的值不进日志**:`/actuator/env` 会输出配置(已由 §五 的 Caddy 规则挡在公网外,红线 #35),但**容器网内仍可访问** → Spring Boot 默认对 `*password*`/`*key*`/`*secret*` 命名的属性做脱敏,故 yml 里的属性名必须**带这些关键词**(`aes.key`、`qr.hmac-key`、`smtp.password` 均已合规;若改名成 `aes.material` 就会明文输出)。

### 4.3 `restart:` 策略(☑ 第十三轮补:第四处"默认值对本项目是错的")

原 compose **五个服务一个 `restart:` 都没有**,默认 `no` —— 容器退出即不再起。这与两处设计**直接冲突**:

- §7.4 的 `-XX:+ExitOnOutOfMemoryError`:其全部价值是"OOM 后立刻退出**让 compose 重启**",没有 restart 策略则退出后就永久死了,比"半死不活"更糟;
- §6.1 的死信/积压告警假设了应用在跑。MySQL 或 Redis 崩后不自启,整套演示直接停摆,而演示形态没有 K8s 之类的外部编排接管。

**钉死**:四个常驻服务(mysql/redis/rmqnamesrv/rmqbroker/backend/caddy)一律 `restart: unless-stopped`;两个一次性服务(`rmq-init`/`frontend-build`)一律 `restart: "no"`(它们**跑完就该退出**,配 `unless-stopped` 会让 compose 无限重启一个已完成的任务并把日志刷满)。

> ⚠️ **不要用 `restart: always`**:`always` 在 `docker compose stop` 手工停止后,宿主重启时仍会把容器拉起来 —— 演示/调试期"我明明停了它怎么又起来了"就是这条。`unless-stopped` 记住手工停止的意图。
>
> ⚠️ **restart 不是高可用**:它只处理"进程死了",不处理"进程活着但不健康"(如 §7.3 的 Redis 内存打满——`ping` 仍 PONG)。故 §6.1 的降级指标不可被"反正会重启"取代,这两者管的是不同故障(与 06 §6.1 矩阵里「Redis 挂的第三种形态」同一个道理)。

### 4.4 RocketMQ topic 的创建口径(☑ 第十三轮补)

⚠️ **原缺口**:06 §一 列了 6 个 topic(`reservation-created` / `compensate-rollback` / `reminder` / `timeout` / `slot-release` / 可选 `ReservationVerified`),但**谁建、何时建**从未定义。broker 的 `autoCreateTopicEnable` 默认 `true`,所以"看起来能跑",但依赖它有三个真实问题:

1. **自动创建的 topic 只有 1 个队列**(默认 `defaultTopicQueueNums=4` 是给 `TBW102` 模板的,实际首次投递创建的 topic 队列数受限),`persistence` 配了 20 个消费线程(§7.4)却只有少量队列可分 → **消费并发度被 topic 队列数卡死**,现象是"线程数调大了但落库延迟没降"。这是一条典型的"配置都对但跑不满"的承载缺陷(与 §7.4 同族)。
2. **首次投递会失败/超时**:自动创建发生在第一条消息投递时,而抢号线程是**同步发消息**(`send-message-timeout: 3000`,§七)。放号瞬间的第一条消息可能因建 topic 而变慢 → 抢号侧超时 → 白走一次 pending-scanner 补投。
3. **生产环境通常关闭 `autoCreateTopicEnable`**,依赖它写出来的代码换环境即挂。

**钉死**:`docker/rocketmq/topics.sh` 由一次性容器 `rmq-init` 执行(§四已加),内容为对 6 个 topic 逐个:

```sh
# 幂等:updateTopic 对已存在的 topic 是更新而非报错,故可重复执行
mqadmin updateTopic -n rmqnamesrv:9876 -c DefaultCluster -t reservation-created -r 8 -w 8
mqadmin updateTopic -n rmqnamesrv:9876 -c DefaultCluster -t compensate-rollback -r 4 -w 4
mqadmin updateTopic -n rmqnamesrv:9876 -c DefaultCluster -t reminder            -r 4 -w 4
mqadmin updateTopic -n rmqnamesrv:9876 -c DefaultCluster -t timeout             -r 4 -w 4
mqadmin updateTopic -n rmqnamesrv:9876 -c DefaultCluster -t slot-release        -r 2 -w 2
```

- **队列数按消费线程数配**:`reservation-created` 是唯一的高吞吐 topic(每次抢号一条),`persistence` 20 线程 → 给 8 个队列(单队列可被多线程并发消费,但队列数 < 消费者实例数时会有实例空转;单实例形态 8 足够且留出 D5 多实例的余量)。`slot-release` 靠选主执行,队列数 2 即可。
- **`rmq-init` 用 `service_completed_successfully` 门控 `backend`**(§四已加):topic 先在,应用再起,彻底消除上面的问题 2。
- **不关 `autoCreateTopicEnable`**:v1 保留它作为兜底(万一 `topics.sh` 漏了一个 topic,自动创建能让功能不挂,只是队列少)。**但队列数不足这件事要能在监控上看见** —— §6.1 加一句:若 `reservation-created` 的落库延迟 p99 高而 `persistence` 线程忙碌数低,**先查 topic 队列数**,这是最容易误判成"MQ 慢"的一个点。

### 4.5 前端产物如何进 `frontend-dist`(☑ 第十三轮补:原卷被挂载但无人填充)

⚠️ **原缺口**:`caddy` 挂载 `frontend-dist:/srv/frontend` 并 `root * /srv/frontend`,`volumes:` 声明了 `frontend-dist`,工程结构里 `frontend/Dockerfile` 写着「多阶段构建」—— **但 compose 里没有任何服务构建前端、也没有任何步骤把 `dist/` 放进那个卷**。`docker compose up --build` 的实际结果是:**Caddy 托管一个空目录,访问 `http://localhost` 返回 404**,而后端接口全正常。这是"一键起全套"这句承诺的直接反例,且会在第一次演示时当场发生。

**钉死**:加一次性服务 `frontend-build`(§四已加),`frontend/Dockerfile` 多阶段的最后一层只需含 `dist/`:

```dockerfile
FROM node:20-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build          # 产出 /app/dist
FROM alpine:3.20           # 最后一层不需要 nginx —— 静态托管由 Caddy 做
WORKDIR /app
COPY --from=build /app/dist ./dist
```

服务的 `command` 把 `dist/` 拷进命名卷,`caddy` 用 `service_completed_successfully` 等它完成。

> ⚠️ **为什么不让前端容器自己跑 nginx**:那样就有两个静态服务器(nginx + Caddy),且 `/api` 反代规则要写两遍。Caddy 已在做反代与静态托管(§五),前端只需交付产物。
>
> ⚠️ **改了前端代码要重跑构建服务**:`docker compose up --build frontend-build`。命名卷里的旧产物**不会自动清**——`cp -r` 只覆盖同名文件,删掉的旧文件(如改名后的 hash 资源)会残留。开发期无害(index.html 只引用新 hash),但长期会让卷越来越大;真要干净:`docker compose down -v` 或在 `command` 里先 `rm -rf /srv/frontend/*`。**v1 取"先删再拷"更省心**,故 `command` 可写成 `sh -c "rm -rf /srv/frontend/* && cp -r /app/dist/. /srv/frontend/"`。
>
> ⚠️ 开发期不必走这条链路:`npm run dev` + Vite proxy(§六)更快;`frontend-build` 是**演示/交付**路径。

### 4.6 Sa-Token 会话存到哪里 + 为何不给 Redis 分库(☑ 第十三轮补)

⚠️ **原缺口**:§三 写「Sa-Token 1.37.x 鉴权(**JWT 双 token**)」、§9.1 写「三角色 + JWT 双 token」,07 §3·补·3 有 `POST /api/auth/refresh`。但**会话状态存哪**从未定义,而这个选择直接决定两件事:注销能不能立即生效、封禁能不能立即踢人。

**裁定:JWT 无状态 access + Redis 存 refresh 白名单**(Sa-Token 的 `sa-token.is-share: false` + `token-style: uuid` 的 refresh + jwt 模式混用):

| 层 | 存哪 | TTL | 为什么 |
|---|---|---|---|
| **access token** | **不存**(JWT 自校验签名) | 30min | 每个请求都要鉴权,若查 Redis 则**每次抢号多一个 round-trip** —— 与 D4-A「抢号只 2 次 Redis round-trip」的口径直接冲突(05 §二)。无状态是这里的硬约束,不是偏好。 |
| **refresh token** | Redis `satoken:refresh:{userId}:{jti}` | 7d | 需要能主动失效(注销/封禁/改密),故必须有状态。低频(30min 一次),多一跳无所谓。 |

**代价必须认下**:

- **注销后 access token 在最长 30min 内仍然有效**(JWT 无法撤销)。注销只删 refresh → 30min 后自然失效。**这是无状态换性能的必然代价**,不要说成"注销立即失效"。
- **封禁用户同理**:`user.status=1` 后,他手上的 access 仍能用 30min。若要立即生效,需要在鉴权链路查一次 Redis 黑名单 —— 那就把每请求一跳加回来了。**v1 的折中**:封禁时删该用户全部 refresh + 写一条 `ban:{userId}` 键,**只在抢号/核销两个写接口**查它(读接口不查)。这样封禁对"能不能再约"立即生效,对"能不能看列表"延迟生效 —— **符合业务上真正在意的那一面**。
- ⚠️ **JWT 里只放 `userId` + `role`,不放任何身份证/邮箱字段**。JWT 是 base64 明文可解的,放 `id_card_masked` 等于把脱敏串发给所有中间环节。

**为何 `database: 0`,不给会话/验证码另开一个库**:

看起来"库存真理源与缓存类 key 分库"更干净,尤其 §7.3 刚裁定 `noeviction`(会话被"不删"而占内存似乎浪费)。但 **Redis 的 `maxmemory-policy` 是实例级、不是 db 级** —— 分 db 完全不改变逐出/OOM 行为,只带来三个真实成本:

1. **Lua 脚本不能跨 db**,而抢号 Lua 要同时动桶/dup/occupy/slot:full/pending —— 这些必须同库(本就都在库存侧,不影响);但限流 key(`ratelimit:*`)若分到另一个 db,风控与限流就不能与抢号合并进同一个 Lua,**D4-A 的 2 round-trip 变 3**;
2. **Redisson / Lettuce 要配多连接工厂**,连接池被拆成两份(§7.4 的 `max-active: 64` 分母失效);
3. **运维视角割裂**:`used_memory` 是实例级,分 db 后仍是一个数,`--bigkeys`/`SLOWLOG` 也不分 db —— **想要的隔离一个都没得到**。

**钉死**:单 db(`0`),隔离靠 **key 前缀命名空间**(05 §五已定:`slot:*` / `occupy:*` / `dup:*` / `pending:*` / `ratelimit:*` / `captcha:*` / `satoken:*`)。真要资源隔离,正确做法是**独立 Redis 实例**(v2,与 06 §6.2 的 Cluster 演进同批考虑),不是 `SELECT n`。

> ⚠️ **会话/验证码占内存要算进 §7.3 的容量估算**:2000 并发用户 × (refresh ~200B + captcha ~100B) ≈ 600KB,相对 1gb 可忽略。但**它们与库存 key 共享 `noeviction`** —— 意味着内存打满时**登录也会失败**(写 refresh 被拒),不只是抢号降级。09 §6.9 用例要覆盖这一点:内存打满态下 `POST /api/auth/login` 应返 `SERVICE_DEGRADED` 而不是 `LOGIN_FAILED`(后者会让用户以为密码错了,这是**把系统故障说成用户错误**,与红线 #32/#40 同一类撒谎)。

### 6.2 熔断器设计(防误判七条,对位复盘 Q2)

⚠️ 本项目"熔断"与 06 §二·补"消费重试分级"是两回事——**重试分级是"本消息失败怎么办"(单条维度),熔断是"下游故障率超阈跳闸"(聚合维度)**。两者互补。

| 熔断要素 | ReserveX 落点 |
|---|---|
| 三态 CLOSED/OPEN/HALF_OPEN | Resilience4j,v1 引入配置 |
| **最小样本量** | 窗口请求数<20~50 不评估错误率,防低流量误熔 |
| **半开探测** | 只放 1~5 个探测请求,成功才全开,失败继续熔断 |
| **错误类型区分** | 业务错误(4xx/route冲突)不计入,只算 5xx/超时/连接异常 |
| **慢调用比例** | 下游没报错但全超时也熔(防线程被慢调用占满) |
| **超时按 p99** | 按 RT p99 定,非 p50(防频繁误判慢调用) |
| **渐进恢复** | 半开成功逐步放量,非一次性全开 |
| **舱壁隔离** | 抢号/核销/查询独立线程池,一个挂不连累共享路径 → ☑ **具体池大小与拒绝策略见 §7.4**(原只有这句承诺,yml 无定义) |

> 本项目哪些下游该熔:**调 QQ SMTP(邮件)**——SMTP 超时率高,该熔+返回兜底(提醒延后);**调 RocketMQ(投递)**——已靠重试+死信,熔断边际增益小,可不配。核心链路(抢号 Lua/DB CAS)是本地操作不该熔。

### 6.4 容量水位看板(对位复盘根因)

数据驾驶舱(07 §四)须展示**容量水位**而非只看业务指标:
- 当前QPS / 安全水位QPS(09 §三)占比 → 接近80%告警(接近静态阈值上限)
- Redis单线程CPU占比 → >70%告警
- ☑ **Redis `used_memory / maxmemory`** → >70%告警(§7.3;到顶=抢号全线降级)
- MQ积压 / 队列最大积压阈值(复盘:队列超阈值快速失败) → 超阈值告警
- DB连接池占用率 → >80%告警(☑ **分母见 §7.4 的 Hikari 池大小**——原 docs 没定池大小,这个指标算不出来)

### 7.2 时区必须全链路统一到 `Asia/Shanghai`(☑ 第十一轮补:原全 docs 未提)

⚠️ **原缺口**:全项目的核心判据都是**时间比较**——`valid_until < now` 决定能否抢(02 §一)、`dup_ttl = slot_date 23:59:59 − now`(04 §1.1)、`exp >= now` 决定 QR 是否有效(07 §3.4.1)、`valid_until < NOW()` 决定批量过期(01 §3.2)、`release_at` 已过决定补放(06 §4.3)。但 docs **从未规定时区**,而默认值恰好三方不一致:

| 组件 | 默认 | 若不显式设置 |
|---|---|---|
| `mysql:8.0` 容器 | **UTC** | `NOW()` 比 JVM 早 8h → 06 §3.4 批量过期扫描把**当天还有效的**预约全刷成 EXPIRED |
| JVM(openjdk 容器) | **UTC**(除非设 `TZ`) | `LocalDateTime.now()` 与用户看到的时间差 8h |
| MySQL JDBC 驱动 | 按服务器时区推断 | DATETIME 读写来回偏移,`valid_until` 写进去与读出来不是同一时刻 |
| Redis | 无时区概念(存 unix 秒) | ✅ 天然安全,但**算 TTL 的那段 Java 代码**受 JVM 时区影响 |

**最刺眼的具体后果**:`dup_ttl` 要算"`slot_date` 当日 23:59:59 距现在多少秒"。JVM 若在 UTC,它算的是**北京时间次日 07:59:59** —— dup 多活 8 小时看似无害,但 `slot:full`/桶 key 用同一派生规则,**桶 key 多活 8h 意味着次日场次开始时前一天的余量还在**,10.3 放号的 `SET` 覆盖恰好又被 #13 的 CAS 拦住不执行 → 该 slot 用着昨天的桶。反向(JVM 在 +08:00 而 MySQL 在 UTC)则是过期扫描提前 8h 屠杀有效预约。

**钉死(三处都要设,缺一不可)**:

1. **容器**:`mysql` 加 `--default-time-zone=+08:00` + `TZ=Asia/Shanghai`;`backend` 加 `TZ=Asia/Shanghai`(§四已改)。
2. **JDBC URL**:三个数据源全带 `?serverTimezone=Asia/Shanghai`(§七已改)。
3. **应用**:`spring.jackson.time-zone: Asia/Shanghai`(§七已改);Java 侧一律用 `LocalDateTime` + 显式 `ZoneId.of(reservex.zone)` 算 unix 秒。**禁止代码里散落 `ZoneId.systemDefault()`**——它读的是容器 `TZ`,漏配就静默偏 8h 且无任何报错;时区常量只从 `reservex.zone`(§七)一处取,与 `dup-ttl-mode` 等派生规则共用同一 `ZoneId`(04 §1.1)。

> ⚠️ **为何不用 UTC 存、展示层转**(工业界更常见的做法):本项目的业务语义本身是**本地日历日**——"一人一天一次"的"天"是北京时间的天(`dup:{slot_date}`、`id_card_route` PK 的 `slot_date`),`slot_hour` 是本地时段。用 UTC 存会让"跨 UTC 零点的本地同一天"在 `slot_date` 上裂成两天,**配额键直接错**。单区业务用单一本地时区是正解,不是偷懒。这条要能答出来,否则会被追问"为什么不 UTC"。
>
> ⚠️ **压测/CI 环境同样要设 `TZ`**:09 的用例「dup TTL 跨天」(§6.4)在 UTC 机器上会**假绿**——它断言的是"TTL 覆盖到次日 23:59:59",UTC 下算出来的秒数更大,断言 `>=` 照样通过。故该用例须断言**精确到秒的目标时刻**,而非只断言"够长"。

### 7.3 Redis 内存与持久化策略(☑ 第十二轮补:原全 docs 未提)

⚠️ **原缺口**:整个 B 方案把**库存真理源**放在 Redis(桶余量),把**窗口期唯一凭证**放在 Redis(`occupy`),把**配额第一道**放在 Redis(`dup`),把**待落库索引**放在 Redis(`pending:persist`)。而 docs 从未规定 `maxmemory` 与 `maxmemory-policy`——原 compose 只有一句 `redis-server --appendonly yes`。这一项漏配的两种默认结局都很坏,且**都不会立刻报错**:

| 若配成 | 会发生什么 | 为什么最难查 |
|---|---|---|
| `allkeys-lru` / `allkeys-random`(很多教程的"标准配置") | 内存到顶时 Redis **静默逐出** key。逐出桶余量 = 库存凭空消失(抢号变"约满");逐出 `occupy` = 窗口期预约**永久丢失**(scanner 按 `EXISTS occupy` 判定"已过期/已回滚"直接 `ZREM` 清掉,D2);逐出 `dup` = 配额失效、route 冲突转为常态;逐出 `slot:full` = 只是多打几次 Lua(唯一无害的一个) | 逐出没有异常、没有日志、HTTP 全 200。表现是"库存对账 diff 无规律地变",而 diff 的方向与真超卖一致(01 §四前提4 同类陷阱) |
| 不配 `maxmemory`(默认无上限) | 容器内存吃满 → **OOMKilled**,而非降级。整个 Redis 进程消失,退化成 D7 的"Redis 挂"但没有任何前兆指标 | 看起来像"Redis 突然重启",实际是慢慢涨上去的 |

**钉死**:

1. `--maxmemory 1gb` + `--maxmemory-policy noeviction`(§四已改)。**noeviction 的语义是"到顶后写命令返回 OOM 错误,而不是删数据"** —— 这正是本项目要的:宁可抢号失败(可重试、可降级、有报错),不可库存被静默删掉。
2. **到顶是一个 D7 事件**:`noeviction` 下 Lua 里的 `HSET occupy` 会直接抛 `OOM command not allowed`。抢号侧**按 D7 的 `SERVICE_DEGRADED` 返回**(07 §3·补·2),不要归到 `SLOT_FULL`——理由与 #32 完全相同(那是撒谎且污染库存指标)。
3. `--appendfsync everysec`(§四已改)。这条是**"AOF 丢是小概率"那句诚实口径的量化依据**:`everysec` 下崩溃最多丢**最近 1 秒**的写;若配 `no`(交给 OS,可能 30s)则那句"小概率"就站不住,若配 `always` 则每次抢号都要等 fsync、Redis 单线程吞吐直接崩(与"只动 Redis 扛写峰值"的招牌冲突)。**面试被追问"AOF 到底丢多少"要能答出 `everysec` 与这三选一的取舍**,答"开了 AOF 就不丢"是错的。
4. 容量估算(证明 1gb 够,不是拍的):单 slot ≈ `bucket_count` 个桶 key(每个 ~80B)+ 1 个 `slot:meta`(7 字段 ~300B);单条在途 `occupy` Hash 8 字段 ≈ 500B,TTL 30min;`dup` ≈ 100B 活到当日结束;`pending:persist` ZSet 每条 ~50B。按 4 时段 × 7 天预生成 + 峰值 5 万在途 occupy 估:`5万×500B ≈ 25MB`,加限流/会话/验证码仍在百 MB 量级。**1gb 是 10 倍余量**;`maxmemory` 的作用不是省内存,是**把"内存失控"变成一个有明确报错的可观测事件**。
5. `--save 900 1` 保留 RDB:AOF 重放慢时 RDB 是更快的冷启动路径,且 06 §6.2 的演进项「AOF+定期 RDB 双持久化」在 v1 就顺手做了(零成本)。

> ⚠️ **监控要加一项**:§6.1 Redis 域已有"内存",此处明确阈值——`used_memory / maxmemory > 70%` 告警。这是唯一能在"到顶"之前看到的信号,而到顶的后果是抢号全线降级。

### 7.4 运行期容量:线程池、连接池、优雅停机(☑ 第十二轮补:原承诺了但没定义)

⚠️ **原缺口**:docs 在三处**承诺**了运行期资源隔离,但三处都把落点指向"08 §七",而 §七从来没有这些项:

| 承诺在哪 | 原文 | 原状 |
|---|---|---|
| §6.2 熔断七条之「舱壁隔离」 | "抢号/核销/查询独立线程池,一个挂不连累共享路径" | yml 无任何池定义 |
| 05 §五 核心链路降级 | "v1 单进程下用线程池隔离(08)" | 同上,指向空处 |
| §6.4 容量水位看板 | "DB连接池占用率 → >80%告警" | **没有池大小 = 没有分母**,这个指标算不出来 |
| D8 单进程模块化单体 | "削峰靠 MQ 消费线程池,非进程隔离" | RocketMQ 只配了 `max-reconsume-times`,并发度未定 |

**这一类缺口的性质与前十一轮不同**:前面几轮是"值/字段/契约不在",这一轮是**"值都对,但运行时没有资源把它跑完"**——表现为压测时一切正常(并发低),放号瞬间才出现"Lua 延迟 p99 飙升""落库延迟破 SLO""连接池等待超时"，而每一条业务断言仍然是绿的。

**钉死(§七已落 yml)**:

| 资源 | 配置 | 判据(为什么是这个数) |
|---|---|---|
| Tomcat 线程 | `max: 200` / `accept-count: 200` | 抢号是短请求(2 次 Redis round-trip),200 足够;队列有界 → 超出即拒,符合 05 §三·补「队列超阈值快速失败」,无界排队会把超时全堆在用户侧 |
| Hikari `ds0`/`ds1` | 各 20 | 抢号热路径**不打 DB**(Q1-B),分库写只来自 persistence-consumer 阶段1 与查询;20 已宽裕 |
| Hikari `single` | 30 | 阶段2 事务(state_log + route + event + occupied)、11 类对账、注册两写都在单库,是最忙的一个池 |
| 三池之和 70 | < MySQL `max_connections` 151 | 留余量给 `mysql` CLI / 对账巡检 / 演练脚本。**漏了这条会在压测中段出现"connection refused"而看起来像 DB 挂** |
| Lettuce 池 `max-active: 64` | 与 Tomcat 200 不必 1:1 | Redis 单线程本就是串行,池太大只是排队位置从应用挪到 Redis;但**太小会把"Redis 排队"伪装成"Lua 慢"**,让 §6.1 的「Lua 延迟 p99」指标指错方向 |
| `persistence` 消费线程 20 | **≤ `single` 池 30** | 它是唯一的写库消费者,线程数就是 DB 写并发上界。配成 64 只会让 64 个线程去抢 30 条连接 → Hikari 等待超时 → 消息重投 → 死信虚高 |
| `consume-message-batch-max-size: 1` | 强制 | D6 五阶段是**单条**语义:批量消费下一条失败会把整批重投,已跑完阶段1~2 的条目被重复执行(靠幂等键兜住但白做功,且掩盖真实失败率) |
| `executor.scheduler.pool-size: 8` | 默认是 **1** | Spring `@Scheduled` 默认单线程:11 类对账 + scanner + 卡单巡检共用一根线程,**任一任务卡住(如慢 SQL)全部定时任务停摆** —— 而 pending-scanner 停摆 = 卡单不被发现、occupy 不续期 → 桶余量泄漏(02 §3.2)。这是本表最容易漏且后果最重的一项 |
| `executor.mail` 独立有界 | core 2 / max 4 / queue 200 | SMTP 是唯一的界外调用(§6.2 唯一该熔的下游),必须与业务池隔离;`caller-runs` 让队列满时自然反压而不丢提醒 |
| `executor.reconcile` 独立 | core 2 / `abort` | 对账慢且不紧急,拒绝无害(下周期还跑,任务本身幂等);**不用 `caller-runs`**——那会卡住调度线程,等于把上一条的"单线程停摆"问题重新引进来 |

**优雅停机(D6 专属风险)**:

```
SIGTERM(docker stop / 滚动重启)
  ├─ server.shutdown: graceful         → Tomcat 停止接新请求,在途请求最多等 30s
  ├─ spring.lifecycle.timeout-per-shutdown-phase: 30s
  ├─ RocketMQ consumer shutdown        → 不再拉新消息;**在途消息跑完当前 consume 方法**
  └─ stop_grace_period: 45s(compose)  → 必须 > 30s,否则 Docker 在 10s(默认)后 SIGKILL
```

- **为什么这条对本项目格外要紧**:D6 的五阶段**跨库**(阶段1 在分库、阶段2 在单库),两阶段之间**没有事务保护**。SIGKILL 落在这里 = reservation 已插入但 route/occupied 未写。**这不是数据错**(阶段1 主键冲突继续跑阶段2 的设计,红线 #10,正是为此而存在),但它把一次**可避免**的重投变成了常态 —— 优雅停机的价值是让"设计好的兜底"回到"极少触发"。
- **不需要**为停机做额外补偿代码:所有 consumer 都是"重投安全"的(幂等键 + CAS)。**唯一要做的是别让 SIGKILL 提前 35 秒到**——即 compose 的 `stop_grace_period` 必须大于 Spring 的停机窗口。默认值(10s)比停机窗口小,是一条纯配置疏漏。
- **Redisson 锁**:持锁节点收到 SIGTERM 后 watchdog 停止续期,锁在 TTL 后自然释放,另一节点接手 → 靠 CAS/marker 保正确(06 §4.1 第 3 层),无需在停机钩子里手动解锁(手动解锁反而会在"任务还没跑完就释放"时制造双跑)。

**JVM(4C8G 容器,09 §八 的压测背书环境)**:

- `-XX:MaxRAMPercentage=70`(§四已改):**不要写死 `-Xmx`**。容器里 JVM 若按宿主内存推断堆,4C8G 限制下会算出远超 limit 的堆 → 被 OOMKilled 而非抛 `OutOfMemoryError`,现象是"容器无声重启",查不到栈。
- `-XX:+ExitOnOutOfMemoryError`:OOM 后立刻退出让 compose 重启,比"半死不活地继续处理消息"安全(半死状态下消费者可能反复失败把消息刷进死信)。
- GC 用默认 G1 即可,不调参 —— 本项目对象生命周期短、堆压力小(热路径不加载大结果集),调参属过度优化。**面试若问 GC 调优,诚实答"没调,因为热路径不打 DB 也不做大对象聚合,G1 默认足够;调参前应先有 GC 日志证据"** 比编一套参数更稳。

## 十、编码红线清单(动工前打印贴屏幕)

> 本轮修补钉死的**必错点**。每条都对应一个"漏了就出数据错、且不会立刻报错"的场景。

| # | 红线 | 漏了会怎样 | 出处 |
|---|---|---|---|
| 1 | 单库表 `@Transactional` 必写 `transactionManager="singleTxManager"` | 挂到默认库,单库事务实际未生效 | 03 §1.1 |
| 2 | 桶初值/增容按**余数规则**逐桶传值,不能各桶同值 | Σ桶 < capacity,库存对账永久带固定差 | 03 §4.2 |
| 3 | 选桶用 `hash(rno)`,**不用** `hash(user_id)`;借桶**环形**扫 | 热点用户永久打同桶;低号桶被借空 | 03 §4.3 |
| 4 | `dup` / `slot:full` / 桶 key TTL 一律活到 `slot_date` 当日结束 | 次日 slot 的 dup 在场次当天消失 → route 冲突成常态 | 04 §1.1 |
| 5 | 任何"桶余量从 0 变正"的路径都要 `DEL slot:full`(10.2a / 10.3 / 增容) | 回补的名额被约满标记永久挡住 | 04 §1.2 |
| 6 | `slot:full` 由 **10.1 Lua 内**写,不在应用层写 | 与增容竞态,永久掩盖新增名额 | 04 §1.2 |
| 7 | 窗口期取消**只标记 `occupy.cancelled`,绝不删 occupy** | 消费者读不到标记 → 按 RESERVED 落库 → 取消无效 | 02 §4.1 |
| 8 | occupy 的删除只允许两处:消费者落库成功、10.2a | 破坏 stuck 回滚参数与末尾复查 | 02 §4.1 / 06 §3.4 |
| 9 | 消费者阶段0(读 occupy 定 target_status)必须在阶段1**之前** | 阶段1 已写完无法回改 | 02 §五 |
| 10 | 阶段1 主键冲突**继续跑阶段2**,不 ACK 跳过 | reservation 有但 route/occupied 缺,长期漂移 | 02 §5.1 |
| 11 | persistence/rollback/timeout/release **成功后**写 `consumed_event`;reminder **发邮件前**写 | 先写会永久丢预约;后写会重复轰炸用户 | 02 §5.1 / 06 §2.1 |
| 12 | 所有 `event_id` **确定性派生**(`'rc-'+rno` 等),禁用 UUID | 补投/重投的幂等表形同虚设 | 02 §3.1 |
| 13 | 10.3 放号 Lua 只在 `released 0→1` CAS 成功后执行 | SET 覆盖把已抢余量重置回满 = 超卖 | 06 §3.5 |
| 14 | 取消 CAS 返回 0 行时**先 SELECT 确认记录不存在**才走 Redis 标记 | 幽灵有效预约(用户看到取消成功,DB 仍 RESERVED) | 02 §4.2 |
| 15 | 消费者阶段3 顺序:写幂等表 → 复查 cancelled → ZREM → DEL occupy | 换序即漏掉窗口期取消 | 02 §五 |
| 16 | route 冲突走 **ACK + 补偿**,不抛异常 | 白重试 N 次进死信,放大无效流量 | 06 §二·补 |
