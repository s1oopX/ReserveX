# 10 · 简历与面试

> 量化指标靠压测真数据(09)撑,不写虚数;引用必带环境。面试口径与 docs 全链一致,被追问不露怯。

## 一、简历写法

### 1.1 项目描述

> ReserveX · 分布式湿地公园参观预约系统
> 面向生态承载量限流的高并发抢约场景(示例配置:每日 4 时段 × 承载量 50,压测 2000 并发),覆盖中间件 / 数据库 / 分布式 / 并发四项核心技术。Spring Boot + ShardingSphere + Sa-Token + Redisson + RocketMQ,前后端分离(React + Caddy),三角色权限(游客/核销员/运营)。

### 1.2 技术亮点(挑 5–6 条,对齐 docs 定稿)

- 设计分批放号削峰(放号时间点运营可配),RocketMQ 5.x 定时消息(任意时间)+ Redisson 分布式锁选主 + 幂等 + 对账补放,多实例零重复放
- **Redis Lua 原子扣减,「判重→选桶→借桶→扣减→写预占满载荷→登记待落库索引」单脚本原子**,分桶+借桶(桶数为运营配置项,=1 即不分桶),抢号只动 Redis、DB 异步落库,wrk 压测(单机 4C8G 容器)峰值 QPS X 万、零超卖
- 参考 TCC 思想自研两阶段状态机(预占/核验/过期取消),`state_log` 三防(空回滚/悬挂/幂等)+ 不可变事件流水,Redis 预占↔MySQL 实到跨存储最终一致;消费者跨库分阶段落库 + 幂等表 + 补偿回滚 + 定时对账收口
- ShardingSphere 按 Snowflake user_id 分库分表 + 全局路由表/单库去重表解决分库下唯一约束失效(注册与一人一证预约两处同构解法),支持水平扩展
- 防缓存穿透 `slot:meta` + 空值缓存;防击穿 Redisson 单飞重建(双重检查)+ 主动维护;分层限流(本地 Guava + Redis RRateLimiter)+ 滑动窗口风控 + 风险触发验证码
- 动态二维码(HMAC-SHA256 签名 + 60s 时效 + nonce,载荷只含 rno)+ 核销 CAS 条件更新(**真正挡重复核销的是 CAS,签名与 nonce 唯一键是入口与存储两道**),扫码与手工核销统一状态机、差异只在入口凭证强度
- **分布式定时任务可靠性**:业务分级(核心强一致 vs 非核心)+ 三层防御(分布式锁减概率 / done-marker 挡整批复跑 / CAS+唯一键保正确)+ 界外调用幂等(提醒邮件先登记后发送);对账任务带自身幂等键 `uk(task_type,period,slot_id)` 挡重跑翻倍
- **故障覆盖与诚实边界**:消费重试分级(业务异常 ACK+补偿/基础设施重投+死信)+ 故障覆盖矩阵(哪些挡得住/哪些认了)+ 演进路径(Sentinel/Cluster/主从);不吹"最终一致零降级",明确认 Redis 丢失场景降一档并给演进口子
- **高并发稳定性治理**:容量规划(单机安全水位QPS×节点×0.7,非压到挂的值)+ 压测覆盖非正常态(缓存失效/Redis故障/限流触发/积压)+ 核心链路降级分级(核销保可用/抢号拒绝是降级非故障/查询兜底)+ 舱壁隔离(旁路任务独立有界线程池,主链路靠限流维度隔离);雪崩靠结构性规避(只动Redis+主动维护+TTL抖动)而非加熔断
- **运行期容量与资源边界**:Redis `noeviction`(库存真理源不可被逐出)+ `appendfsync always`(成功写在返回前 fsync)+ 三连接池与消费并发度按"写并发上界 ≤ 连接池"定 + 优雅停机对齐跨库两阶段边界;**每个中间件默认值都反问过"对本项目是否成立"**(Redis 无内存上限 / `@Scheduled` 默认单线程 / Docker 停机窗口 10s 三处默认值都是错的)
- **可观测与故障自愈**:三件套(Metrics+Tracing+Logging)5分钟定位热key/慢SQL + 熔断防误判七条(最小样本量/半开/错误类型区分) + 核心监控5域(死信突增=核心信号)+ 容量水位看板(故障前可见)
- ☑ **一键可复现的工程交付**:`docker compose up` 起全栈(三库建表脚本 + 种子数据 + topic 显式建队列 + 前端产物入卷 + 十二个环境变量),**四把密钥物理分离**(数据加密 / 身份证 pepper / QR 签名 / JWT)且启动时断言两两不等;身份证 AES-256-GCM 存 `iv‖ct‖tag` + 按行记密钥版本使轮换真正可行;登录走"路由表 PK → 分片键"两跳,避免分库表按非分片键**全分片广播**

## 二、面试追问预案

| 追问 | 回答方向(对齐 docs) |
|---|---|
| 抢号为什么只动 Redis | 抢号那一刻只和 Redis 交互(内存快),DB 异步走 MQ;Redis `occupy:{rno}` 预占记录是可恢复 outbox,承担窗口期凭证 + 前端渲染,DB 落库后无缝切 |
| Redis 扣了 DB 没记怎么办 | 普通消息发送失败→pending-scanner 扫 `pending:persist` ZSet 补投;消费业务失败(route 冲突)→10.2a 原子撤销 Redis(桶+1/删occupy/删dup/ZREM pending),原消息已 ACK 不再重投;基础设施异常→重投+DLQ+人工(不自主回滚,防幽灵预约);对账收口。route冲突下 DEL dup 违 M7 瑕疵在 dup 已丢前提下不显现(04 §三·补·2) |
| 为什么不用事务消息 | 事务消息解决 DB↔MQ 一致,管不到 Redis↔MQ;本项目原子边界在 Redis↔MQ,事务消息买不到该段可靠性,却逼出"同步落主表"牺牲"只动 Redis"招牌,性价比差 |
| Redis 挂了怎么办 | 降级表(00 §D7):抢号拒绝/查询放行/核销保可用+本地限流/管理低频;Redis 崩+AOF 且回 DB occupied 近似重建——降一档但单机 AOF 小概率+代价不对称 |
| 压测怎么做 | token 池 2000 独立用户随机取样;固定单 token 会被配额规则全挡,测拒绝速度非抢号链路;带环境背书 |
| 取消和爽约走 Cancel 有区别吗 | **无**:都不返还(M1)、都不减 occupied(累计语义)、都纯 DB CAS;dup 都不删(配额消耗不改约)。对账统一口径无需跳过已结束 slot |
| 才 200 个号为什么分桶 | bucket_count 是 slot 配置项,平日配 1(=不分桶),旺季配 10;已放号禁改桶数(hash 路由错位) |
| **选桶用什么做 hash** | `hash(reservation_no) % bucket_count`,**不用 user_id**——user_id 分布长期固定,热点用户会永久打同一桶;rno 每次新生成故天然均匀。桶满借桶按 `(bucket_no+i)%n` **环形**扫,不固定从 0 扫(否则低号桶被反复借空、分布倾斜) |
| **capacity 不能整除桶数怎么办** | 余数分摊:`base=C/n, rem=C%n`,前 rem 个桶各多 1。简单 `C/n` 会丢余数 → Σ桶 < capacity → 库存不变量 `C=A+R+V+X` 永久带固定差,库存对账差值恒不为 0。增容同理逐桶传值(delta=5 到 10 桶时整除为 0,DB 已 +5 而 Redis 一个没加) |
| 单体为什么搞 TCC | 诚实:无跨服务调用,TCC 用于 Redis 预占↔MySQL 实到跨存储一致,参考其思想;MQ+对账管数据同步,状态机管可回滚推进,两者并存 |
| 空回滚/悬挂怎么处理 | state_log:Cancel 先到记 status=3,Try 后到查 status=3 拒绝。**写入点四处**:Try=消费者阶段2(不在抢号热路径)、Confirm=核销 CAS 后、Cancel=取消/timeout/route冲突清孤儿、空回滚占位=窗口期取消。⚠️ 别只说"有张 state_log 表"——被追问"什么时候写"答不出就是纯叙事 |
| **配额可配吗** | v1 **结构上锁死 1 次/天**:`id_card_route` PK `(id_card_hash, slot_date)` 与 Lua `SET NX dup` 两道防线都只能表达"一天至多一条";配成 2 时两道**同时失效**。真要支持 N 次/天需同时改 PK 语义 + dup 从 SET NX 改 INCR 比对上限,是 v2 演进。yml 保留该项但启动时 `!=1` fail-fast。**别答"改个配置就行"** |
| 分库后唯一索引失效 | 全局路由表(注册)+ 单库 id_card_route + Lua SET NX(预约判重),两处同构。**区别在方向**:注册**先占位后写主体**(唯一性优先,防并发同邮箱都写成 user 留孤儿 user);预约**先写主体后占位**(D6,主体在分库且已有 Redis dup 做第一道)。孤儿 route 可自愈(再点一次注册复用同 user_id),孤儿 user 不可自愈 |
| **单库表为什么不用广播表** | 广播表把同一行写进 ds0/ds1 两份,无 XA 时两库写入本身非原子,且唯一约束退化为"每库各自唯一"——而全局唯一性是这三张路由表存在的**全部理由**。故配**独立 `single` 数据源**不纳入分片规则,单库事务显式 `@Transactional("singleTxManager")` |
| 为什么状态码不叫 Try/Confirm | DB 落的是业务终态语义(RESERVED/VERIFIED/CANCELLED/EXPIRED),TCC 是流转思想非字段命名;简历仍写"参考 TCC 思想" |
| 限流为什么分层 | 本地 Guava 扛接口/STAFF(零开销削峰),Redis RRateLimiter 管须全局的用户/场次;单机 Redis 下限流与 Lua 争时间片,分层减 round-trip |
| 穿透怎么防 | slot:meta 缓存 + 空值缓存 NULL;抢号前应用层校验已放号/未过期,挡未放号/已过期/不存在三种非法 slot_id(修复过期能抢号 bug) |
| 击穿怎么防 | slot:meta 低频元数据靠主动维护(放号/增容刷新),单飞重建仅兜底;桶余量不套单飞(原子写对象) |
| 雪崩怎么防 | 结构性规避而非加熔断:① 抢号只动 Redis 不打 DB(热路径无 DB 可打穿)② slot:meta 主动维护+逻辑过期(高峰不过期)③ TTL 加抖动;另补容量规划——限流按"保护最稀缺下游资源"定(单机安全水位QPS×节点×0.7),压测覆盖缓存失效/Redis故障/限流触发/积压四种非正常态 |
| 热key怎么拆 | 本项目热 key 是 slot 桶——已用分桶天然拆(桶数=运营配置);识别用 LFU+redis-cli --hotkeys(非 LRU,LRU看最近性不看频次);L1 本地缓存用 Caffeine(W-TinyLFU 淘汰)才是 LRU/LFU 的正解位置 |
| 限流怎么定 | 按保护最稀缺下游定:基线靠压测找单机安全水位(p99 RT不破SLO/CPU<70%/零错误)、集群=单机×节点×0.7、按瓶颈资源限(本项目瓶颈Redis单线程);双层本地+Redis、算法令牌桶(限流)+滑窗(风控) |
| Redis挂了核心链路断吗 | 核销(核心)保可用走DB CAS不断;抢号(核心)Redis挂时拒绝——拒绝是降级非故障(有下批可重试,宁不超卖);查询/提醒/统计非核心可降。B方案本身即"先预占后异步落库"=复盘的先接单后处理,常态就这么做 |
| 熔断怎么防误判 | 最小样本量(窗口<20~50不评估)+半开探测(1~5个)+错误类型区分(业务错误不计入,只算5xx/超时)+慢调用比例+超时按p99非p50+渐进恢复+舱壁隔离;本项目该熔的是调SMTP(邮件超时高),核心链路(抢号Lua/DB CAS)是本地操作不该熔 |
| 系统可观测怎么做 | 三件套:Metrics(Actuator+Micrometer→Prometheus v2)+Tracing(MDC+traceId贯穿,v2接SkyWalking)+Logging(结构化日志串事件链);核心监控指标分5域(抢号/MQ/一致性/核销/Redis),死信突增是核心告警信号;容量水位看板让"接近水位"故障前可见 |
| QR 会被截图转发吗 | 载荷 `v1.{kid}.{rno}.{exp}.{nonce}.{sig}`(07 §3.4.1):HMAC-SHA256 签名防篡改 rno、`exp` 60s 时效、载荷只含 rno 不含身份证。**截图外泄最多暴露一个 rno 且 60s 后失效** |
| **nonce 到底防什么** | ⚠️ 诚实:**真正挡住重复核销的是 CAS `status 0→1`**(同一 rno 只有一条记录可改),`uk(qr_nonce)` 是第二道,让"同一张截图二次核销成功"在存储层不可能。服务端**不预存 nonce**(取码高频,写 Redis 会占抢号的时间片),所以没有"比对 nonce"这一步。别答"靠 nonce 唯一键防重复核销",会被追问"不入库你拿什么比对" |
| **手工核销和扫码是两套规则吗** | 不是。**状态机与 CAS 只有一套**,差异只在"入口凭证强度":扫码凭签名,手工凭 STAFF 身份 + 二次确认 + `audit_log(MANUAL_VERIFY)`。手工的 `verification_log.qr_nonce` 存 **NULL**(故该列不能 `NOT NULL`),失败/重放尝试的 nonce 记 `attempt_nonce` —— 否则重放的第二次会撞 uk **连日志都记不下来**,监控里"无效码次数"就没数据源(08 §十 #26) |
| 窗口期查不到预约怎么办 | 查「我的预约」从 Redis occupy 渲染(D1 满载荷),DB 落库后字段一致无缝切,用户无感 |
| 集群部署定时任务怎么保证只执行一次 | exactly-once 执行在有 crash 的分布式里不存在;靠业务幂等坍缩成"效果只一次":锁减概率、done-marker 挡整批复跑、CAS+唯一键保正确(地基);界外调用先登记幂等表再发邮件。单/多节点是成本选择非正确性选择 |
| 对账任务重跑会不会重复写 | reconcile_log 带 `uk(task_type,period,slot_id)` 挡重跑翻倍;修复动作带状态守卫(NX 标记/CAS);业务异常不重试(重试有 bug 的逻辑=复制坏数据) |
| 有本地事务了为什么还要幂等表 | 事务管单次原子(这一次要么全成要么全败),幂等表管跨次去重(同消息重投时挡);crash 在事务之间或消息重投,事务救不了,得靠幂等键。原子性≠幂等,两件事 |
| 消息重试耗尽去哪 | 基础设施异常重投 N 次仍失败进死信队列(DLQ),DLQ 监听告警+独立 group 幂等+人工重投;业务异常(route冲突)只 ACK+先 CAS 清孤儿 reservation+触发 10.2a 补偿,不重投(06 §二·补)。**为什么不基础设施失败也回滚**:自主放弃持久化会与 pending-scanner 补投竞态致幽灵预约(桶已回补但预约仍落库),retry 与 compensate 必须意图互斥(04 §三·补) |
| 系统有哪些不完美/降级点 | 主动甩 06 §6.1 故障覆盖矩阵:Redis 崩+AOF 丢降一档(近似重建)、DB 主库挂(演示无主从);其余故障(MQ 重复/丢失/乱序/消费者重启/对账双触发)全兜得住。再甩 §6.2 演进路径证明想清了取舍,非没想过 |
| MQ 能保证 exactly-once 吗 | 不能。调度层/MQ 永远只给 at-least-once(无法区分写盘前后 crash);exactly-once 是业务层把 at-least-once 坍缩成"效果一次"——靠 consumed_event/id_card_route 唯一键 + CAS。所以全篇不吹"MQ 保证 once",而是一层层堆幂等键 |
| **幂等表是先写还是后写** | **分两类,判据是"这个动作重复一次,有没有唯一键/CAS 把它变成 no-op"**。有 → 成功后写(persistence/rollback/timeout/release),幂等表只是加速跳过;没有(界外调用如 SMTP)→ 动作前写,幂等表是唯一防线。⚠️ 一律"先写"在跨库场景会**永久丢预约**:consumed_event 在单库、reservation 在分库,先写成功后阶段1 崩 → 重投被幂等表挡 → 该预约永不落库。这是我 review 时找到的一个 P0 |
| **窗口期用户点取消怎么办** | 取消 CAS 命中 0 行时**不能直接判定是窗口期**——先 SELECT 确认记录真不存在,才走 Redis 路径;窗口期只 `HSET occupy.cancelled=1` **绝不删 occupy**(删了标记就不存在,消费者会按 RESERVED 落库 → 用户看到取消成功但预约仍生效),同时写 `state_log` 空回滚占位做双通道(Redis 丢 key 时的第二道)。消费者阶段0 读标记定 target_status,阶段3 在 DEL occupy 前**再复查一次**(挡"标记晚于检查点"的窄窗)。三道收口:末尾复查 + 不轻信 0 行 + 到期对账 |
| **补偿代码怎么保证跑过** | 诚实:dup TTL 修好后 route 冲突在正常运行中**不可能触发**,而它是 10.2a 的唯一触发源 → 补偿是**冷路径**。正确性上这是好事(第一道防线够硬),但工程上必须靠故障注入:手工 `DEL dup` 后同证再抢 / 测试 profile 去掉 dup 分支 / 预插 route,断言五项 Redis 副作用(桶+1、occupy 删、dup 删、ZREM pending、**slot:full 删**)+ DB 状态 + 不变量。**且必须在"slot 已约满"前置态下跑一遍**,否则漏掉 `DEL slot:full` 测试照样绿,线上却表现为"回补的名额被永久挡住" |
| **valid_until 为什么固化成字段而不运行时算** | 抢号前置校验、Lua 写 occupy、到期对账三处都要它;任一处派生口径不一致就会出现"A 处认为已结束、B 处认为可约"。固化 = 单一真理源。未放号可随 slot_hour/duration_min 改而重算,已放号锁定 |
| **放号脚本重复执行会怎样** | 10.3 是 `SET` 覆盖写,在已放号 slot 上重跑会把**已被抢掉的余量重置回满 = 超卖**。所以必须 `released 0→1` CAS 成功**之后**才执行,CAS 受影响 0 行 → 直接返回绝不执行。这是"锁只减概率、CAS 才保正确"在放号链路的具体落点——真正拦住重复放号的不是 Redisson 锁,是这个 CAS |
| **业务失败如何映射 HTTP** | 严格按资源语义使用状态码:校验失败 400、未认证 401、无权限 403、资源不存在 404、状态/配额冲突 409、缺少或失效前置条件 428/412、限流 429、依赖降级 503；JSON `code` 保留更细业务原因，创建资源用 201+Location |
| **压测数字怎么保证不是拒绝速度** | 两层:① token 池 2000 独立用户(固定单 token 会被配额全挡)② **wrk 同时按 HTTP 与 JSON `code` 分类**——创建成功是 201+OK，售罄/配额冲突是 409，降级是 503；不解析 body 则"成功预约数 = capacity"和"超卖 0"两条验收底线无法断言 |
| **为什么 ID 要序列化成字符串** | Snowflake 是 19 位 Long(~1e18),JS `Number.MAX_SAFE_INTEGER` 只到 `2^53-1`(~9e15)→ `JSON.parse` **静默改写末位**。轻则取码返 `RESERVATION_NOT_FOUND`(用户看到"预约成功"却取不到码),**重则改写后恰好命中另一条真实 rno**(同毫秒序列号连续)→ 读到他人预约,而归属校验挡不住(攻击方没伪造任何东西,是精度丢失自己改成了邻居的)。落地:统一在 `common/` 的 ObjectMapper 配 `Long→String` **一次**,不逐 DTO 标注——漏一个就是一条静默错路径(07 §3·补·4) |
| **为什么不用 UTC 存时间** | 本项目的业务语义就是"**本地日历日**":`dup:{slot_date}:{hash}`、`id_card_route` PK `(hash, slot_date)`、"一人一天一次"都以本地自然日为单位。UTC 存会把一个本地日切到两个 `slot_date` 上,**配额键直接失真**。所以选"全链路单一时区 `Asia/Shanghai`",三处一起钉:容器 `TZ` + JDBC `serverTimezone` + Jackson `time-zone`。漏一处的后果不对称:MySQL 在 UTC 而 JVM 在 +08:00 → **到期扫描提前 8h 把当天有效预约全刷 EXPIRED**;反向 → dup/桶 key 多活 8h,次日场次用着昨天的桶,而 10.3 的 `SET` 被 `released 0→1` 的 CAS 挡住、不会自愈(08 §7.2) |
| **列表页的"剩余名额"怎么算** | 从 `slot:meta.bucket_count` 逐个拼出 `slot:{id}:b:0..n-1` 后一次 `MGET`,**禁用 `KEYS`/`SCAN` 通配**:`KEYS` 是 O(N) 且**阻塞 Redis 单线程**,而它与抢号 Lua 争的是同一根线程——列表页高频调用等于自己给抢号造毛刺。另一半更隐蔽:**`bucket_count` 是唯一真理源**,不能"有几个 key 算几个桶",否则某桶被 TTL 清掉会被误读成"这个 slot 只有 n-1 个桶",库存对账 diff 直接错。展示层负值夹 0、**对账层不夹**(对账看到负数就该告警)(05 §1.4.1) |
| **Redis 的 `maxmemory-policy` 配什么** | **`noeviction`,禁一切 `allkeys-*`**。理由要说到点上:本项目 Redis 里存的不是缓存,是**库存真理源**——桶余量、`occupy`(窗口期唯一凭证)、`dup`(配额第一道)、`pending:persist`(待落库索引)。配 `allkeys-lru` 时内存到顶 Redis 会**静默逐出**:桶被逐出=库存凭空消失;`occupy` 被逐出=scanner 按 `EXISTS occupy` 判定"已过期/已回滚"直接 `ZREM` 清掉,**预约永久消失**;而全程 HTTP 200、无异常、无日志。`noeviction` 的语义是"到顶后写命令返 OOM 而不是删数据",于是内存打满变成一个**有报错、可降级、可告警**的事件——抢号返 `SERVICE_DEGRADED`(不是 `SLOT_FULL`,同 #32 的理由)、读照常。**这是"缓存"与"数据"用同一个中间件时最容易踩的一脚**(08 §7.3) |
| **AOF 为什么选 always** | 桶余量、occupy、dup、pending 都是库存真理源，不是可丢缓存；`appendfsync always` 让成功写在返回前完成 fsync。代价是吞吐下降，因此只承诺实测安全水位；若改成 `everysec`，必须明确接受崩溃时最多丢最近 1 秒写并做恢复演练 |
| **"舱壁隔离"具体隔离了什么** | 诚实分两半:**主链路(抢号/核销)不套异步池**——它们是同步短请求(2 次 Redis round-trip),套 `@Async` 只多一次线程切换和排队、反而抬 p99;主链路的隔离由**限流维度**(`rl:slot` vs `rl:staff`)+ **Redis key 命名空间**承担。真正配独立池的是**旁路任务**:邮件(界外调用,SMTP 超时高,`caller-runs` 自然反压)、对账(慢但不紧急,`abort` 拒了下周期还跑)、`@Scheduled`。**代价要主动认**:抢号洪峰仍会挤占核销的 Tomcat 线程,物理隔离得拆 worker(v2,D8 留了边界)(08 §7.4) |
| **`@Scheduled` 的坑** | **默认池大小是 1**。本项目有 11 类对账 + pending-scanner + 卡单巡检共用它:任一任务卡在慢 SQL 上,**全部定时任务停摆** → scanner 不再续期 `occupy` → 30min 后 occupy 过期而预约未落库 → **桶余量永久泄漏**(02 §3.2)。修法只有一行 `pool-size: 8`,但它是我这轮找到的**后果最重的一条**:一个框架默认值,能把设计好的兜底机制整条关掉(08 §7.4 / 红线 #41) |
| **消费线程数怎么定** | `persistence` 消费线程 20,判据是**必须 ≤ `single` Hikari 池(30)**——它是唯一的写库消费者,线程数就是 DB 写并发的上界。配成 64 的后果最误导:64 个线程抢 30 条连接 → Hikari 等待超时 → 消息重投 → **死信虚高,看起来像 MQ 故障,实际是配置错**。另外 `consume-message-batch-max-size` 必须是 **1**:D6 五阶段是单条语义,批量下一条失败会整批重投,已跑完的条目被重复执行(靠幂等键兜住但白做功,且掩盖真实失败率)(08 §7.4 / 红线 #42) |
| **滚动重启会不会写坏数据** | 不会,但要说清为什么。D6 阶段1(分库)与阶段2(单库)之间**没有事务保护**,SIGKILL 落在这里 = reservation 已插入而 route/occupied 未写 —— 而"阶段1 主键冲突继续跑阶段2"(红线 #10)这条设计本就是为此存在的,重投即收口。所以优雅停机的价值**不是防数据错,是别把设计好的兜底当常态用**(那会掩盖真实失败率)。具体一条纯配置疏漏:Docker `stop_grace_period` 默认 **10s** < Spring 停机窗口 30s → 每次重启都强杀在途消息,必须显式配 45s(08 §7.4) |
| **次日场次是怎么生成的** | 定时任务读 `slot_template`(单库,`enabled=1` 的每行一条),按 `slot_date 00:00 + release_offset_min` 算 `release_at`、按 `slot_hour + duration_min` 算 `valid_until`,**复制**模板字段值写进 `slot`(`template_id` 只作溯源,不是外键、不做 join)。⚠️ 这是我第十三轮补的一处 P0:**模板在四个地方被当现成的读**(次日生成任务 / 管理端"场次配置" / 03 的 capacity 与 bucket_count 来源 / 07 的发布闭环),**而全 docs 没有这张表** —— 更要紧的是 `release_at` 是 `NOT NULL` 且**字面上算不出来**(没有任何字段告诉你"提前多久放"),等于一个没有填充路径的非空约束。为什么不能写在 yml 里:改承载量要重启、不同时段配不同容量表达不了、"停用某时段但保留历史场次"表达不了。另一条:某个 template 撞 `uk(slot_date,slot_hour)` 说明该场次已生成,**跳过这个 template 继续下一个**,不能整批 return(否则重跑时第一条冲突就让后面的场次永远不生成,且无告警)(03 §4.0 / 红线 #48) |
| **模板改了,已生成的场次会变吗** | 不会,**刻意的**:生成时是**复制值**而非引用。理由是已放号的 slot 改 `bucket_count` 会导致 hash 路由错位(红线里既有的一条)、改 capacity 要走"增容"这条带 Redis 逐桶分摊的专门路径。所以模板编辑只影响**未来**的场次;要改今天的场次走带 `ETag`/`If-Match` 的 `PATCH /api/admin/slots/{slotId}`。模板也**不允许删除**,只能 `enabled=0`——删了会让历史 slot 的 `template_id` 变悬空引用 |
| **身份证密文具体怎么存** | AES-256-GCM,库里存 **`iv(12B) ‖ ct ‖ tag(16B)` 拼接后的整块** `VARBINARY(256)`(18 位身份证 → 46 字节),**IV 每次加密随机生成**、不复用、不存在别的列里。加上一列 `id_card_key_id` 记这一行用的密钥版本(= `reservex.aes.key-id`),yml 侧配 key-set(`aes-v1`/`aes-v2` 共存),这样"支持密钥轮换"才是真的——否则轮换后**旧行永久解不开**。落地上把 `encrypt(plain) -> byte[]` / `decrypt(bytes, keyId) -> String` 封在 `crypto/` 里,**不把 IV 暴露成入参**:GCM 下同一密钥重用 IV 会直接泄露明文异或关系,而"参数能传就有人传常量"(03 §2.1 / 红线 #45) |
| **`id_card_hash` 为什么用固定 pepper 而不是每行 salt** | 因为这个 hash 的用途不是"验证口令",是**跨用户可比**:M6 一证一天一约靠 `id_card_route` 的 PK `(id_card_hash, slot_date)` 保证,两个不同用户拿同一张身份证必须算出**同一个 hash**。每行随机 salt 会让两次算出不同值,唯一约束**结构上失效**。代价必须主动认:① pepper 泄露 = 身份证 hash 可被彩虹表反推(身份证空间小),只能靠"与 AES 密钥同级保护:仅环境变量、不入 git、不进日志"缓解;② **pepper 不可轮换**——它进了 PK,换一次等于全表 hash 作废 + PK 重建。这是一处"业务不变量赢过密码学最佳实践"的取舍,别答"加个 salt 更安全"(03 §2.1 / 00 §6.4) |
| **登录怎么查用户?分库了 email 不是分片键** | 两跳:① 单库 `SELECT user_id FROM email_route WHERE email=?`(PK 命中)② 分库 `SELECT * FROM user WHERE user_id=?`(分片键命中)。**禁止在分片表上按 `email` 查** —— ShardingSphere 会把它变成**全分片广播 + 内存归并**,登录是最高频接口,2 库时看不出问题、扩到 8 库时 QPS 直接除以 8。第一跳查到而第二跳查不到 = 孤儿 route,返 `LOGIN_FAILED` 并**告警**,不在登录路径上自愈(自愈是注册路径的事)。附带一条对外/对内不对称:`LOGIN_FAILED` 对外必须合并"邮箱不存在/密码错/孤儿 route"三种原因防用户枚举,但**服务端日志必须分三个分支**——否则孤儿 route 这种真故障永远查不出来(03 §2.2 / 红线 #44) |
| **超管账号是怎么来的** | 部署时产生,**没有任何 HTTP 接口能造 ADMIN**。四个坑都要能说:① `user_id=1` → `1 mod 2 = 1` → seed **必须插进 `reservex_ds1`**,插错库的现象极具误导性:route 表查得到 user_id 但分库查不到,长得像"孤儿 route" bug;② **不能把 BCrypt 密文写进 git 的 seed 里**(仓库公开=人人可登超管),做法是 seed 写哨兵值 `'!'`,应用启动时用 `ADMIN_INIT_PASSWORD` 现算 BCrypt 回填并写 `audit_log(ADMIN_BOOTSTRAP)`,首登返 `PASSWORD_CHANGE_REQUIRED` 强制改密;③ 超管的 `id_card_*` 是 `NOT NULL`,用保留占位 hash 且**不插 `id_card_route`**(否则占掉一个真实身份证的配额位);④ `docker-entrypoint-initdb.d` **只初始化空卷**,已有卷的 seed/schema 变更必须追加不可变迁移(08 §4.1) |
| **有几把密钥,分别能不能换** | 四把,**必须两两不等**,启动时 `@PostConstruct` 断言(相等或过短直接 fail-fast):`AES_KEY`(身份证加密,**可轮换**,靠 `id_card_key_id` 按行记版本)、`ID_HASH_PEPPER`(身份证 hash,**不可轮换**,进了 PK)、`QR_HMAC_KEY`(动态码签名,**可随意换**,60s 后旧码自然失效)、`JWT_SECRET`(会话签名,换一次=**全员掉线**)。为什么要断言而不只是写进文档:**红线清单里有、代码里没断言的条目,迟早会被违反**——尤其"复用一把 key 更省事"在本地调试时毫无副作用。第十三轮我顺手做了一遍全清单排查:48 条红线里哪些能变成启动断言或集成测试(08 §4.2 / 红线 #47) |
| **会话存哪里,登出是否立即生效** | Sa-Token 1.45 `StpLogicJwtForSimple`:access 是 30min JWT，但同时保留 Redis token mapping/session；refresh 是 7d opaque 白名单并绑定 access 摘要做单次轮换。因此登出会撤销当前 access/refresh，改密和 STAFF 封禁会递增 refresh 版本并注销该用户全部 access。代价是鉴权依赖 Redis，不再宣称“无状态 JWT”。JWT 不放邮箱/身份证，派生身份字段只进服务端 token session(08 §4.6)。 |
| **为什么 Redis 不给不同业务分 db** | `database` 恒为 **0**,理由三条,且都不是洁癖问题:① **Lua 脚本不能跨 db** —— D4-A 的限流与抢号扣减在不同 db 就得拆成两次 round-trip,把"2 次 Redis 交互"的设计前提破掉;② 每个 db 要各自的连接工厂,连接数翻倍而池是按实例配的;③ 真正想要的隔离(内存、`SLOWLOG`、`--bigkeys`、单线程 CPU)**全是实例级的**,`maxmemory-policy` 也是实例级——分 db 一点没隔离,只是让 `redis-cli` 多打一次 `SELECT`。隔离靠 **key 前缀命名空间**,要物理隔离就上第二个 Redis 实例(v2)(08 §4.6) |
| **RocketMQ 的 topic 谁建的** | 一次性 `rmq-init` 容器跑 `mqadmin updateTopic`(幂等,`depends_on: service_completed_successfully`)，显式建 3 个业务 Topic + 3 个 DLQ：`reservation-created` 8 队列，另外两个业务 Topic 4 队列，DLQ 各 1 队列。`autoCreateTopicEnable=false`，漏配即启动失败。RocketMQ 5.5 用 `authenticationEnabled/authorizationEnabled`；旧 `aclEnable` 已实测不生效并移除(08 §4.4)。 |
| **前端产物是怎么到 Caddy 的** | 一次性 `frontend-build` 服务:多阶段 Dockerfile 里 `npm run build` 后把 `dist/` 拷进 `frontend-dist` 命名卷,Caddy `depends_on` 它 `service_completed_successfully`。⚠️ 这是第十三轮找到的一条"文档齐全但起不来":compose 里 Caddy **挂了这个卷,却没有任何服务往里写东西** → 托管一个空目录 → 访问首页 **404,而所有后端接口正常**。这种缺陷的特征是**功能测试里根本跑不到**,因为测试环境的前端是开发者手工 `npm run dev` 起的。同理 `restart:` 也要区分:6 个常驻服务 `unless-stopped`(不是 `always`——手工 `docker stop` 后不该被拽起来),2 个一次性服务必须 `"no"`(否则 seed/topic 脚本无限重跑刷日志)(08 §4.5 / §4.3) |
| **Redis 内存打满时登录会怎样** | 必须返 `SERVICE_DEGRADED`,**不能返 `LOGIN_FAILED`**。两个理由:① `LOGIN_FAILED` 是"你的凭证不对",把系统故障说成用户错误,用户会反复重试加剧压力;② 监控上**登录失败率会被刷成尖峰**,长得像撞库攻击,值班第一反应是封 IP 而不是看 Redis 内存 —— 一个错误码能把排查方向带偏半小时。这条和 #32(`SLOT_FULL` vs `SERVICE_DEGRADED`)是同一条判据的第二次应用:**凡"系统原因"与"用户原因"共用一个错误码,监控上必然被污染**(07 §3·补·2) |

## 三、诚门口径(必守,被追问不翻车)

1. **场景**:湿地限流有生态承载政策依据,非人为限量;"为什么抢而非排队"答生态承载是硬上限,现场排队消化不了。
2. **TCC**:参考思想自研,非 Seata;解决 Redis↔MySQL 跨存储一致,非跨服务。
3. **分库分表**:驱动力高可用+水平扩展演示,非数据量;单实例多 schema 演示形态。
4. **Redis 单机(M3)**:演示形态,水平扩容可迁 Cluster/Sentinel,**不吹高可用**。
5. **限流分层(D4-A)**:demo 单实例下本地全维度(D4-C)更优,选 A 是简历展示 RRateLimiter——对此诚实。
6. **可靠性降一档场景**:Redis 崩+AOF 丢,小概率+代价不对称接受——被问"有什么不完美"主动说。更强做法:甩出 06 §6.1 故障覆盖矩阵(哪些挡得住/哪些认了)+ §6.2 演进路径(Sentinel/Cluster/主从),证明不是"没想过"而是"想清了取舍"。
7. **数字带环境**:QPS 必带 `单机 4C8G 容器 / Redis 同机`,无环境背书的数字是虚数。
8. **黑名单**:v2 规划,本期未实现,不遮不掩;防黄牛由防刷+验证码承担。
9. ☑ **配额不可配**:v1 结构性锁死 1 次/天,别答"改配置就行"(会被追问出 route PK + SET NX 那条链子)。
10. ☑ **提醒邮件可能永久漏发**:先写幂等表后发邮件的必然代价。取舍是"宁可漏发一封,不可重复轰炸";提醒是非核心,漏发=体验降级。要两者都保需引入邮件发送状态机(登记 pending→发送→标记 sent),v1 刻意不做——**这是唯一一处"动作前写幂等表"的 consumer,与其余五个刚好相反,不对称是刻意的**。
11. ☑ **补偿链路是冷路径**:route 冲突正常不触发,10.2a 只在病理态执行,靠故障注入保证代码跑过。别吹"补偿天天在跑"。
12. ☑ **单库表不是广播表**:早先方案曾写广播表,已作废(唯一性会退化成每库各自唯一)。被问"ShardingSphere 怎么配"要答"三数据源 + 分片规则只覆盖 user/reservation"。
13. ☑ **单一本地时区,不是 UTC 存储**:全链路 `Asia/Shanghai`。被问"为什么不 UTC"别答"没考虑"——答**业务语义是本地日历日**(配额键 `dup:{slot_date}` 与 `id_card_route` PK 都以本地自然日为单位,UTC 存会把一个本地日裂成两个 `slot_date`)。同时承认代价:**跨时区扩展需要重构日期语义**,单区业务不预付这个成本。
14. ☑ **v1 舱壁只隔离旁路,不隔离主链路**:抢号与核销共用 Tomcat 线程池,独立池只给邮件/对账/定时任务(08 §7.4)。别答"每条链路都有独立线程池"——主链路是同步短请求,套异步池只会抬 p99。代价要主动认:**抢号洪峰会挤占核销的 Tomcat 线程**,真要物理隔离得拆 worker(v2,D8 已留边界)。
15. ☑ **Redis 内存到顶 = 抢号不可用,这是主动选的方向**:`noeviction` 换来"库存永不被静默逐出",代价是打满时抢号完全不可用而非部分可用(08 §7.3)。被问"为什么不配 LRU 让它自己腾地方"要能答出"我这里存的是数据不是缓存,逐出等于删库存"。
16. ☑ **`id_card_hash` 的 pepper 不可轮换**:它进了 `id_card_route` 的 PK,换一次 = 全表 hash 作废 + PK 重建。被问"哈希为什么不加 per-row salt"**别答"疏忽了"**——答**这个字段必须跨用户可比**(M6 一证一天一约的唯一约束就建在它上面),加随机 salt 会让约束结构性失效。同时主动认代价:pepper 泄露则身份证 hash 可反推,且换不了(03 §2.1)。**这是全项目唯一"照密码学教材做反而错"的地方,主动讲比被问出来强。**
17. ☑ **JWT 不等于无状态**:本项目的 Simple JWT 仍有 Redis token mapping/session，登出、改密和 STAFF 封禁可即时撤销。代价是 Redis 故障会影响鉴权；别再回答“30 分钟内撤不掉”(08 §4.6)。
18. ☑ **initdb 不是 schema 版本管理**:`docker-entrypoint-initdb.d` 只在数据目录为空时跑一次;已有卷由一次性 `mysql-migrate` 按文件名执行不可变迁移并核对 SHA-256 checksum。阶段 0 的空库初始化只在可丢弃的独立 Compose project 上验,业务卷禁止删除(08 §4.1)。

## 三·补 review 自己文档找到的问题(高阶加分项)

> 面试官问"你这个项目做了多久 / 遇到最大的坑是什么",这一段比任何亮点都值钱——它证明的是**自审能力**,而非记忆力。挑 2–3 条讲,每条都是"决策定了但承载它的字段/参数/写入点没落地"的同一病根。

| 找到的问题 | 为什么危险(不修会怎样) | 怎么发现的 |
|---|---|---|
| `dup` key TTL 写成"次日 0 点 − now" | **次日 slot 的 dup 会在场次当天开始时消失** → 一人可反复抢 → route 冲突从病理态变成并发常态,而整个"补偿只在病理态触发"的论证随之崩塌 | 顺着"TTL 到底覆盖到哪一刻"逐 key 推演 |
| 幂等表"先写"与"成功后写"两处口径并存 | 跨库场景下先写会**永久丢预约**(单库幂等表已写、分库主体未写、重投被挡) | 追问"这两个库不是一个事务,中间崩了会怎样" |
| 窗口期取消写成"删 occupy + 标记" | occupy 删了标记就不存在 → 消费者按 RESERVED 落库 → **用户已收到"取消成功",预约却仍生效且配额已耗** | 读到"标记"三个字就去查"标记存在哪、谁会读、那时它还在吗" |
| `state_log` 有表定义但**全链路没有写入点** | TCC 三防是纯叙事;B 向对账的检测条件"Try 未 Confirm"永远查不到数据,那条对账任务实际是空跑 | 反向查:每张表都问一句"谁在什么时候写它" |
| `slot` 表**没有 `valid_until` 字段**,但三处都读它 | 编码即卡死;若各处自行派生则口径不一致("A 处认为已结束、B 处认为可约") | 做 DDL ↔ Redis key ↔ Lua 参数 ↔ 流程的四向对齐 |
| 10.2a 补偿漏 `DEL slot:full` | 回补的名额被"约满"标记**永久挡住**,而且测试很容易绿(只在 slot 已满后触发补偿才暴露) | 问"这个 key 是谁写的、谁负责删" |
| ☑ `verification_log.qr_nonce` 是 `NOT NULL UNIQUE`,但**手工核销没有 nonce** | 手工核销直接插不进(编码即卡死);且重放的第二次尝试会撞 uk → **连失败日志都记不下来**,监控里"无效码次数"永远是 0 | 反查 DDL 每个 `NOT NULL`:"这条路径拿什么填它" |
| ☑ QR 的 `hmac-key` 与 AES 数据密钥复用同一个 `AES_KEY` | 一处泄露两处失守,且身份证密钥与签名密钥的轮换周期本该不同 | 逐个环境变量问"这把 key 被几处用" |
| ☑ 全 docs 只有 **2 个 URL**,没有统一响应包/错误码/接口清单 | 每条业务分支的语义都写透了(Lua 返 -1/0/1、窗口期"正在确认"、CAS 0 行),但**前端不知道判哪个字段**;真动工时每个 controller 各发明一套,后期统一 = 重写全部前端判断分支 | 站到前端视角问一句"我拿到这个响应,怎么知道是售罄还是配额用完" |
| ☑ `SLOT_FULL`(真售罄)与 D7 降级拒绝没有区分手段 | 两者前端都是"约不到"但语义相反;混成一个 → 降级请求污染「库存不足率」指标,**D7 降级在监控上完全不可见**(而 D7 是简历里的降级分级亮点) | 反查监控指标:「这个指标的数据源会被哪些请求污染」 |
| ☑ Snowflake ID 直接以 JSON 数字返给前端 | 超 JS `2^53` 安全整数 → rno 末位被**静默改写**:轻则"预约成功但取不到码",重则改写后**恰好命中另一条真实 rno**(同毫秒序列号连续)→ 读到他人预约,而归属校验挡不住(不需要伪造,精度丢失自己就改成了邻居的) | 问一句"这个 19 位的 Long 到了浏览器还是它自己吗" |
| ☑ 全 docs **没有一处规定时区**,而 `mysql:8.0` 容器默认 UTC | 全项目核心判据都是时间比较。MySQL 在 UTC 而 JVM 在 +08:00 → **到期扫描提前 8h 把当天有效的预约全刷成 EXPIRED**;反向 → dup/桶 key 多活 8h,次日场次用着昨天的桶 | 把「`valid_until < now`」这个判据里的 `now` 追到底:**谁的 now** |
| ☑ 「Σ桶余量」被四处当现成数用,却从未定义怎么读 | 最自然的写法 `KEYS slot:{id}:b:*` 是最坏的:O(N) 且**阻塞 Redis 单线程**,而它与抢号 Lua 争的是同一根线程——列表页高频调用等于自己给抢号造毛刺;且"有几个 key 算几个桶"会把 TTL 清掉的桶误读成桶数变少,库存对账 diff 直接错 | 反查:被多处引用的"派生量",它的**计算方法**有没有唯一定义 |
| ☑ Redis 没规定 `maxmemory-policy`,而桶余量/`occupy`/`dup` 是**库存真理源不是缓存** | 若按常见教程配 `allkeys-lru`:内存到顶时 Redis **静默逐出** → 桶被逐出=库存凭空消失;`occupy` 被逐出=scanner 按 `EXISTS occupy` 判成"已回滚"直接 `ZREM`,**预约永久消失**。全程 200、无异常、无日志,且 diff 漂移方向与真超卖一致最难辨 | 问一句"我往 Redis 里放的这些东西,**是缓存还是数据**?丢了能重建吗" |
| ☑ 「舱壁隔离」「连接池占用率告警」承诺了但 yml 里**一个池都没定义** | ① 舱壁是纯叙事(与 `state_log` 曾经"有表无写入点"同构);② 占用率**没有分母,指标算不出来**;③ `@Scheduled` 默认池 **1** → 一个慢对账把 scanner 一起停掉 → occupy 不续期 → **桶余量永久泄漏** | 反查每一句"用线程池隔离(见 08)":**去 08 看那个池到底在哪个配置项里** |
| ☑ 优雅停机无口径,`stop_grace_period` 默认 10s < Spring 停机窗口 30s | 每次滚动重启都 SIGKILL 在途消息,把"阶段1 冲突继续跑阶段2"这条**设计好的兜底当常态用**,掩盖真实失败率;JVM 不设 `MaxRAMPercentage` 则容器里按宿主内存算堆 → OOMKilled 而非抛 OOM,现象是"容器无声重启查不到栈" | 问每个中间件/框架的默认值:"**这个默认值对本项目是对的吗**" |
| ☑ 次日 slot 生成任务被四处引用,但**没有任何表存"生成什么"** | `slot_template` 不存在 → 生成任务读不到 `slot_hour/capacity/bucket_count/release_offset_min`,**`release_at` 这个 NOT NULL 列没有任何填充路径**;写死在 yml 则改承载量要重启、且无法表达"某时段停用但保留历史" | 反查每个定时任务:"**它的输入从哪张表读**" |
| ☑ `init.sql` 在 compose 里挂了,但**内容从未定义**;超管账号只被"假设存在" | 换台机器 `up` 起来是空库,而 `role='ADMIN'` 按设计**不能由任何 HTTP 接口产生** → 谁都进不了管理端。更隐蔽:超管 `user_id=1` → `1 mod 2 = 1` → seed 若按直觉写进 `ds0`,登录第 2 跳查 `ds1` 查不到,现象是"**孤儿 route**",会去查一个根本不存在的注册竞态 | 问一句"**这个系统在一台干净机器上,从 `git clone` 到能登录管理端,少哪一步**" |
| ☑ AES 只写了"AES-256-GCM",**IV 存哪、`key-id` 存哪都没定义** | GCM 没有 IV 无法解密 → 最自然的错法是"IV 写成常量"(GCM 下同密钥重用 IV **可恢复明文**);而 `accepted-key-ids` 承诺了轮换,但行上不记密钥版本 → 换 key 后**旧行全部解不开**,轮换承诺是空的 | 反查每个"支持轮换"的承诺:"**旧数据靠什么知道自己是哪把钥匙加的**" |
| ☑ `id_card_hash` 写"SHA256",没说加不加盐、加什么盐 | 按最佳实践写"每行随机 salt"就**直接违反 M6**:hash 必须跨用户可比才能做 `id_card_route` 的 PK,per-row salt 让"一证一天一约"彻底失效。定成全局 pepper 后又必须认一条代价:**pepper 进了 PK,所以不可轮换** | 问"这个 hash 的**用途**是防泄露还是做等值比较" |
| ☑ 登录只写了"邮箱+密码",没写**在分库里怎么找到这个用户** | 分片键是 `user_id`,`WHERE email=?` 会**全分片广播 + 内存归并**;库多一倍慢一倍,而且它是全站最高频的写前读 | 反查每条 SQL:"**WHERE 里有分片键吗**;没有的话 ShardingSphere 会怎么办" |
| ☑ Caddy 挂载 `frontend-dist` 卷,**却没有任何服务往里写东西** | 访问 `http://localhost` 返回 **404,而后端接口全正常** —— 最容易被误诊成 Caddy 配置错,真因是卷本身是空的。需要一个一次性 `frontend-build` 服务把 `dist/` 拷进去,并让 caddy `depends_on: service_completed_successfully` | 反查每个 volume:"**谁写它、谁读它**",只有读没有写的就是空的 |

> 收束口径:「这几条的病根是同一个——**前几轮 review 都在决策层(选哪个方案、为何选),没做过一次实现层的四向对齐**。所以我后来固化了两张表:一张 DDL/Redis/Lua/流程 四栏字段自检表(每个字段四栏都必须有落点,任一栏空即缺口),一张 48 条编码红线清单(专收"漏了会出数据错但不会立刻报错"的点)。**机制比修补重要**,因为同类缺口还会再长出来——事实上它确实又长了五次:第九轮长在凭证面(QR 载荷没定义),第十轮长在 HTTP 面(错误码没定义),第十一轮长在**承载面**(ID 序列化/时区/求和读法没定义),第十二轮长在**运行面**(内存策略/线程池/停机没定义),第十三轮长在**初始化面**(模板表/init.sql/密钥口径/登录读路径没定义)。**同一个病根换六张脸,说明检查维度本身要成套**:数据面、凭证面、接口面、承载面、运行面、初始化面各查一遍。
>
> ☑ 而且最后三轮最值得讲,因为常规测试**结构上抓不到它们**。第十一轮那三条:HTTP 200、日志无异常、业务分支全对,只是值在跨边界时被改错了(Long 过 JSON 边界被 JS 削精度、DATETIME 过容器/驱动边界偏 8h、Σ桶余量用 `KEYS` 读且把 key 数当桶数)——只能靠"**拿真值逐位比对**"。第十二轮那三条更进一步:**连低并发压测都是绿的**,只在放号峰值/长跑/滚动重启时显形,而且现象全指向错误方向(像 MQ 故障、像 DB 挂、像 Lua 慢)。第十三轮那四条最极端:**在功能测试里根本跑不到**——因为测试环境是我自己几天前手工搭好的,缺口全在"**搭**"这一步(模板表、seed、密钥、前端产物)。所以我把缺陷按"会不会让测试变红"分成四档,每档配不同抓法(00 §6.3·补):会变红 → 功能测试;永远绿 → 逐位比对;低并发也绿 → 峰值+长跑+主动杀进程;根本跑不到 → **在可丢弃的独立 Compose project 上做空库初始化**。第四档必须排在验收最前面,因为它是其余三档的前置条件——**起不来就什么都测不了**。
>
> ☑ 顺带我还发现自己写的一条测试断言是**假绿**的:dup TTL 只断言"覆盖到次日 23:59:59"用 `>=`,而 UTC 环境下算出的秒数更大、照样通过——**一个只会假绿不会假红的断言,比没有断言更危险**,因为它被当成"已验证"。」

| ☑ "运营可配场次与承载量" | 03 §四 `slot_template` + §9.1 变更约束 + 07 §四 管理端页面 | ✅(原先四处引用"模板"但无表,`release_at` 无填充路径) |
| ☑ "`docker compose up` 一键起全栈" | 08 §4.1–§4.5(建表/seed/topic/前端产物/restart 策略)+ 09 §6.9 | ✅(**在可丢弃的独立空库环境验过才算**——原先 Caddy 挂的卷没人写,首页 404;业务卷不得删除) |
| ☑ 三角色权限(游客/核销员/运营) | 08 §4.1(超管由部署 seed 产生,无接口可造 ADMIN)+ 07 §3·补·3 | ✅(否则"第一个管理员从哪来"答不上,或存在提权接口) |

> 自检原则:简历每条亮点都能在 docs 找到落地章节 + 面试预案对应回答。说不通的改简历,别改 docs 掩盖。
>
> ☑ **新增一条自检**:亮点里提到的**每张表都要有写入点**、**每个字段都要有读写流程**(03 §十)。`state_log` 就是反例——表存在、简历写了、面试能背,但代码里没人写它,一追"什么时候写"就露。
>
> ☑ **再加一条(第十三轮)**:简历上每一句"自动/一键/可配/支持轮换",都要能在干净机器上**演示一遍**。`docker compose up` 起不来的项目,亮点全是文档;而"支持密钥轮换"若换完 key 旧数据解不开,那句话本身就是缺陷而不是亮点。判据:**凡是能被"你现在起给我看看"问倒的表述,都得先补承载再写进简历。**

## 五、面试话术分层(从被动到主动)

> 简历亮点能背不算会,被追问能拆解才算会,主动暴露降级点才算"想清了"。三层递进。

### 5.1 被动层(被问到能答)

第一层只要预案表(§二)全覆盖即可。核心是**每个亮点配一个"为什么这么选"的取舍论证**,而非只说"我用了 X":
- 不只说"用了 Lua",要说"为什么不用 SETNX+DECR 两步"(防 CHECK-then-DECR 超卖)
- 不只说"分桶",要说"才 200 号为什么分桶"(桶数是运营配置项,平日配1)
- 不只说"补偿+对账",要说"为什么不用事务消息"(原子边界不对位)

### 5.2 主动层(主动暴露不完美)

面试官最看重的是"是否知道自己系统的边界"。主动甩三张牌比被动问出来强:

| 牌 | 主动说 | 落地 |
|---|---|---|
| **降级点** | "这套方案不是零降级,Redis 崩+AOF 丢会降一档——但我有故障覆盖矩阵和演进路径" | 06 §6.1/§6.2 |
| **代价不对称** | "选只动Redis而非事务消息,是性价比判断——事务消息买不到Redis↔MQ可靠性却牺牲招牌" | 02 §七 |
| **诚实边界** | "demo单实例下D4-C纯本地更优,选D4-A是简历展示RRateLimiter" | 05 §4.2 |
| ☑ **自审能力** | "我在动工前做了一轮实现层对齐,自己找出 6 个 P0——比如幂等表'先写'在跨库下会永久丢预约" | §三·补 |

> ☑ 更强的版本:「而且这个病根**又长出来五次**——第九轮发现 QR 只有口号没有载荷格式,第十轮发现全 docs 只有 2 个 URL、没有错误码,第十一轮发现 ID 序列化/时区/Σ桶读法一处都没定义,第十二轮发现"舱壁隔离""连接池告警"承诺了但 yml 里一个池都没有,第十三轮发现"按模板生成次日场次"被引用四次却没有那张表、`init.sql` 挂了但内容从没写过。同一个'决策定了但承载它的契约没定义'换六张脸(数据面/凭证面/接口面/承载面/运行面/初始化面),这才让我明白**检查维度要成套,而不是逐个打补丁**。而且最后三张脸最难发现——**第四张的缺陷不会让功能测试变红,第五张连低并发压测都是绿的,第六张在功能测试里根本跑不到**(测试环境是我自己手工搭的,缺口在"搭"这一步),只能靠拿真值逐位比对 + 峰值长跑主动杀进程 + 独立空库环境验收。」

被问"有什么不完美"时,**不要答"目前没发现"**——那是最大红旗。答上述四张牌。**第四张最强**:前三张证明"想清了取舍",第四张证明"能自己发现问题",后者是更稀缺的能力。

### 5.3 升维层(把单点问题拉到方法论)

被追问深时,把具体问题拉到通用方法论,展示"不是这个项目凑巧做对,是懂原理":

| 单点追问 | 升维到 |
|---|---|
| "为什么不用事务消息" | exactly-once 在分布式里不可能(FLP),所有"框架保证 once"都是伪命题,正确性只能业务层幂等坍缩 |
| "对账任务重跑怎么办" | 锁减概率→marker挡复跑→CAS+唯一键保正确,三层职责不可混;重心要在第三层 |
| "MQ 重复消费怎么办" | 投递语义三态:调度层只给 at-least-once,exactly-once 是业务层把 at-least-once 坍缩成效果一次 |
| "有事务为何还要幂等表" | 原子性管单次(这一次要么全成全败),幂等管跨次(重投去重),两件事 |
| "Redis挂了核心断吗" | 降级分级:核心不可断走DB CAS/拒绝是降级非故障,非核心可降;先接单后处理是B方案常态 |
| ☑ "补偿代码怎么测" | **冷路径的可测性是通病**:所有"只在异常时执行"的代码(补偿/回滚/兜底分支)在正常运行中零覆盖,必须靠故障注入而非等它自然发生。判据:一段代码若只由病理态触发,它的正确性只能由主动注入证明 |
| ☑ "字段/表怎么保证不漏" | 决策层评审(选哪个方案)与实现层评审(承载它的字段在不在)是两件事,前者做十轮也发现不了后者。机制:四向对齐表(DDL/缓存/脚本/流程)+ 每张表反查"谁在什么时候写它" |
| ☑ "契约类缺口怎么系统性发现" | **换视角比加轮次有效**:同一份 docs 我按"数据面(字段在不在)→ 凭证面(载荷长什么样)→ 接口面(前端判哪个字段)→ **承载面(值传过去还是原来那个)** → **运行面(有资源把它跑完吗)** → **初始化面(从零起一次起得来吗)**"各查一遍,每换一个视角都能挖出上一轮完全看不见的 P0。判据是**站到消费方立场提问**——DDL 的消费方是代码,QR 的消费方是核销端,响应包的消费方是前端,承载层的消费方是**跨边界的另一侧运行时**(JS 引擎 / MySQL 容器 / Redis 单线程),运行面的消费方是**操作系统与中间件的默认值**(它们已经替你做了决定),初始化面的消费方是**拿到仓库的下一个人**(他没有你机器上那些手工搭的状态) |
| ☑ "静默错怎么测" | **按"会不会让测试变红"给缺陷分四档**(00 §6.3·补):① 业务分支类会红(状态不对、字段为空);② **承载层永远绿**(HTTP 200、日志无异常、值悄悄被改)→ 只能靠"**拿真值逐位比对**"(body 里的 ID 与 DB 逐字符比、容器 `date`/`SELECT NOW()`/`LocalDateTime.now()` 三者互差 0、`SLOWLOG` 里不许出现 `KEYS`);③ **运行期类连低并发压测都绿**(池够用、内存没到顶、没重启过)→ 只能靠"**峰值 + 长跑 + 主动杀进程**";④ **初始化类在功能测试里根本跑不到**(缺口在"搭"环境这一步,而环境是手工搭好的)→ 只能靠"**独立的可丢弃空库环境验收**",且这一档必须**排在验收最前面**,因为起不来就什么都测不了。推论一:**断言必须精确到值**,`>=`/"够长"这类宽松断言会假绿——一个只会假绿不会假红的断言比没有断言更危险。推论二:**凡是"红线清单里有但代码里没断言"的条目,迟早会被违反**,所以我把 48 条红线过了一遍,标出哪些能做成启动断言(如四把密钥两两不等、`maxmemory-policy=noeviction`)、哪些能做成集成测试、哪些只能靠人眼 |
| ☑ "怎么保证别人能把你的项目跑起来" | 判据一句话:**假设接手者只有一台干净机器和这份文档**。于是"初始化"要像业务代码一样被设计——建表脚本拆 `01-schema.sql`(三库 + 分片表建两份)与 `02-seed.sql`(只放超管和场次模板,不放测试数据);topic 显式建并指定队列数(**队列数是消费并发的硬上限**,靠自动创建会让 20 个消费线程只有 4 个干活,现象像"MQ 慢");前端产物由一次性服务写进卷(不然 Caddy 托管空目录 → 首页 404 而接口全正常);一次性服务 `restart: "no"`、常驻服务 `unless-stopped`。`docker-entrypoint-initdb.d` 只初始化空卷,已有卷由 `mysql-migrate` 按 checksum 增量迁移;空库复现使用独立可丢弃 project,业务卷禁止删除 |
| ☑ "配置也是设计吗" | 是,而且有一条锋利的例子:06 §6.1 故障覆盖矩阵里「Redis 内存打满」这一行,在 `maxmemory-policy=noeviction` 下是 **✅ 可控降级**,在 `allkeys-lru` 下立刻变成 **❌ 静默数据丢失** —— **一个配置项决定这一行是挡得住还是兜不住**。推广判据:**每个中间件的默认值都要问"这个默认值对本项目是对的吗"**。三个反例:Redis 默认 `maxmemory` 无上限(→ OOMKilled 而非降级)、Spring `@Scheduled` 默认池 1(→ 一个慢任务停掉全部定时任务、桶余量泄漏)、Docker `stop_grace_period` 默认 10s(→ 小于停机窗口,每次重启都 SIGKILL)。**默认值不是中立的,它是别人替你做的决定** |

### 5.4 红线(绝不能说的话)

- ❌ "Redis 不会挂" / "MQ 保证不重复" —— 框架保证论,踩 FLP 红线
- ❌ "目前没发现什么问题" —— 自承没想过边界
- ❌ "用了 X 就高可用/最终一致了" —— 堆组件不解决根因(复盘批评的)
- ❌ "单节点就够了不用集群" —— 治标下策,正确姿态是多节点+幂等
- ❌ QPS 不带环境 —— 虚数
- ☑ ❌ "JWT 一定无状态、登出后还能用 30 分钟" —— 当前 Simple JWT 有 Redis mapping，登出会即时撤销(08 §4.6)
- ☑ ❌ "哈希当然是每行加随机 salt" —— 本项目 `id_card_hash` 必须跨用户可比(唯一约束建在它上面),per-row salt 会让 M6 结构性失效;正确答案是全局 pepper 且**认下不可轮换**(03 §2.1)

> 这五条红线对应桌面两案例批评的候选人通病:把补救当根因、把框架保证当正确性、堆组件不纠根因。守住红线=不犯案例里的错。
