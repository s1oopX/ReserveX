# 06 · MQ 与最终一致

> Q1-B 定调:RocketMQ 普通消息(非事务消息)+ 补偿 + 对账 + 定时兜底。本项目的最终一致由「可重试+可补偿+可对账」给到,而非跨存储原子事务。

## 一、消息事件目录

| 事件 | Topic | 触发 | Payload 关键字段 | 幂等键 | 消费者 | 顺序键 |
|---|---|---|---|---|---|---|
| `ReservationCreated` | `reservation-created` | 抢号 Lua 成功后 | rno/user_id/slot_id/slot_date/bucket_no/id_card_hash/create_ts | `event_id='rc-'+rno` | persistence-consumer | — (无序) |
| `CompensateRollback` | `compensate-rollback` | **仅** route 冲突(消费者业务失败 ACK 后驱动) | rno/dup_key/bucket_key/**slot_full_key**/reason | `'cr-'+rno`(10.2a 自幂等) | rollback-consumer | — |
| `ReservationVerified` | *(可选异步)* | 核销 CAS 后 | rno/staff_id/event_time | `'rv-'+rno` | (写 event/统计,V2) | — |
| `ReminderTrigger` | `reminder` | 抢号成功投递,延时到 valid-30min | rno | `'rm-'+rno` | reminder-consumer | — |
| `TimeoutExpire` | `timeout` | 抢号成功投递,延时到 valid_until | rno/slot_id | `'te-'+rno` | timeout-consumer | — |
| `SlotRelease` | `slot-release` | 时段模板生成时投递,延时到 release_at | slot_id | `'sr-'+slot_id` | release-consumer | — |

> ☑ `CompensateRollback` payload 补 `slot_full_key` —— 10.2a 现在要 `DEL slot:full`(04 §三 P1 修),该 key 须随消息带过去(或由 rollback-consumer 从 `bucket_key` 前缀推导 `slot:{slotId}` 后拼出,二者选一,推荐显式带)。
>
> ⚠️ 幂等键全部**确定性派生**,不用 UUID:补投/重发时 event_id 不变,`consumed_event` 才真正生效(02 §3.1)。

> RocketMQ 5.x 定时消息(`setDeliverTimeMs` 任意时间)用于 release_at 精确放号、30min 提醒、过期取消三类延时,不受 4.x 18 级限制。broker 版本锁 5.3.1。

## 二、幂等消费(必须,RocketMQ 不保证不重复)

每个消息含:`event_id / event_type / aggregateId(rno) / occurredAt / schemaVersion / traceId / payload`。

**`event_id` 由聚合 ID 确定性派生**(02 §3.1 钉死):`'rc-'+rno` / `'cr-'+rno` / `'rm-'+rno` / `'te-'+rno` / `'sr-'+slot_id`。**不用随机 UUID** —— 否则 scanner 补投/重发时 event_id 变化,`consumed_event` 唯一键形同虚设。

```sql
INSERT INTO consumed_event(consumer_group, event_id, consumed_at) VALUES (?, ?, NOW());
-- 唯一键冲突 → 已处理
```

### 2.1 写幂等表的**时机分两类**(☑ P0 修:原"一律先写"会永久丢预约)

⚠️ **原缺陷**:本节原文写「消费者**先**写幂等表,唯一键冲突 → 已处理,直接 ACK 返回成功」,与 §3.1 的「成功 → 记 consumed_event」矛盾。而"一律先写"在跨库场景下**会丢数据**:`consumed_event` 在单库、`reservation` 在分库,先写幂等表成功后阶段1 崩 → 重投时被幂等表挡掉 → **该预约永不落库**(详细推演见 02 §5.1)。

**分类钉死**:

| 时机 | 适用 consumer | 幂等的真正来源 | 判据 |
|---|---|---|---|
| **成功后写** | persistence / rollback / timeout / release | 业务侧唯一键或 CAS(`reservation` PK、`id_card_route` PK、`state_log` PK、`status` CAS、`released` CAS) | 下游动作**本身幂等** → 幂等表只是"加速跳过",不是正确性来源。先写反而吞掉未完成的工作 |
| **动作前写** | reminder(发邮件) | **`consumed_event` 就是唯一防线** | 界外调用(SMTP)无 DB 唯一键可依 → 必须先登记才能挡重发(§3.3、§4.6) |

> **可推广的判据**:**问一句"这个动作重复执行一次,有没有唯一键/CAS 会把它变成 no-op?"** 有 → 成功后写;没有(尤其跨系统调用)→ 动作前写。这就是 §4.6「界外调用是分水岭」的操作化版本。

业务唯一键(rno/slot_id)+ consumed_event 双重幂等。消息乱序由 DB CAS(`WHERE status=0`)兜,不依赖 MQ 顺序(RocketMQ 顺序只对同组有效,不同组不保全局序)。

## 二·补 消费重试分级与死信(最终一致的最后一公里)

§4.7「业务异常不重试」是原则,此处定义其落地机制——**重试与否由消费者的 ACK/抛异常行为决定,而非口号**:

| 异常类型 | 消费者行为 | 框架动作 | 为何 |
|---|---|---|---|
| **业务异常**(数据脏/route 冲突/逻辑 bug) | **ACK 吞掉**(不抛) + 写 consumed_event + 触发补偿(10.2a)/落对账 | 不重投 | 重试有 bug 的逻辑 = 复制坏数据,比漏跑更危险(桌面 §3.4) |
| **基础设施异常**(DB 超时/Redis 闪断/网络) | **抛异常** | 框架按策略重投 N 次 | 瞬时故障可恢复,重试有意义 |
| **未知异常** | 抛异常 | 重投 N 次 → 仍失败 → 进死信 | 兜底,不静默丢 |

> ⚠️ 关键:route 唯一冲突(DuplicateKey)**不是基础设施异常**——它是"该证已被另一并发请求约走",属业务事实,应 ACK + 补偿回滚(02 §五已如此),**不抛**。若抛则框架重投,重投仍冲突,白重试 N 次再进死信,放大无效流量。

### 死信处理路径

```
消息重投达上限(RocketMQ 默认 16 级,可调)→ 进入死信队列 DLQ(topic = %DLQ%consumerGroup)
  ├─ DLQ 监听器(dedicated consumer)收到 → 写 consumed_event(死信侧,独立 group)→ 告警
  ├─ ADMIN 消息任务页(07)展示死信列表:消息体摘要(敏感字段脱敏)/重试次数/最后错误/业务ID
  └─ 人工处置:
       ├─ 数据已落(误死信)→ 标记忽略
       ├─ 瞬时故障已恢复 → 一键重投(走原 topic,consumed_event 幂等挡重复)
       └─ 业务 bug → 修代码后重投 / 触发补偿回滚
```

- 死信侧 consumed_event 用独立 `consumer_group=dlq-*`,与正常消费幂等表隔离,避免污染。
- 死信**绝不自动重投**——必须人工研判后操作,写 audit_log。
- 监控:死信数量是核心告警指标(08 监控 / 09 验收),突增=链路异常信号。

> 这一段是"可恢复"的兜底:正常链路(重试+补偿+对账)处理 99.9%,死信+人工收口最后 0.1%。缺它,耗尽重试的消息会静默丢失,「不少约」被破坏。

## 三、四大消费者职责

### 3.1 persistence-consumer(落库,02 §五 D6 分阶段)

```
ReservationCreated(event_id='rc-'+rno)
 ├─ consumed_event 判重(**只读判重,不写** —— 写在最后,见 §2.1)
 ├─ 阶段0:HGETALL occupy:{rno} → 定 target_status(cancelled=1→2 / expired=1→3 / 否则 0)
 │     ☑ 必须前置于阶段1(原文档写"阶段2 读标记 → 阶段1 改写"时序不成立)
 ├─ 阶段1:INSERT reservation(分库,status=target_status)
 │     主键冲突(rno 已存在)→ **不 ACK 跳过,继续阶段2**(上次可能跑完阶段1 就 crash)
 │     基础设施失败(超时/连接)→ 抛异常 → 框架重投 N 次 → 耗尽 DLQ(人工),不触发 10.2a
 ├─ 阶段2:单库本地事务(@Transactional("singleTxManager")):
 │     INSERT state_log(xid='rx-'+rno, status=1)   ← Try(03 §6.1)
 │        PK 冲突 → 查 status,=3 → 窗口期已取消 → CAS reservation 0→2,本条转 CANCELLED
 │     INSERT id_card_route  DuplicateKey(业务事实,该证已被并发约走)
 │        → CAS 清阶段1 孤儿 reservation(status 0→2,语义未成立作废,M1 不影响 occupied)
 │        → 发 CompensateRollback(执行 10.2a)→ 写 consumed_event → ACK 本消息(原消息不再重投 → 与 10.2a 无竞态)
 │     INSERT reservation_event(CREATED)
 │     UPDATE slot_bucket occupied+1
 │     基础设施失败 → 抛异常 → 重投 + DLQ(不自主 10.2a,防幽灵预约,见 04 §三·补)
 └─ 阶段3(收尾,顺序不可换):
      1. INSERT consumed_event          ← 成功之后才写(§2.1)
      2. 复查 HGET occupy cancelled     ← 02 §4.2 竞态收口第 1 道
      3. ZREM pending:persist
      4. DEL occupy
      5. 投递 ReminderTrigger + TimeoutExpire
```

> ⚠️ **10.2a 触发边界**:仅 route 冲突(业务已判定不可成立)+ ACK 后驱动。基础设施异常走重投+DLQ,**不自主 10.2a**——自主放弃持久化会与 pending-scanner 补投/MQ 重投竞态致幽灵预约(桶已回补但预约仍落库),详见 04 §三·补。route 冲突前先 CAS 清阶段1 孤儿 reservation,防 B 向对账误重建 occupy 与 10.2a 冲突。

### 3.2 rollback-consumer(补偿,执行 10.2a)

```
CompensateRollback(event_id='cr-'+rno) → 执行 04 §10.2a Lua
  ├─ occupy:{rno} 存在 → INCR bucket / **DEL slot:full** / DEL occupy / DEL dup / ZREM pending → 返回 1
  └─ 不存在(已回滚)→ 幂等返回 0
  └─ 末尾:CAS state_log status→3(Cancel,03 §6.1)
```

10.2a 本身幂等(EXISTS 判定),所以 CompensateRollback 重投安全。⚠️ `DEL slot:full` 是 P1 修补项(04 §三):漏了它,回补的名额被约满标记永久挡住。

### 3.3 reminder-consumer(到点提醒)

```
ReminderTrigger(延时到 valid-30min,event_id='rm-'+rno)
 → 先 INSERT consumed_event(consumer_group, event_id)   ← 界外幂等地基,见下
     ├─ 唯一键冲突 → 已提醒过,ACK 跳过(幂等)
     └─ 成功 → 续
 → 查 reservation.status 或 occupy:{rno}(窗口期读 Redis)
     ├─ RESERVED → 发邮件(预占状态才提醒,已到场/不来不打扰)
     └─ VERIFIED/CANCELLED/EXPIRED → ACK 跳过(已登记幂等,后续重投也会被挡)
```

⚠️ **界外调用顺序(硬性)**:邮件是跨系统调用,超时/ACK 失败会触发消息重投,`consumed_event` 的 INSERT **必须在发邮件之前**——insert 成功(唯一键挡重投)→ 发邮件;即便发邮件后 ACK 失败消息重投,consumed_event 已在,不会重发。若反过来(先发邮件后记幂等),重投会重复发邮件,踩中桌面案例「界外调用无 DB 约束兜底」的坑。

> ⚠️ **这是全项目唯一"动作前写幂等表"的 consumer**(§2.1),与 persistence-consumer 的"成功后写"刚好相反。**代价必须认**:先写幂等表后发邮件失败 → 该提醒**永久不发**(重投被幂等表挡)。这是"宁可漏发一封提醒,不可重复轰炸用户"的取舍——提醒是**非核心任务**(§4.0 分级),漏发只是体验降级。若要两者都保,需引入"邮件发送状态机"(登记 pending → 发送 → 标记 sent,失败时按 pending 重试),v1 不做,是**刻意的不对称**。

### 3.4 timeout-consumer(超时取消)

```
TimeoutExpire(延时到 valid_until,event_id='te-'+rno) → CAS
  UPDATE reservation SET status=3 WHERE rno=? AND status=0 AND valid_until<NOW()
  受影响1 → EXPIRED + 写 event + CAS state_log→3
  受影响0 → 已被核销/取消,幂等跳过
```

⚠️ 窗口期预约(DB 未落)的处理:timeout-consumer 须先 `EXISTS occupy:{rno}`;DB 未落但 occupy 在 → **`HSET occupy:{rno} expired 1`**(消费者阶段0 读此标记,直接按 status=3 落库)。

> ☑ **P2 修正:删掉原文的"或直接 DEL occupy 清理"选项。** 原文把两个不等价的做法并列成"或":
> - `DEL occupy` 会让在途的 `ReservationCreated` 消费时读不到任何标记 → 按 **RESERVED** 落库 → 一条已过期却是 RESERVED 的记录,只能等到期状态对账(§4.3)二次收口才变 EXPIRED;
> - 且 `DEL occupy` 会连带破坏 02 §3.2 的 stuck 回滚参数、02 §4.2 的复查机制。
>
> **统一纪律:窗口期的所有"终态意图"都用 occupy 标记表达(`cancelled` / `expired`),occupy 的删除权只属于「消费者落库成功」与「10.2a 回滚」两处。** 这与 02 §4.1 同一条规则,不再有例外。

### 3.5 release-consumer(放号,见 07 §一)

延时至 release_at → 抢 Redisson 锁 `slot:release:{slotId}` → 选主 → 翻转 DB `released 0→1`(CAS version)→ **CAS 成功才**执行 10.3 Lua(逐桶初值按 03 §4.2 余数规则)→ `HSET slot:meta` 全 7 字段 + 长 TTL(抖动)→ 主动删 slot:full。

> ⚠️ **10.3 必须在 `released 0→1` CAS 成功之后**:10.3 是 `SET` 覆盖写,若在已放号的 slot 上重跑,会把**已被抢掉的余量重置回满**(超卖)。CAS 受影响 0 行 = 已放过号 → **直接返回,绝不执行 10.3**。这是 §4.1 三层模型里"第 3 层 CAS 保正确"在放号链路的落点——锁只是减概率,真正拦住重复放号的是这个 CAS。

## 四、对账与定时任务(分布式可靠性设计)

> 本节是 ReserveX 的「分布式定时任务可靠性」专章。设计基准:桌面《分布式定时任务-面试案例与分析》§3.6 六层模型。核心认知——**"exactly-once 执行"在有 crash 可能的分布式系统里根本不存在;触发一次≠执行一次。真正的 exactly-once 是业务效果上的,由幂等键(唯一约束+CAS)坍缩出来。锁减概率、marker 挡整批复跑、CAS/唯一键保正确——三层各司其职,缺一不可。**

#### 两个易混认知(面试防露怯)

**① 投递语义三态——exactly-once 只在业务层成立**

| 语义 | 含义 | 谁负责 | 本项目落点 |
|---|---|---|---|
| At-Most-Once | 最多一次,可能漏(不重试) | — | 不取(漏=少约) |
| At-Least-Once | 至少一次,可能重(失败就重试) | **调度层/MQ 默认这个** | RocketMQ 重投 + pending-scanner 补投 |
| Exactly-Once | 效果上一次 | **业务层坍缩** | consumed_event 唯一键 + id_card_route 唯一 + CAS |

调度层/MQ 永远只给到 at-least-once(它无法区分"写完盘后 crash"和"写盘前 crash",不重试→漏,重试→重)。**exactly-once 不是调度层保证,是业务层把 at-least-once 坍缩成"效果一次"**——靠幂等键让重复执行变 no-op。这是为什么 docs 全篇不吹"MQ 保证 once",而是一层层堆幂等键。

**② 原子性 ≠ 幂等——有事务为何还要幂等表**

D6 消费者分阶段事务是"原子"的(阶段2 的 route/event/occupied 一个本地事务同生成败),但**原子性挡不住跨消息/跨事务的重复执行**:crash 发生在两条消息之间,或同一条消息被重投,第二次仍会从头跑一遍事务。事务保证"这一次要么全成要么全败",不保证"不会跑第二次"。所以仍要 consumed_event 幂等表挡重投 + id_card_route 唯一键挡重复写。**常见误读:"我有本地事务了,为什么还要幂等表?"——答:事务管单次原子,幂等表管跨次去重,两件事。**

### 4.0 业务分级(第 0 层:抵御过度设计)

不是所有定时任务都要零容忍重跑。先分级,后配约束:

| 等级 | 任务 | 重跑后果 | 约束强度 |
|---|---|---|---|
| **核心强一致** | **次日 slot 生成**、到期状态对账、库存对账、路由表对账、Redis-DB预约对账(A向)、DB-Redis预约对账(B向)、场次发布对账、pending-scanner、timeout-consumer、release-consumer | 号源漂移/漏放/少约/重复落库/**重复场次致号源翻倍** | **零容忍**,配强约束(锁+marker+CAS/唯一键) |
| **非核心常规** | 提醒任务对账、pending索引对账、**孤儿 route 清理**、reminder-consumer | 重发邮件/浪费扫描 | 轻量幂等即可,不配锁/marker,避免过度设计 |

> ☑ **P1 补:「次日 slot 生成」原本不在此清单里**(07 §3.1 有这一步但从未纳管)。它显然是核心级——重跑会生成重复 slot 行,号源直接翻倍。修补三件套:① `slot` 表加 `UNIQUE(slot_date, slot_hour)`(03 §四已加);② `done:slotgen:{date}` marker;③ 按 §4.2 信封纳管。**这是"业务流程里有但任务清单里没有"的典型漏网**,同类还有孤儿 route 清理(03 §八·补 已补)。
>
> ☑ **第十三轮再补一层:这个任务当时纳管了,但它要读的「模板」当时并不存在**。检测条件"按模板"里的模板既无表也无字段,仅靠 08 §七 四个 `default-*` 静态配置项冒充(改容量要重启、无法按时段差异化容量、`release_at` 根本算不出来)。现已建 `slot_template` 表(03 §4.0),本行的检测条件与修复动作均改为读表。**这是同一处缺口的第二层**:上一轮补的是"任务没被纳管",这一轮补的是"任务的输入没有承载"。

> 分级原则:核心任务重跑 → 资损或数据错乱(对应桌面案例的"资金结算");非核心重跑 → 体验降级或浪费。把两类混居同一约束=该死守处没死守、该省心处没省心。

### 4.1 正确性地基原则(必须内化)

| 层 | 机制 | 性质 | 能保证什么 |
|---|---|---|---|
| 1 选择层 | Redisson 锁 + watchdog 续期(核心任务) | 减概率 | 通常只一个节点跑;**救不了边界**(持锁节点 GC 卡死→锁续期停→TTL 到→第二节点抢锁→卡死节点醒来继续写) |
| 2 批次层 | `done:{task}:{period}` marker,执行前查到则秒退 | 挡整批复跑 | 只挡"整批已完成被重踢";**挡不住整批中途 crash 被重跑**(marker 未写) |
| **3 记录层(地基)** | 逐项 CAS 状态机 + 修复动作唯一键 | **保正确** | **无论执行几次、锁失效与否,效果只一次** |

> ⚠️ 重心不可倒置:锁和 marker 只是减概率/挡复跑,**真正在所有 crash 模式下保正确的是第 3 层**。读本节若得出"靠锁放心"的印象=误读。姿态声明:**集群部署 + CAS/唯一键兜正确性,单/多节点是成本/效率选择,不是正确性选择**;资金/账期窗口选单节点是为省心降操作面,非因其在正确性上更稳。

### 4.2 统一信封(所有核心任务套用)

```
任务 {name} @ 周期 {period}:
  ├─ 抢 lock:{task}:{period} (Redisson+watchdog,核心任务;非核心跳过)     # 1层 减概率
  ├─ CHECK done:{task}:{period} ? → 秒退                                  # 2层 挡整批复跑
  ├─ 逐项扫描(分页+限速):
  │     检测 {检测条件}
  │     修复 {修复动作} 带 {幂等键/状态守卫}                              # 3层 保正确(地基)
  ├─ SET done:{task}:{period}=1 (短 TTL,防误判当批内)                     # 整批完成标记
  └─ 释放锁
```

修复操作共性:幂等 / 分页 / 限速 / 可暂停 / 可重跑 / 记录前后值 / 支持 dry-run / 大规模差异只告警不自动全改。

### 4.4 B 向对账重建 vs 10.2a 回滚的并发互斥(硬伤修正)

⚠️ **原 06 缺口**:B 向"reservation 在但 occupy 删 → 重建摘要",若此刻该预约正被 10.2a 回滚(INCR 桶/DEL occupy),B 向的 HSET 会覆盖 INCR 出来的桶余量——触发一次"幽灵余量"。

**修正(B 向重建三守卫)**:
1. **状态前置**:重建前查 `reservation.status`;**CANCELLED/EXPIRED 不重建**(它本就该消失,occupy 删是正确的)。
2. **NX 语义**:重建 occupy 用 `HSET ... NX` 字段级(不存在才设),或整条 `SET occupy:{rno} ... NX` 占位,**不覆盖正在变更的**。
3. **仅补漏**:B 向语义固化为"补 occupy 缺失的预约摘要",非"覆盖"。与 10.2a 的 DEL 天然不冲突(10.2a 删的是已回滚项,B 向不重建已回滚项)。

> 这是桌面 §3.2「触发一次≠执行一次」在 06 的实例:对账重建与补偿回滚是两个独立触发源,并发靠状态守卫 + NX 语义收口,不靠锁。
>
> ⚠️ 语义区分:`HSET NX`(B 向重建,字段不存在才设=补漏)与抢号侧 04 §10.1 的 `HSET`(覆盖写=新建预占)刻意不同——前者只补不覆盖,后者是首次写入。两者不冲突:抢号写的是新 rno(occupy 必然不存在),B 向补的是已落库但 occupy 被清的 rno(重建前已查 status 非 CANCELLED)。

### 4.5 库存对账修复的自身幂等(硬伤修正)

⚠️ **原 06 缺口**:`reconcile_log` 表(03 §七)只有 `id` 主键,无业务唯一键。库存对账重跑 → log 翻倍;若配自动 INCR 修复 → 两次修复抵消/叠加漂移。**这是桌面案例"明细表无唯一键"在本项目的直接对应物。**

**修正(两件套)**:
1. **log 去重**:`reconcile_log` 加 `UNIQUE(task_type, period, slot_id)`——同任务同周期同 slot 只记一条差异(冲突则更新而非新增)。
2. **修复状态守卫**:自动修复动作执行前 `SET reconcile:fixing:{task}:{period}:{slotId} NX`(短 TTL),修复完删;或对 `slot_bucket` 写时用 CAS `WHERE occupied=检测时旧值`(只在差值仍匹配时生效,防止两次修复叠加)。

> 库存对账默认**只告警不自动改**(9.5 §约束),自动修复需显式开启且必带状态守卫。

### 4.6 界外调用(第 4 层)

| 任务 | 界外段 | 幂等手段 |
|---|---|---|
| reminder-consumer(发邮件) | SMTP | **先 INSERT consumed_event 再发邮件**(3.3 已落);或邮件 message-id 幂等 |
| release/pending-scanner(投 MQ) | RocketMQ 投递 | 下游 consumed_event + id_card_route 幂等挡 |
| 其余对账 | 无界外(纯 Redis↔DB) | DB 唯一约束 + CAS |

> 界外调用 DB 唯一约束管不到,只能靠幂等流水号/消息键 + 对账兜底。这是资金类任务和普通对账的分水岭(桌面 §3.5)。

### 4.7 运营层(第 5 层)

- **失败重试分级**:业务异常(数据脏/逻辑 bug)**不重试**——重试有 bug 的逻辑=复制坏数据,比漏跑更危险;仅网络/节点故障类触发有限次数重试。
- **调度中心 HA**:只防**漏发**(中心不死),**不防重发**(重发仍靠 4.3 幂等键兜)——勿把调度中心集群当正确性保证。
- **关键窗口单节点**:大促/候鸟季放号高峰,核心对账可切单节点专属模式,**但因有 4.3 地基兜底,这是省心降操作面的取舍,不是正确性退路**。
- **调度日志持久化**:所有任务执行留痕可追溯(写 audit_log/reservation_event)。

### 4.8 跳过已结束 slot 的口径

定稿统一口径下(00 §3.2),对账**无需**对已结束 slot 做"不返还特例跳过"——`occupied` 累计语义含取消/过期且不减回,对所有 slot 统一比对 `capacity-Σ桶余量` vs `Σ occupied` 即可。唯一例外:场次发布对账对**已过 release_at 且未发布**的 slot,继续初始化无业务意义,记异常而非补放。

## 五、异常恢复闭环

```
监控/对账发现差异
  → 判定可自动修复?
     ├─ 是 → 补投/补写/CAS/回滚(幂等) → 重新校验 → 通过则关闭差异单
     └─ 否 → 升级人工(ADMIN 对账中心) → 二次确认 + 写 audit_log → 执行 → 再对账确认
```

> 规划文档原话:只能发现异常不能进入处理页验证修复=监控,非闭环。本项目对账中心(07)+ audit_log 形成真闭环。
>
> **死信与异常恢复的关系**:死信是"消息层"的最后一公里(§二·补),异常恢复闭环是"业务层"的兜底(本节)。两者层级不同:消息进死信说明消费重试耗尽,而异常恢复闭环处理的是 Redis↔DB 之间的长期漂移。一个具体 rno 可能同时进死信 + 进对账差异单——死信侧人工重投(走 consumed_event 幂等),对账侧比对状态,二者最终都收敛到 DB 同一正确状态。

## 六、可靠性的诚实边界

B 方案(02 §六):「可重试+可补偿+可对账」覆盖了 MQ 重复/丢失/延迟/消费者重启四类常见故障,达到可控最终一致。**降一档场景**:Redis 崩 + AOF 丢 → 号源实时状态 + occupy 全丢,只能 DB `occupied` 近似重建。此场景单机 AOF 下小概率,代价(牺牲招牌)不对称,接受。若未来上 Cluster/Sentinel + 多副本,该场景概率进一步降。

### 6.1 故障覆盖矩阵(诚实自检:哪些挡得住,哪些认了)
| 故障 | 谁兜 | 能否到最终一致 | 备注 |
|---|---|---|---|
| MQ 消息重复投递 | consumed_event 唯一键 + 业务唯一键 | ✅ 最终一致 | 幂等坍缩;**依赖 event_id 确定性派生**(02 §3.1) |
| MQ 消息丢失(投递/消费) | pending-scanner 补投 + 对账 | ✅ 最终一致 | 双通道恢复 |
| MQ 延迟/积压 | 消费线程池 + 落库延迟监控 | ✅ 最终一致 | 体验降级(查询走 occupy) |
| 消费者重启 | consumed_event(已处理的)+ 幂等键(未处理的) | ✅ 最终一致 | 重启后重投;**幂等表须"成功后写"**(§2.1),先写会丢 |
| 消息乱序 | DB CAS `WHERE status=0` | ✅ 最终一致 | 不依赖 MQ 顺序 |
| 消费业务异常(route冲突) | ACK + 10.2a 补偿(不重投) | ✅ 最终一致 | 不复制坏数据;**冷路径,靠故障注入验证**(04 §三·补·3) |
| 消费基础设施异常 | 重投 + DLQ(耗尽)→ 人工 | ✅ 最终一致(人工兜底) | 死信不静默丢 |
| **补投耗尽(卡单)** | `stuck_reservation` 落库 + occupy 续期 + 人工 | ✅ 最终一致(人工兜底) | ☑ 新增:原方案停续期会致桶余量永久泄漏(02 §3.2) |
| **窗口期取消/过期** | occupy 标记 + state_log 双通道 + 消费者末尾复查 + 到期对账 | ✅ 最终一致 | ☑ 新增:三道收口(02 §4.1/§4.2) |
| **Redis 崩 + AOF 丢** | ⚠️ **降一档** | ⚠️ 近似重建 | 号源实时状态丢失,回 DB `occupied` 近似重建,窗口期 occupy 丢。**此项认了**(小概率+代价不对称) |
| **Redis 崩 + AOF 未丢** | Redis 重启恢复内存 | ✅ 短暂不可用后恢复 | AOF 回放重建桶余量/occupy |
| **DB 主库挂** | ⚠️ 演示形态无主从 | ⚠️ 不可用直到恢复 | 单实例演示,无 HA |
| **应用节点挂** | 多实例(D5)+ 锁选主 | ✅ 最终一致 | 抢号无状态可水平扩 |
| **对账任务双触发** | done-marker + CAS/唯一键 | ✅ 效果只一次 | 06 §四三件套 |
| **注册跨库两写失败** | route 先占位 + 补偿删 + 孤儿清理 + 自愈复用 user_id | ✅ 最终一致 | ☑ 新增:原 docs 完全缺位(03 §八·补) |
| **提醒邮件发送失败** | ⚠️ **认了:永久漏发** | ⚠️ 不重发 | ☑ 诚实标注:先写幂等表后发邮件的必然代价;提醒是非核心,漏发=体验降级(§3.3) |
| ☑ **Redis 内存打满**(`noeviction`) | D7 降级:写命令返 OOM → 抢号返 `SERVICE_DEGRADED`;读不受影响 | ✅ 可控降级 | 第十二轮补:**前提是 `maxmemory-policy=noeviction`**(08 §7.3)。若配成 `allkeys-lru` 则**此项立刻变成"❌ 静默数据丢失"**——桶/`occupy`/`dup` 被逐出且无任何报错,是本矩阵里唯一"一个配置项决定挡得住还是兜不住"的故障 |
| ☑ **进程被 SIGTERM 打断(滚动重启)** | 优雅停机 + 消息重投 + 幂等键 | ✅ 最终一致 | 第十二轮补:D6 跨库两阶段之间无事务保护,但阶段1 主键冲突继续跑阶段2 的设计(红线 #10)本就是为此;优雅停机(08 §7.4)只是把"可避免的重投"从常态降回极少 |
| ☑ **SIGKILL(停机窗口配小)** | 同上兜底,但重投量级放大 | ✅ 最终一致 | 第十二轮补:`stop_grace_period` 默认 10s < Spring 停机窗口 30s → 每次重启都强杀在途消息。**不是数据错,是把兜底当常态用**,且掩盖真实失败率 |
| ☑ **`@Scheduled` 单线程被慢任务占死** | ❌ **原方案兜不住** → 已修 | ⚠️ 修前:全部定时任务停摆 | 第十二轮补:默认池大小 1,11 类对账 + scanner + 卡单巡检共用一根线程 → scanner 停摆则 occupy 不续期、卡单不被发现,**桶余量永久泄漏**(02 §3.2)。修法:显式 `pool-size: 8`(08 §7.4 / 红线 #41)。**这是本矩阵里唯一"故障源在自己进程内"的一条** |
| ☑ **次日 slot 生成跑到一半 crash** | `uk(slot_date,slot_hour)` + **逐 template 跳过**(红线 #48) | ✅ 最终一致 | 第十三轮补:修前是"整批 return",四模板里第 2 个已存在则第 3、4 时段**永远不生成**,且 marker 未写、下周期再撞同一点 → **永久卡死且无告警**(场次少了两个,只有用户投诉才发现)。这条与阶段1 主键冲突继续跑阶段2(红线 #10)是同一条纪律的两个实例 |
| ☑ **AES 密钥轮换** | ⚠️ **原方案兜不住** → 已修 | ⚠️ 修前:存量密文永久不可读 | 第十三轮补:`aes.key-id` 声明"支持轮换"但 `user` 无 `key_id` 列 → 换 key 后旧行解密抛 `AEADBadTagException`。且它只在"授权解密"低频路径暴露,**可能上线数月后才发现**。修法:加 `user.id_card_key_id` + yml 改密钥集(03 §2.1 / 红线 #46) |
| ☑ **`id_card_hash` 的 pepper 泄露** | ⚠️ **认了:不可轮换** | ⚠️ hash 可彩虹表攻 | 第十三轮补:pepper 进了 `id_card_route` 的 PK,轮换 = 全表 hash 作废 + PK 重建。**此项认下**,靠"与 AES 密钥同级保护(仅环境变量、不入 git)"缓解,不靠算法(03 §2.1) |
| ☑ **超管 seed 插错分库** | ❌ 无机制兜,靠阶段 0 验收 | ⚠️ 超管登不上 | 第十三轮补:`user_id=1` 必须落 `ds1`(`1 mod 2 = 1`)。插 ds0 则登录第 2 跳查不到,**现象是"孤儿 route"**(route 有、user 无)→ 排查方向被引向 03 §八·补 的补偿链路,而真因是 seed 插错库(08 §4.1 / 红线 #43) |
| ☑ **Redis 内存打满时登录也失败** | D7 降级:refresh 写不进 → 返 `SERVICE_DEGRADED` | ✅ 可控降级 | 第十三轮补:会话与库存 key 共享同一实例同一 `noeviction`(08 §4.6),故内存打满**不只抢号降级,登录同样写不进**。关键是**别返 `LOGIN_FAILED`** —— 那是把系统故障说成用户密码错,与红线 #32/#40 同类撒谎 |

> ✅ = B 方案四件套(重试/补偿/对账/死信)兜得住;⚠️ = 明确认下的降级点。**docs 的诚实体现在这张表**——哪些挡得住、哪些认了,一目了然,不让"最终一致"四个字掩盖认下的缺口。

### 6.2 怎样让"认了的"不再是"认了"(演进路径)

本节是给架构演进留的口子,不是 v1 要做:

| 降级点 | v1 认 | v2 缓解 | 代价 |
|---|---|---|---|
| Redis 崩+AOF 丢 | 近似重建 | Redis Sentinel 主从 + AOF+定期 RDB 双持久化 | 增加运维复杂度 |
| Redis 崩+AOF 丢(完全) | 同上 | Redis Cluster 多副本 + 多数派写 | 失去单机合并 Lua 跨槽优势(M3 重审) |
| DB 主库挂 | 不可用 | MySQL 主从 + ShardingSphere 读写分离 | 写仍主,读可从 |
| 落库窗口期体验 | Redis occupy 兜(已做) | 暴露 PENDING 状态 + 前端轮询确认(切 M8) | 状态机复杂度增加 |
| ☑ Redis 内存到顶=抢号不可用 | `noeviction` 降级 + 70% 告警(08 §7.3) | Cluster 分片摊内存 / occupy 落一份到 DB 中间表 | 前者失去合并 Lua,后者把 DB 写回热路径(与 Q1-B 招牌冲突) |
| ☑ v1 舱壁只隔离旁路任务 | 抢号/核销共用 Tomcat 线程池(08 §7.4) | 拆独立 worker 进程(D8 已留边界),核销独立部署 | 运维复杂度 + 失去"单进程模块化单体"的简洁叙事 |

> 关键认知:**没有"零降级点"的方案**,只有"明确认了哪些降级点 + 演进路径"的方案。桌面案例给的标准,本质不是"消除所有风险",而是"哪些风险有保正确的机制、哪些明确认了、认了之后怎么演进"——这三件事说清,就是诚实的工程。
