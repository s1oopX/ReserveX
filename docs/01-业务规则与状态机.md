# 01 · 业务规则与状态机

> 编码前必须锁死的领域模型与流转规则。与 docs-old《基于分析的规划》第一/二部分对齐,口径以 00-决策基准为准。

## 一、角色与系统边界

| 角色 | 定位 | 账号来源 | 核心职责 | 明确禁止 |
|---|---|---|---|---|
| USER | 访客 | 自助注册(邮箱验证码) | 抢号、取消、出示 QR、查记录 | 管理场次、核销他人、看运营数据 |
| STAFF | 入园核销员 | 管理员后台创建 | 扫码/手工核销、查今日待核销 | 自助注册、创建场次、改容量、看全部历史 |
| ADMIN | 园区运营 | 初始化脚预置超管 | STAFF 全权 + 场次配置 + 放号监控 + 对账统计 | 绕状态机直改业务数据 |
| SYSTEM | 自动任务执行者 | 无登录 | 发布、落库、提醒、超时取消、补偿、对账 | 无权限概念 |

STAFF/ADMIN **不能自助注册**。注册接口写死 `role=USER`,不接受前端传角色——安全点 + 组织约束。ADMIN 继承 STAFF 全权。MVP 三角色枚举,**不做完整 RBAC**(过度设计)。

## 二、核心业务规则

### 2.1 号源与容量

1. **号源有限且离散**:容量上限由生态承载量决定,管理端配 `capacity`,分批投放(示例:每日 4 时段 × 50,默认 10 桶 × 5)。
2. **抢约不直接扣实库,先预占**:抢号成功 = 占 Redis 预占额度,核销才转实到。
3. **一个号源同一时刻只能给一个人**:防超卖底线。
4. **容量只增不减**:已放号 slot 禁调小 `capacity`(不能对已预约游客反悔);`bucket_count` 已放号禁改(hash 路由错位)。
5. **分批放号削峰**:一次大峰拆多个小峰。

### 2.2 预约与配额(M7)

6. **一人一证一天配额**:**v1 固定 1 次/天**(结构性锁死,非配置项——见 03 §3.1)。Redis `SET NX dup:{slot_date}:{id_card_hash}` 第一道 + 单库 `id_card_route` PK`(id_card_hash, slot_date)` 第二道。
   > ⚠️ 两道防线的结构都只能表达"一天至多一条",`daily-per-idcard` 配成 >1 时**两道同时失效**;故 v1 固定 1,yml 保留该项但启动时 `!=1` fail-fast。真支持 N 次/天是 v2 演进(需同时改 route PK 语义 + dup 从 SET NX 改 INCR),详见 03 §3.1。
7. **取消/过期消耗配额、不补、不改约**(M1):取消或过期后,**当天不可再约**。dup 标记保留至 **`slot_date` 当日结束**(TTL 自然过期,04 §1.1 —— 原"次日 0 点"是 bug:次日 slot 的 dup 会在场次当天开始时消失),不主动删。名额作废不返还。

### 2.3 时效与兜底

8. **预占有有效期**:`valid_until` 后未核销 → 定时任务 EXPIRED(CAS),名额作废。`valid_until` 是 `slot` 表的**固化字段**(= `slot_date + slot_hour + duration_min`,03 §4.1),不在运行时派生。
9. **未核销不候补**:「号过作废」,时段过了补给别人无意义。
10. **全链路幂等**:同一 reservation_no 重复预占/确认/取消只生效一次。
11. **接口成功语义明确**:Redis 预占成功 ≠ DB 预约记录已可靠建立(落库窗口期靠 Redis occupy 兜)。

## 三、状态机

DB 物理存储 `TINYINT`,应用枚举语义名:

| TINYINT | 语义 | 含义 |
|---|---|---|
| 0 | RESERVED | 预约成功,待入园 |
| 1 | VERIFIED | 已核销入园 |
| 2 | CANCELLED | 用户主动取消 |
| 3 | EXPIRED | 超时未核销 |

> **不暴露 PENDING_PERSISTENCE / PERSIST_FAILED**(M8)。落库窗口由 Redis `occupy:{rno}` + pending-scanner + 对账覆盖。
>
> ⚠️ ☑ 修:原写「前端轮询,落库前返回"处理中"」与 D1/07 §2.1.1 矛盾——窗口期**直接从 occupy 渲染 RESERVED**(不是"处理中"),窗口期取消也直接返回终态「已取消」。v1 抢号同步返回 rno + occupy 即跳成功页,**不强制轮询**;「处理中页」是 v2 增强(07 §2.4)。这是 M8「不暴露中间态」的真正含义:对用户只有四态,没有第五态。

### 3.1 状态迁移矩阵

| 当前状态 | 操作 | 目标 | 允许 | 兜底 |
|---|---|---|---|---|
| 无记录 | 创建预约(消费者阶段0 无标记) | RESERVED | ✅ | — |
| 无记录 | 创建预约(阶段0 读到 `occupy.cancelled=1` 或 `state_log.status=3`) | **CANCELLED** | ✅ | ☑ 补:窗口期取消的落地态(02 §五) |
| 无记录 | 创建预约(阶段0 读到 `occupy.expired=1`) | **EXPIRED** | ✅ | ☑ 补:窗口期 timeout 先到(06 §3.4) |
| RESERVED | 闸机扫码核销 | VERIFIED | ✅ | CAS |
| RESERVED | 手工核销 | VERIFIED | ✅ | CAS |
| RESERVED | 用户取消 | CANCELLED | ✅ | CAS(valid_until 未到) |
| RESERVED | 超时处理 | EXPIRED | ✅ | CAS(valid_until 已过) |
| RESERVED | route 冲突清孤儿(SYSTEM) | CANCELLED | ✅ | ☑ 补:CAS 0→2,语义"未成立作废"(02 §五) |
| VERIFIED | 取消/核销 | — | ❌ | 幂等返回 |
| CANCELLED | 核销 | — | ❌ | 幂等返回 |
| EXPIRED | 核销 | — | ❌ | 幂等返回 |
| 任意终态 | 重复相同操作 | 保持原状态 | 幂等 | 读最新状态返回 |

> ☑ 前三行是**创建时即为终态**的三条路径(原矩阵只有"无记录→RESERVED"一条,与 02 §五 的 `target_status` 三分支不对齐)。**编码含义:阶段1 的 `INSERT reservation` 的 `status` 是变量,不是常量 0。**

### 3.2 状态变更用条件更新(CAS),非先查后改

```sql
-- 核销:带 version(STAFF 页面已读到 version,可挡"页面数据过期"的误操作)
UPDATE reservation
SET status = 1, verified_at = NOW(), version = version + 1, update_at = NOW()
WHERE reservation_no = ? AND status = 0 AND version = ?;   -- 受影响行数判:1成功 / 0状态已变幂等返回

-- 取消:不带 version(见下 ⚠️)
UPDATE reservation SET status = 2, version = version+1, update_at = NOW()
WHERE reservation_no = ? AND status = 0 AND valid_until >= NOW();

-- 过期(定时任务批量):不带 version
UPDATE reservation SET status = 3, version = version+1, update_at = NOW()
WHERE slot_id = ? AND status = 0 AND valid_until < NOW();
```

> ⚠️ **`version` 只在核销带,取消/过期不带 —— 这个不对称是刻意的**(04 §五 已对齐):
> - **取消**:窗口期取消时 DB 里根本没有记录,**读不到 version**,带 version 的写法在该路径无法构造(02 §4.1);且 `status=0` 已是充分守卫(状态机只有 0 有出边)。
> - **过期**:`WHERE slot_id=?` 是多行批量更新,无法逐行带 version。
> - **核销**:STAFF 扫码后先看到预约详情页(已持有 version),带上它能挡"详情页停留期间该预约已被取消、STAFF 仍点核销"的误操作 —— 这里 version 有真实语义价值。
>
> 核销与取消靠 CAS 受影响行数天然解决竞态:1=本次成功,0=状态已变→读最新状态幂等返回。**无需分布式锁。**

### 3.3 状态变更必须同步推进 `state_log`(03 §6.1)

每次 CAS 成功后,同一本地事务内推进 `state_log`(单库):核销 → `status→2`(Confirm);取消/过期/route冲突清孤儿 → `status→3`(Cancel)。窗口期取消无 reservation 记录时,直接 `INSERT ... ON DUPLICATE KEY UPDATE status=3`(空回滚占位)。

> ⚠️ 这是把 §六 TCC 三防**从叙事变成可执行**的关键 —— 原 docs 定义了 `state_log` 表却无任何写入点,三防表实际是空的,B 向对账(06 §4.3)的检测条件也永远查不到数据。写入点已在 03 §6.1 钉死。

## 四、库存不变量

$$
C = A + R + V + X
$$

| 符号 | 含义 | 存哪 |
|---|---|---|
| $C$ | 总容量 | slot.capacity |
| $A$ | 可预约库存(桶余量和) | Redis 各桶 |
| $R$ | 已预约未核销 | reservation(status=RESERVED) |
| $V$ | 已核销 | reservation(status=VERIFIED) |
| $X$ | 已消耗不再返还(取消+过期) | reservation(status∈{CANCELLED,EXPIRED}) |

⚠️ 注意:`slot_bucket.occupied`(DB)= $R+V+X$ 的近似(异步滞后),即**累计成功预约数**,不随取消/过期减回。$A$ 只在 Redis。对账本质校验 $C - A \approx \text{occupied}$。

> ⚠️ **不变量成立的四个前提**(缺一即永久带固定差,不是"近似滞后"而是"结构性错"):
> 1. **Σ桶初值 = capacity**:`capacity` 不能整除 `bucket_count` 时须按 03 §4.2 余数规则分摊(前 rem 个桶各多 1),不能各桶同值 `capacity/bucket_count`;
> 2. **增容也按余数规则**:`delta % bucket_count` 的余数同样要分摊,否则增容 5 个到 10 桶时 `5/10=0` → DB capacity 已 +5 而 Redis 一个没加;
> 3. **A 类补偿回补桶,B 类不回补**:10.2a 回补(预约从未成立,$R$ 未产生)/ 取消过期不回补(计入 $X$)。混淆则 $A$ 与 $X$ 双计。
> 4. ☑ **$A$ 的读法唯一**(第十一轮补):$A$ 必须按 `slot:meta.bucket_count` 逐个拼出 `slot:{id}:b:0..n-1` 后单次 `MGET` 求和(05 §1.4.1),**不能用 `KEYS`/`SCAN` 通配、不能"有几个 key 算几个桶"**——某桶被 TTL 清掉时后者会把桶数误读成 n-1,$A$ 偏小 → 不变量带差且**表现为"像是超卖"**,方向恰好与真超卖一致,最难辨。
>
> 这四条是库存对账(06 §4.3)差值恒为 0 的前提,压测"成功预约数 = capacity"(09 §三)也靠它们。

## 五、事件流水(不可变)

每次状态变更落 `reservation_event`,回答"谁何时把预约从何状态改成何状态":

```text
reservation_event: event_id / reservation_no / event_type / from_status / to_status /
                   operator_type(USER/STAFF/ADMIN/SYSTEM) / operator_id / request_id / event_time
```

与 `state_log`(TCC 三防:空回滚/悬挂/幂等)并存:state_log 管事务边界,reservation_event 管业务审计。

## 六、TCC 三防(简历叙事)

| 威胁 | 防护 | state_log |
|---|---|---|
| 空回滚 | Cancel 先到(status=0)→ 记 status=3 | Try 后到查 status=3 拒绝 |
| 悬挂 | Cancel 后 Try 到 → 查 status=3 拒绝 Try | 同上 |
| 幂等 | 重复 Confirm/Cancel → 查 status 已 2/3 → 跳过 | 同上 |

> 单体应用无跨服务调用,本项目的 TCC=「跨存储(Redis 预占↔MySQL 实到)两阶段状态机」,参考 TCC 思想自研,非标准 Seata TCC。简历诚实写法见 10。
