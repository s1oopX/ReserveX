## 二、定稿修正需调整的页面口径

> 相对 docs-old《页面内容分析》,以下因 M1/M4/B 方案需改文案/交互:

### 2.1 取消弹窗文案(M1 不返还)

docs-old §五取消确认弹窗原写「取消名额不重新释放」。定稿 M1 统一不返还,文案强化:

> 取消后名额**作废且不返还**,他人无法重抢;您当日配额已消耗,**不可改约其他时段**。确认取消?

并补:取消成功后 QR 立即失效、状态→CANCELLED、写时间轴、发取消通知(可选 v2)。

#### 2.1.1 窗口期取消的前端口径(☑ 补:02 §4.1/§4.2 的 UI 面)

落库窗口期(DB 还没记录)用户点取消时,后端走「只标记 `occupy.cancelled=1`,不删 occupy」路径。前端必须按此渲染,**不能因为 DB 查不到就显示"预约不存在"**:

| 情形 | 后端返回 | 前端展示 |
|---|---|---|
| DB 有记录,CAS 成功 | CANCELLED | 「已取消」+ QR 失效 |
| DB 无记录(窗口期),已标记 | CANCELLED(状态由 `occupy.cancelled` 派生) | 「已取消」+ QR 失效,**与上一行完全一致** |
| DB 有记录但状态已变(已核销/已过期) | 幂等返回当前状态 | 「该预约已核销 / 已过期,无法取消」 |

> ⚠️ 关键:窗口期取消返回的仍是**终态「已取消」**,不是「处理中」——用户点了取消就该看到取消成功。后端的双通道(occupy 标记 + state_log 空回滚占位)保证消费者落库时会落成 CANCELLED,前端无需暴露这段复杂度(M8 不暴露 PENDING)。

### 2.2 「我的预约」窗口期态(B 方案 D1)

落库窗口期(典型<1s,极端分钟级)DB 无记录。列表/详情**从 Redis occupy:{rno} 渲染**(D1):

- 列表:列出 occupy 中 rno + 场次摘要(slot_date/slot_hour)+ 状态 RESERVED。
- 详情:occupy 全字段 + 状态 RESERVED + "数据同步中"轻提示(可选)。
- DB 落库后字段一致,**用户无感切换**。

接口实现:查「我的预约」→ 先查 DB(user_id 命中分库)→ 补查 Redis `occupy` 中 user_id 匹配但 DB 无的 rno → 合并去重返回。

> ⚠️ 合并时**必须读 occupy 的 `cancelled` / `expired` 标记**并据此派生状态,不能一律显示 RESERVED —— 否则窗口期取消后用户在列表里仍看到「待入园」,与 §2.1.1 的取消成功页自相矛盾。
>
> ⚠️ `occupy` 里若有 `stuck=1`(02 §3.2 卡单),前端仍按 RESERVED 正常渲染,**不向用户暴露卡单**(那是运维态);卡单只进 ADMIN 对账中心(§四)。

### 2.3 场次卡片状态(D3 slot:meta)

| 状态 | 文案 | 按钮 |
|---|---|---|
| 未发布 | `10:00 开放预约`(倒计时取 `release_at`) | 不可点击 / "提醒我" |
| 可预约 | `剩余 23 个名额`(桶余量和,读法见 05 §1.4.1:按 `bucket_count` 拼 key + `MGET`) | 立即预约 |
| 余量紧张 | `仅剩 3 个` | 立即预约 |
| 已满 | `名额已满`(slot:full 命中) | 禁用 |
| 已结束 | `预约已结束`(valid_until<now,slot:meta 判) | 禁用 |
| 已预约当日 | `您今天已有预约`(dup 命中或 DB RESERVED) | 查看预约 |
| 系统繁忙 | `预约人数较多,请稍后重试` | 重新尝试 |

> 未发布倒计时 / 已结束禁用**依赖 slot:meta 缓存**(D3),否则卡片高频查打 DB。

### 2.4 预约处理中页(B 方案)

抢号返回 rno 后,若前端选轮询确认落库:

```
提交 → "正在确认预约" + rno + 加载态
  ├─ 落库成功(查 DB/occupy 均在)→ 成功页
  ├─ 落库中(occupy 在 DB 无)→ 持续/返回成功页(occupy 渲染)
  ├─ 补偿回滚(occupy 已删)→ 失败页"名额未占用,请重新选择"
  └─ 暂无法确认 → 保留 rno,记录中可查
```

v1 可简化:抢号同步返 rno+occupy 即跳成功页(occupy 渲染),不强制轮询;处理中页作 v2 增强。

## 三、六条业务闭环

### 3.1 场次发布闭环

```
ADMIN 创建/启用 slot_template(03 §4.0,单库表)
→ 次日 slot 生成任务(每日 cron,核心级)读 slot_template WHERE enabled=1
   ├─ uk(slot_date, slot_hour) 冲突 → 已生成,**跳过该 template 继续下一个**(红线 #48)
   ├─ INSERT slot(template_id 溯源;capacity/bucket_count/duration_min **复制**自模板,不引用;
   │             valid_until = slot_date + slot_hour + duration_min;
   │             release_at = slot_date 00:00 + release_offset_min,均固化)
   └─ INSERT slot_bucket(逐桶按余数规则:前 rem 个桶各多 1)→ released=0
→ 投递 SlotRelease 延时消息(release_at,event_id='sr-'+slot_id)
→ release-consumer 抢 Redisson 锁 → CAS released 0→1
→ **CAS 成功才**执行 10.3 初始化 Redis 桶(逐桶传值)→ HSET slot:meta 全7字段(带 TTL 抖动)→ 删 slot:full
→ 未抢到锁/CAS 0 行的实例 → 幂等跳过,**绝不执行 10.3**(SET 覆盖会把已抢余量重置回满=超卖)
→ 场次发布对账(release_at 已过且 released=0 → 幂等补放)
→ 发布监控页展示结果
```

> ⚠️ **模板改动不回溯已生成的 slot**(03 §4.0):`slot` 复制了容量/桶数而非引用 `template_id`。管理端「场次模板」页保存后要提示"自次日生成起生效",否则运营会以为改了今天的容量。要改今天的,走「场次日历」的增容接口(§3·补·3 `POST /api/admin/slots/{id}/capacity`)。

### 3.2 用户预约闭环(B 方案)

```
USER 场次列表 → 预约确认页 → 限流+风控+slot:meta校验
→ 10.1 Lua:dup判重+选桶扣减+写occupy满载荷+ZADD pending
→ 返 rno+RESERVED → 成功页(occupy渲染)
→ 发 ReservationCreated → persistence-consumer 分阶段落库(D6)
→ 写 route/event/occupied → ZREM pending
→ 投递 ReminderTrigger + TimeoutExpire
→ DB 落库后"我的预约"无缝切 DB
异常:dup已用→配额提示;售罄→slot:full刷新;落库失败→10.2a补偿
```

### 3.3 提醒闭环

```
ReminderTrigger 延时到 valid-30min → 查 occupy/DB status
→ RESERVED → 发邮件(预占才提醒)
→ VERIFIED/CANCELLED/EXPIRED → 跳过
→ 发送失败重试 → 超限进死信队列(06 §二·补)→ ADMIN 对账中心/消息任务页处理
```

### 3.4 核销闭环

```
USER 出示 QR(60s 动态+HMAC)
→ STAFF 扫码/手工输入 → 服务端校验签名+时效+nonce+状态+权限
→ CAS status 0→1 (WHERE status=0 AND version=?)   ← 详情页已持有 version(01 §3.2)
→ 同一本地事务:Confirm state_log(status 1→2)+ 写 verification_log(qr_nonce 唯一防重放)+ reservation_event
→ 1 成功 / 0 已核销(重复,返首次信息)/ 状态已变(返对应拒绝)
→ 扫码与手工走同一服务端流程,不形成两套规则
```

> ⚠️ **窗口期不可核销**:若 DB 查无该 rno(仍在落库窗口),核销**返回"预约正在确认,请稍候重试"而非"无效码"**。理由:此时 CAS 无行可改,若按无效码拒绝,游客已在闸口却被判假票;而放行更不可以(没有可 CAS 的记录 = 无法保证只核销一次)。窗口期典型 <1s,提示重试即收口。**这条是 STAFF 端最容易被漏掉的边界。**

#### 3.4.1 QR 载荷与验签契约(☑ 补:原只有"60s HMAC + nonce"口号,载荷格式/取码接口/手工核销入参全未定义)

⚠️ **原缺口**:00 §四 把「QR 签名」列进阶段 1 MVP,08 §9.2 声明"自研 HMAC 签名"是亮点,但**载荷长什么样、nonce 谁生成、手工核销输入什么**三处全空 → 编码即卡死,且 `verification_log.qr_nonce` 的 `NOT NULL UNIQUE` 手工核销根本满足不了。

**载荷格式(点分五段,base64url 无填充)**:

```
v1.{kid}.{rno}.{exp}.{nonce}.{sig}
   kid   = 密钥版本(对应 yml qr.key-id,支持双 key 并存轮换)
   rno   = reservation_no(十进制)
   exp   = 过期 unix 秒 = now + qr.ttl-sec(60)
   nonce = 16 字节随机 hex(32 字符),每次取码新生成
   sig   = base64url( HMAC-SHA256(qr.hmac-key[kid], "v1|kid|rno|exp|nonce") )
```

**取码接口**:`GET /api/reservations/{reservationNo}/qr`(登录态,**只能取自己的** reservationNo,越权返 403)→ 返回 `{payload, exp}`;前端按 `exp` 倒计时,到点自动重新取码。

- **服务端不预存 nonce**(不写 Redis):取码是高频操作,每次写 Redis 会把"抢号只动 Redis"的时间片让给取码。防重放由**验签时的两道**承担,见下。
- 载荷**只含 rno**,不含姓名/身份证/手机号 —— 截图外泄最多暴露一个 rno,且 60s 后失效。

**验签顺序(任一失败即拒,不继续)**:

```
1. 解析五段 + 版本号 = v1        → 否则 result=4 无效码
2. kid 在当前有效密钥集内        → 否则 result=4(轮换下线的旧 kid 直接拒)
3. sig 重算比对(常量时间比较)   → 否则 result=4(防篡改 rno)
4. exp >= now                    → 否则 result=4「二维码已过期,请刷新」
5. 查 reservation(rno 定位分库) → 查无 → **"预约正在确认,请稍候重试"**(见上 ⚠️,不是无效码)
6. CAS status 0→1 (AND version=?) → 0 行则读最新状态返对应拒绝
```

**手工核销的入参与授权(与扫码的唯一差异处)**:

| | 扫码核销 | 手工核销 |
|---|---|---|
| 入参 | 完整 payload | **仅 `rno`**(STAFF 手输/搜索,配 `id_card_masked` 二次比对身份) |
| 签名校验 | 有(第 1~4 步) | **无**(没有载荷可验) |
| 授权补偿 | STAFF 角色即可 | **二次确认 + `audit_log(MANUAL_VERIFY)` 必写** |
| `verification_log.qr_nonce` | 填载荷 nonce | **NULL** |
| 状态机/CAS/state_log | 完全相同 | 完全相同 |

> ☑ 这才是 §3.4 「扫码与手工不形成两套规则」的准确含义:**状态机与 CAS 只有一套,差异只在"入口凭证强度"**——扫码凭签名,手工凭 STAFF 身份 + 审计留痕。别写成两条服务路径。
>
> ⚠️ **`verification_log` 的两处 DDL 修正**(03 §七已改):① `qr_nonce` 改**可为 NULL**(手工核销无 nonce;MySQL 唯一索引允许多个 NULL,uk 仍成立);② 失败尝试也要落流水,但 `qr_nonce` 存 NULL、真实 nonce 记入非唯一列 `attempt_nonce` —— 否则"重放的第二次尝试"会撞 uk 而**连日志都记不下来**,08 §6.1 的「无效二维码次数/重复核销次数」指标就没有数据源。
>
> ⚠️ **诚实口径**:真正挡住重复核销的是 **CAS `status 0→1`**(同一 rno 只有一条记录可改);`uk(qr_nonce)` 是第二道,作用是让"同一张截图二次核销成功"在存储层不可能。面试别说成"靠 nonce 唯一键防重复核销"——那会被追问"nonce 不入库前你拿什么比对",答案是不比对,靠 CAS。
>
> ⚠️ **密钥必须与 AES 数据密钥分离**:`qr.hmac-key` 用独立环境变量 `QR_HMAC_KEY`,**不复用 `AES_KEY`**(08 §七已改)。同一密钥既加密身份证又签 QR,一处泄露两处失守,且轮换周期本该不同。

### 3.5 取消闭环(M1 不返还)

```
USER 详情点取消 → 二次确认(作废不改约文案)
→ CAS status 0→2 (WHERE status=0 AND valid_until>=now)   ← 不带 version(01 §3.2)
→ 受影响 1:QR 立即失效 → Cancel state_log(→3)+ 写 reservation_event
→ 受影响 0:**先 SELECT 确认记录是否存在**(02 §4.2 收口第2道)
     ├─ 查到 → 状态已变(已核销/已过期)→ 幂等返回
     └─ 查不到 → 窗口期 → HSET occupy.cancelled=1 + state_log 空回滚占位 → 返回"已取消"
→ 全路径均不回补 Redis 桶、不删 dup、不删 slot:full、不减 occupied
→ 配额消耗,当天不可改约
```

### 3.6 异常恢复闭环

```
对账/监控发现差异 → 判可自动修复?
→ 是:补投/补写/CAS/10.2a回滚(幂等)→ 重校验 → 闭单
→ 否:升级 ADMIN 对账中心 → 二次确认+audit_log → 执行 → 再对账
```

## 三·补 接口契约(☑ 第十轮补:原全 docs 只有 2 个 URL 散落,无清单/无响应包/无错误码)

⚠️ **原缺口**:docs 定义了每条业务分支的**语义**(Lua 返 -1/0/1、窗口期"正在确认"、越权 403、route 冲突、CAS 0 行…),但从未定义这些语义**在 HTTP 层怎么表达**。后果:前端无法写(不知道判什么字段)、后端每个 controller 各发明一套、09 的压测脚本与验收断言无锚点。**这是与 §3.4.1 同类的缺口:决策定了,承载它的契约没有。**

### 3·补·1 统一响应包(所有接口,含失败)

```json
{ "code": "OK", "msg": "成功", "data": { }, "requestId": "..." }
```

- **HTTP 状态码表达资源处理结果**:GET/PATCH 成功 200,创建 201,异步受理 202,删除成功 204;请求错误 400,未登录 401,无权 403,不存在 404,状态冲突 409,前置条件失败 412,限流 429,依赖不可用 503。响应体始终保留稳定 `code` 供前端细分业务原因。
- `code` 是**字符串枚举**不是数字:排障时日志里 `QUOTA_USED` 比 `1003` 直接可读;前端 switch 不需要对照表。
- `requestId` = MDC 里那一个(08 §6.0 Tracing),**响应里必须回带** —— 用户截图报错即可全链路定位,否则"5 分钟定位"少了入口。
- `data` 在失败时为 `null`;**唯一例外**:`ALREADY_VERIFIED` 要回带首次核销信息(§3.4 "返首次信息"),放 `data`。

### 3·补·2 错误码表(与各章业务分支一一对位,不新增语义)

| code | HTTP | 触发点 | 前端展示 |
|---|---|---|---|
| `OK` | 200 | 成功 | — |
| `SLOT_NOT_FOUND` | 404 | slot:meta 不存在/空值缓存(02 §一 前置校验) | 「场次不存在」 |
| `SLOT_NOT_RELEASED` | 409 | `released=0`;`data.releaseAt` 回带 | 「未放号」+ 倒计时(§2.3) |
| `SLOT_ENDED` | 409 | `valid_until < now` | 「预约已结束」 |
| `SLOT_FULL` | 409 | Lua 返 **0**(04 §二) | 「名额已满」(§2.3 禁用卡片) |
| `QUOTA_USED` | 409 | Lua 返 **-1**(dup 命中) | 「您今天已有预约」+ 跳我的预约 |
| `CAPTCHA_REQUIRED` | 400 | 风控滑窗触发(05 §四);`data.captchaToken` | 弹图形验证码 |
| `CAPTCHA_INVALID` | 400 | 验证码错/过期 | 「验证码错误,请重试」 |
| `RATE_LIMITED` | **429** | 本地 Guava 或 Redis RRateLimiter 未取到令牌 | 「预约人数较多,请稍后重试」 |
| `SERVICE_DEGRADED` | 503 | D7 降级:**Redis 挂的三种形态**均归此码——① 连不上(超时/拒连)② Lua 执行异常 ③ ☑ **内存打满**(`noeviction` 下写命令返 `OOM command not allowed`,进程活着、读照常、`ping` 仍 PONG,05 §五 / 08 §7.3) | 「系统繁忙,请稍后重试」(**不说"已满"**,那是撒谎) |
| `RESERVATION_NOT_FOUND` | 404 | DB 与 occupy 查无,或当前用户不是资源所有者(防存在性枚举) | 「预约不存在」 |
| `RESERVATION_CONFIRMING` | 409 | 窗口期核销:DB 查无但 occupy 在(§3.4 ⚠️) | 「预约正在确认,请稍候重试」 |
| `ALREADY_CANCELLED` / `ALREADY_EXPIRED` | 409 | 取消/核销时状态已变 | 「已取消 / 已过期,无法操作」 |
| `ALREADY_VERIFIED` | 409 | 核销 CAS 0 行且现状=1(`result=1`);`data` 回带首次 `verifyTime`/`staffId` | 「已核销」+ 首次核销时间 |
| `QR_INVALID` | 400 | 验签 1~3 步失败(`result=4`) | 「无效二维码」 |
| `QR_EXPIRED` | 400 | 验签第 4 步 `exp < now`(`result=4`) | 「二维码已过期,请刷新」 |
| `REGISTRATION_CONFLICT` | 409 | 邮箱或手机号 route PK 冲突(对外不区分字段,防账号枚举) | 「邮箱或手机号已注册」 |
| ☑ `LOGIN_FAILED` | 401 | 登录两跳任一失败:route 查无 / 分库查无(孤儿 route)/ BCrypt 不匹配(03 §2.2) | 「邮箱或密码错误」(**三种原因同一文案**,防用户枚举) |
| ☑ `ACCOUNT_BANNED` | 403 | `user.status=1` | 「账号已封禁,请联系管理员」 |
| ☑ `PASSWORD_CHANGE_REQUIRED` | 409 | 超管首登(`force-change-on-first-login`,08 §4.1);`data` 回带一次性改密 token | 跳强制改密页 |
| ☑ `TEMPLATE_INVALID` | 400 | 建/改模板校验失败:`release_offset_min >= slot_hour*60` 或 `capacity < bucket_count`(03 §9.1) | 「放号时点晚于场次结束 / 容量小于分桶数」 |
| `SLOT_RELEASED_LOCKED` | 409 | 改已放号 slot 的 `bucket_count` 等锁定字段(03 §九) | 「该场次已放号,此项不可改」 |
| `FORBIDDEN` | **403** | 角色不符 | 「无权操作」 |
| `UNAUTHORIZED` | **401** | 未登录 / token 失效 | 跳登录 |
| `INTERNAL_ERROR` | **500** | 未捕获异常(**不泄露堆栈/SQL**) | 「系统异常,请稍后重试」+ `requestId` |

> ⚠️ **`SLOT_FULL` 与 `SERVICE_DEGRADED` 必须区分**:两者前端都是"约不到",但语义相反(前者名额真没了、后者系统不可用)。混成一个会让 D7 降级在监控上完全不可见(08 §6.1「库存不足率」指标会被降级请求污染)。**内存打满是这条纪律最刁的一种触发**:Lua 的 `INCR`/`DECR` 返 OOM 错误而非返 0,若 catch 里笼统 `return SLOT_FULL`,监控上表现为"全部场次同时约满"——一个不可能的业务事实(09 §6.8 用例 2 专抓此点,红线 #40)。
>
> ⚠️ **窗口期的三个 code 是一组**:`RESERVATION_CONFIRMING`(核销)/ 取消返 `OK`+CANCELLED(§2.1.1)/ 查询返 `OK`+occupy 渲染(§2.2)。**同一状态在三个接口上有三种正确表达**,这正是 M8「不暴露 PENDING」的代价——前端不知道有窗口期,只看到三种普通结果。
>
> ⚠️ ☑ **`LOGIN_FAILED` 必须把三种原因合成一个 code**(邮箱不存在 / 孤儿 route / 密码错)。分开返会变成**用户枚举接口**:攻击者用邮箱列表刷一遍,凭 `EMAIL_NOT_FOUND` 与 `PASSWORD_WRONG` 的区别就能筛出所有已注册邮箱。**但服务端日志里三者必须可区分**——孤儿 route 那一支要单独告警(它意味着 03 §八·补 的补偿链路留下了脏数据)。「对外一个码、对内三个日志分支」是这条的完整口径。
>
> ⚠️ ☑ **内存打满时登录返 `SERVICE_DEGRADED` 而非 `LOGIN_FAILED`**:refresh token 要写 Redis(08 §4.6),`noeviction` 下写被拒。返 `LOGIN_FAILED` 等于告诉用户"你密码错了"——**把系统故障说成用户错误**,与 `SLOT_FULL`/`SERVICE_DEGRADED` 那条(#32/#40)是同一类撒谎,同样会污染指标(登录失败率飙升会被误判为撞库攻击)。

### 3·补·4 序列化契约:ID 一律字符串、时间一律显式(☑ 第十一轮补:原全 docs 未定义)

⚠️ **原缺口**:`reservation_no` / `user_id` / `slot_id` 都是 **Snowflake BIGINT**(19 位十进制,量级 `1e18`),而 JS `Number` 的安全整数上限是 `2^53-1 ≈ 9.007e15`。**JSON 里直出数字 → 前端拿到的 rno 末 2~3 位被静默改写**。后果链:

1. 成功页拿到错的 reservationNo → `GET /api/reservations/{错reservationNo}/qr` 返 `RESERVATION_NOT_FOUND`,用户看到"预约成功"却取不到码;
2. 更坏的情况是**改写后恰好命中另一条真实 rno**(Snowflake 同毫秒序列号连续,末位相邻的 rno 真实存在)→ 越权读/取到他人的码,而 #33 的归属校验**挡不住**(它校验的是"这个 rno 属不属于我",而攻击不需要伪造——精度丢失自己就把 rno 改成邻居的了);
3. QR 载荷里 `rno` 是十进制段(§3.4.1),前端把错 rno 传回验签环节 → 签名验过但查库查空,落到"预约正在确认"分支,`attempt_nonce` 里堆一堆查不出原因的失败;
4. 09 压测脚本按 body 解析 rno 做后续请求同样错位。

**这不会立刻报错**(数字合法、HTTP 200、前端不抛异常),属于典型"静默数据错"。

**契约(钉死)**:

| 类型 | JSON 表示 | 理由 |
|---|---|---|
| `reservationNo` / `userId` / `slotId` / `staffId` / `eventId` / 所有 Snowflake ID | **字符串** | 越过 `2^53` 精度悬崖;字符串比对与拼 URL 都无损 |
| `slotDate` | 字符串 `"2026-08-10"` | 对应 DDL `DATE`;前端只用于展示与分组,不做时区换算 |
| `slotHour` | 数字 `9` | 对应 DDL `INT`,小整数无精度问题 |
| `validUntil` / `createAt` / `verifyTime` 等 DATETIME | 字符串 `"2026-08-10 11:00:00"`(不带时区后缀) | 全系统单时区(08 §7.2),带偏移量反而给前端制造换算机会 |
| `exp`(QR 载荷内)/ `releaseAt` 的倒计时用值 | **unix 秒**(数字) | 倒计时要做算术;秒级量级 `1.8e9` 远在安全区内 |
| 余量 / 计数 / `version` | 数字 | 小整数 |

**落地**:Jackson 全局配置 `Long`/`long` 序列化为 String(或在 DTO 上标 `@JsonSerialize(using=ToStringSerializer.class)`),**统一在 `common/` 的 ObjectMapper 配置里做一次**,别逐个 DTO 标注——漏一个就是一条静默错路径。反序列化侧接受字符串与数字两种输入(前端回传的一定是字符串)。

> ⚠️ **路径参数不受影响但仍要小心**:`/api/reservations/{reservationNo}` 里 reservationNo 是 URL 字符串,后端 `Long.parseLong` 无损;**错的来源永远是"前端先把它当数字存过一次"**。所以前端侧的纪律是:**reservationNo 从收到到用掉全程当字符串**,不要塞进任何做过 `JSON.parse` 后再 `Number()` 的路径。
>
> ⚠️ **`slotDate` 不要用 `Date` 对象中转**:`new Date("2026-08-10")` 在浏览器里按 UTC 解析,`toLocaleDateString()` 在 +08:00 下仍是 8/10,但在负时区机器上会显示 8/9 —— 演示环境不会暴露,换台机器就错。直接当字符串用。
>
> ⚠️ **别让这条配置串到 MQ payload 上出问题**:MQ 消息体(06 §一)也含 `rno`/`slot_id`,若与 HTTP 共用同一个全局 ObjectMapper,payload 里的 ID 同样会变成字符串——**这本身无害**(Java 两侧都无精度问题),但**消费者的 DTO 必须能接受字符串输入**,否则升级这条配置的当天所有在途消息反序列化失败、集体进 DLQ。两个做法二选一并写清:① 全局 ObjectMapper 统一 + 消费者 DTO 用 `Long` 且允许 String 入参(Jackson 默认支持);② MQ 用独立 ObjectMapper 不做 Long→String。**推荐 ①**(少一个配置分叉),但要在集成测试里覆盖"字符串形式的 payload 能被消费"。

### 4.2 发布监控页要看什么(☑ 补)

对位 §3.1 闭环与 06 §4.3「场次发布对账」:

| 区块 | 内容 |
|---|---|
| 待发布 | `released=0` 且 `release_at` 未到 → 倒计时 |
| 发布异常 | **`release_at` 已过且 `released=0`** → 红色告警(对账每分钟补放,持续未变即链路故障) |
| 已发布 | `released=1` + Σ桶余量 / capacity 水位条 + `slot:meta` 是否存在(缺失=需单飞重建) |
| 一致性 | 该 slot 的 `capacity - Σ桶余量` vs `Σ slot_bucket.occupied` 实时差值(>0 持续即进差异单) |
