# 02 · 抢号链路

> 项目核心链路。Q1-B 定调:抢号只动 Redis,主表落库由 MQ 消费者异步完成,失败靠 pending-scanner + 10.2a 补偿 + 对账收口。

## 一、抢号主链路(B 方案)

```
用户提交抢号(slot_id)
 ├─ 服务层限流:D4-A 分层
 │     本地 Guava(接口级)→ Redis RRateLimiter(用户级 rl:user:{id} + 场次级 rl:slot:{slotId})
 ├─ 风控:滑动窗口 ZSet
 │     高频(脚本特征)→ 弹图形验证码,通过才续
 │     低频(真人)→ 放行
 ├─ 状态前置校验(D3):读 slot:meta:{slotId}
 │     ├─ 不存在/=NULL → "场次不存在"
 │     ├─ released=0    → "未放号 + 倒计时"(取 slot:meta.release_at,不进 Lua)
 │     ├─ valid_until<now→ "已结束"(不进 Lua)  ← 修复过期能抢号 bug(依赖 slot.valid_until 字段,03 §四)
 │     └─ 合法          → 续
 ├─ 生成 rno(Snowflake)→ 算路由:bucket_no = hash(rno) % bucket_count(03 §4.3)
 │     KEYS[1]=命中桶;KEYS[2..]=环形借桶序 (bucket_no+i)%bucket_count —— 顺序由应用层排,勿固定从0
 ├─ Redis Lua 原子(04 §10.1): SET NX dup 判重 + 选桶/借桶扣减 + 写 occupy 满载荷 + ZADD pending
 │     dup 已存在 → 返回 -1「今日配额已用」(不占库存、不发消息)
 │     全空      → 返回 0「已约满」+ **Lua 内 SET slot:full**(04 §1.2)  ← D3:应用层已挡非法id,此处只防真售罄
 │     成功      → 返回 1 + 命中桶号 + reservation_no
 ├─ 发 RocketMQ 普通消息(ReservationCreated)
 │     payload: event_id/rno/user_id/slot_id/slot_date/bucket_no/id_card_hash/create_ts
 │     **event_id = 'rc-' + rno(确定性派生,§3.1)** —— 补投必须复用同一 event_id,否则幂等表失效
 │     发送失败 → 有限重试 → 仍失败 → pending-scanner 扫 occupy 补投(对账兜底)
 ├─ 同步返回 reservation_no + RESERVED(立即可查)
 └─ 用户侧:抢号成功页/我的预约 → 窗口期从 occupy:{rno} Redis Hash 渲染(D1)
```

> ⚠️ **抢号线程内不写任何 DB**(Q1-B 招牌)。`state_log` 的 Try 写入在消费者阶段2(03 §6.1),不在此处——否则 DB 写回到热路径,与"只动 Redis"矛盾。

## 二、occupy 满载荷(D1)

Lua 内 `HSET occupy:{rno}` 塞:

```
slot_id / slot_date / slot_hour / valid_until / bucket_no / user_id / id_card_masked / create_ts
```

- 窗口期(落库前 DB 无记录)预约成功页 + 我的预约 + 详情 **全程 Redis 渲染**。
- DB 落库后 reservation 表字段与 occupy 一致,**无缝切换**,用户无感。
- **为何敢 denormalize**:slot 字段发布后锁定(slot_hour/valid_until 发行即定;capacity 只增;bucket_count 已放号禁改),user 脱敏注册后不变 → **staleness 风险为 0**。
- 备选 synthetic(occupy 只存四主键,场次/user 字段从 slot:meta + user 路由合成):单源真理但每次多 2 lookup;staleness 实为 0 故无 denormalize 收益,弃。

## 三、pending:persist ZSet 索引(D2)

Lua 内并行写:

```
HSET occupy:{rno} ...        # 满载荷
ZADD pending:persist {create_ts} {rno}   # 待落库索引
```

- **消费成功** → `ZREM pending:persist {rno}`(消费者侧)。
- **10.2a 补偿撤销** → Lua 末尾**必须 `ZREM pending:persist {rno}`**(否则 ZSet 泄漏、scanner 脏扫)。
- scanner `ZRANGEBYSCORE 0 (now-30s)` 捞超时未落库;捞到的 rno 先 `EXISTS occupy` 判定:存在→补投 MQ + **续期 occupy TTL**(防补投后仍积压时 occupy 过期导致查询断);不存在(已过期/已回滚/已落库)→显式 `ZREM` 清理。
- **补投上限(防与 10.2a 竞态)**:scanner 对同一 rno 补投次数设上限(默认 5 次,见 08 yml `pending.reinject-max`)。耗尽仍 pending → 转 §3.2 stuck 流程,**不自主 10.2a 回滚**(理由见 04 §三·补:自主放弃与补投竞态致幽灵预约)。

### 3.1 补投消息必须复用同一 `event_id`(☑ P1 修:原未定义)

⚠️ **原缺陷**:06 §一 声明 `ReservationCreated` 幂等键 = `event_id + rno`,但 scanner 补投时 `event_id` 从哪来**从未定义**。若补投生成新 `event_id`,`consumed_event(consumer_group, event_id)` 去重**完全失效**——同一预约的 N 次补投在幂等表里是 N 条不同记录,全部会被消费。

**钉死**:`event_id` 由 rno **确定性派生**,不用随机 UUID:

| 消息 | event_id 规则 |
|---|---|
| `ReservationCreated` | `'rc-' + rno` |
| `CompensateRollback` | `'cr-' + rno` |
| `ReminderTrigger` | `'rm-' + rno` |
| `TimeoutExpire` | `'te-' + rno` |
| `SlotRelease` | `'sr-' + slot_id` |

- 首次发送与 scanner 补投、MQ 重投**天然同 event_id** → `consumed_event` 唯一键真正生效;
- 前缀区分事件类型,防不同事件的 event_id 在同一 `consumer_group` 下相撞(虽然 group 已隔离,前缀让排障时肉眼可辨);
- 无需额外存储 event_id(不用为了"记住第一次发的 id"再加一张表)。

> ⚠️ 这条同时修好了 09 §六「MQ 发送成功客户端认为失败 → 幂等表挡重复」这条故障注入 —— 原本 event_id 不确定时该测试根本不可能通过。

### 3.2 stuck 状态必须**落库**,不能只靠 Redis(☑ P1 修:桶余量永久泄漏)

⚠️ **原缺陷**:原文档写「补投达上限 → 标记 `occupy.stuck=1`、**停止续期**、转人工」。停止续期 → occupy 在 TTL(30min)后消失。此后:

- 人工研判若选"回滚",10.2a 因 `EXISTS occupy == 0` 直接走幂等分支返回 0,**桶不回补**;
- 而 06 §4.5 库存对账默认**只告警不自动改** → 该名额**永久损失且无任何自动收口**;
- 更糟:占用凭证消失后,人工连"该回滚什么"都查不到(bucket key、dup key 全在 occupy 里)。

**修正:stuck 时把恢复所需的一切落 DB,不依赖 Redis 存活**:

```
scanner 判定 reinject 次数耗尽:
 ├─ 1. INSERT stuck_reservation(rno, slot_id, bucket_key, dup_key, user_id, id_card_hash,
 │        slot_date, create_ts, reinject_count, last_error, status=0 待研判)   ← 单库新表,见 03
 ├─ 2. HSET occupy:{rno} stuck 1  且 **继续续期 occupy**(不再停)
 │        理由:窗口期查询仍要靠 occupy 渲染,停续期会让用户"我的预约"里这条直接消失
 ├─ 3. ZREM pending:persist {rno}(移出待扫索引,避免 scanner 每轮重复捞同一条)
 └─ 4. 告警 + 进 ADMIN 对账中心「卡单列表」(07 §四)
人工处置(对账中心,写 audit_log):
 ├─ 重投 → 复用 event_id 'rc-'+rno 重发(§3.1) → 成功后 stuck_reservation.status=1
 └─ 回滚 → 执行 10.2a(参数从 stuck_reservation 表取,**不依赖 occupy 是否还在**)
         → occupy 若已过期,则手工补齐:INCR bucket_key / DEL dup_key / DEL slot:full → status=2
```

> ⚠️ 关键改动:**继续续期 occupy** + **参数落库**。前者保用户查询不断,后者保回滚能力不随 Redis TTL 消失。这与 04 §三「10.2a 不自主触发」不冲突——人工研判后的回滚是**有决策的**,不是自主放弃。

## 四、落库窗口期接口行为

| 接口 | 窗口期(occupy 在,DB 无) | 落库后 |
|---|---|---|
| 抢号成功页 | occupy Redis 渲染,状态 RESERVED | DB 渲染,字段一致 |
| 我的预约 (列表) | 列出 occupy 中的 rno + 场次摘要 | 列出 DB 记录 |
| 预约详情 | occupy 全字段 + 状态 RESERVED | DB 全字段 |
| 取消预约 | CAS DB 0 行(DB 还没落库)→ **标记 `occupy.cancelled=1`(不删 occupy)** + 写 state_log 空回滚占位 | CAS DB 置 CANCELLED |

### 4.1 窗口期取消:**只标记,绝不删 occupy**(☑ P0 修:原文档自相矛盾)

⚠️ **原缺陷**:原表格取消行写「改走 occupy **删除** + 标记作废,等落库时消费者读标记直接置 CANCELLED」——**occupy 删了标记就不存在**,消费者读不到标记 → 按 RESERVED 落库 → **用户已收到"取消成功",预约却仍然生效**(且名额已消耗、当天不可再约,用户彻底困住)。§五 与 06 §3.1 只说标记不说删,三处口径不一。

**钉死口径**:

```
取消请求(窗口期,DB CAS 返回 0 行)
 ├─ 1. HSET occupy:{rno} cancelled 1        ← 只标记,occupy 保留
 ├─ 2. 单库:INSERT state_log(xid, branch, status=3) ON DUP KEY UPDATE status=3
 │       ← 双通道兜底:标记若因 Redis 丢失而消失,消费者仍能从 state_log 读到"已 Cancel"
 ├─ 3. 不动桶、不删 dup(M1 名额作废)、不删 slot:full
 └─ 4. 返回"取消成功"(状态 CANCELLED,前端由 occupy.cancelled 渲染)
```

`occupy` 的删除**只有两个合法时机**:消费者落库成功后 `DEL`(§五)、10.2a 补偿回滚(04 §三)。**取消路径永不删 occupy。**

> ⚠️ 为何要 state_log 双通道:`occupy.cancelled` 存在 Redis,若在窗口期内 Redis 丢 key(病理态),标记消失 → 消费者按 RESERVED 落库 → 又回到"取消无效"。state_log 在 DB,与消费者阶段2 同库同事务可见,是可靠的第二道。这也是 03 §6.1 把「空回滚占位」列为 state_log 四个写入点之一的原因。

### 4.2 窗口期取消的第二类竞态:**标记晚于消费者检查点**

上面解决的是"标记丢失",还有一类是"标记来得太晚":

```
t1 消费者阶段1 INSERT reservation(status=0)提交
t2 消费者阶段2 读 occupy.cancelled → 无 → 继续按 RESERVED 落 route/event/occupied
t3 用户点取消:CAS DB —— 此时 reservation 已提交,CAS 应当成功 ✅(正常收口)
```

t3 走的是正常 DB CAS 路径,**不是问题**。真正的窄窗是:

```
t1 阶段1 INSERT 提交
t2 用户点取消 → CAS DB —— 但取消服务连的是 ds0/ds1,若恰好读到未同步的连接/事务隔离下不可见 → 返回 0 行
   → 误判为"窗口期" → 只写 occupy.cancelled=1
t3 消费者阶段2 已过检查点(t2 之前读过)→ 按 RESERVED 落库完成 → DEL occupy(标记随之消失)
结果:用户看到"取消成功",DB 里是 RESERVED —— 幽灵有效预约
```

**收口(三道,按成本排序)**:

1. **消费者末尾复查**(主要手段):阶段2 提交后、`DEL occupy` **之前**,再读一次 `occupy.cancelled`;若已置位 → 立即 `CAS status 0→2` + 写 event,再 DEL occupy。成本 = 每条消息多 1 次 HGET,可接受。
2. **取消接口不轻信 0 行**:CAS 返回 0 行时,先 `SELECT status FROM reservation WHERE rno=?`(同一分库),**查到记录说明不是窗口期**(状态已变 → 幂等返回;status=0 却 CAS 失败 → 重试一次 CAS)。只有确实查不到记录才走 Redis 标记路径。这把误判窗口从"CAS 0 行"收窄到"记录真不存在"。
3. **到期状态对账兜底**(06 §4.3):`valid_until<now 且 status=0` → EXPIRED。即便前两道都漏,名额本就不返还(M1),最终状态收敛到 EXPIRED 而非 RESERVED,不产生"能入园的幽灵预约"。

> ⚠️ 三道里 **1 和 2 都必须实现**——只做 1 会漏"消费者已 DEL occupy 之后用户才点取消"(此时 DB 有记录,走正常 CAS,不成问题);只做 2 会漏 t2/t3 的交错。这是 D6 分阶段落库最难的一处竞态,08 §9.2 已标「消费者分阶段跨库事务最易出 bug,必写集成测试」——**这两条就是那个集成测试的主要用例**。

## 五、MQ 消费者落库(D6 分阶段)

```
消费者收到 ReservationCreated
 ├─ 阶段0(前置读,不写库):HGETALL occupy:{rno}
 │     ├─ cancelled=1 → 本条按 status=2(CANCELLED)落库(见下 target_status)
 │     ├─ expired=1   → 本条按 status=3(EXPIRED)落库(06 §3.4 timeout 窗口期标记)
 │     └─ 均无        → target_status = 0(RESERVED)
 │     ☑ 修:cancelled 判定必须在阶段1 **之前**——原文档写在"阶段2 读标记 → 阶段1 改写",
 │        而阶段1 已执行完毕无法回改,是时序不成立的伪码
 ├─ 阶段1:INSERT reservation(分库表,按 user_id 命中 ds0/ds1,status = target_status)
 │     基础设施失败(分库超时/连接异常)→ 抛异常 → 框架重投 N 次 → 耗尽进 DLQ(人工),不触发 10.2a
 │     主键冲突(rno 已存在)→ 幂等,跳到阶段2(可能是上次跑到阶段1 后 crash,须补完阶段2)
 ├─ 阶段2:单库本地事务(reservex_single,@Transactional("singleTxManager")):
 │     ├─ INSERT state_log(xid='rx-'+rno, branch=rno, status=1)   ← 03 §6.1 Try 写入点
 │     │     PK 冲突 → 查已有 status:=3 → 说明窗口期已取消 → CAS reservation 0→2 + 本条转 CANCELLED
 │     ├─ INSERT id_card_route(id_card_hash, slot_date, rno)
 │     │     DuplicateKey(route 冲突,该证已被并发请求约走,属业务事实)
 │     │       → 先 CAS 清阶段1 孤儿 reservation:UPDATE reservation SET status=2
 │     │         WHERE rno=? AND status=0  (语义"未成立作废",M1 不返还故不影响 occupied)
 │     │       → 发 CompensateRollback(执行 10.2a 回滚 Redis)
 │     │       → 写 consumed_event(标记本条已处理)+ ACK 当前消息(防死信循环 → 与 10.2a 无竞态)
 │     ├─ INSERT reservation_event(CREATED 流水)
 │     └─ UPDATE slot_bucket SET occupied = occupied+1 WHERE slot_id=? AND bucket_no=?
 │     基础设施失败 → 抛异常 → 重投 + DLQ(同阶段1,不自主 10.2a)
 ├─ 阶段3(收尾,幂等登记 + 清理,顺序不可换):
 │     ├─ 1. INSERT consumed_event(consumer_group, event_id)   ← ☑ 成功之后才写,见 §5.1
 │     ├─ 2. 复查 HGET occupy:{rno} cancelled → 若已置位:CAS status 0→2 + 写 event(§4.2 收口第1道)
 │     ├─ 3. ZREM pending:persist {rno}
 │     └─ 4. DEL occupy:{rno}
 └─ 阶段4:发 ReminderTrigger(valid-30min) + TimeoutExpire(valid_until) 延时消息
```

### 5.1 `consumed_event` 写入时机:persistence-consumer **成功后写**(☑ P0 修:原两处口径矛盾)

⚠️ **原缺陷**:06 §二 规定「消费者**先**写幂等表,唯一键冲突 → ACK 返回」,而 02/06 §3.1 的流程写「成功 → 记 consumed_event」。两个口径并存,而**按"先写"会永久丢预约**:

```
consumed_event 在 reservex_single,阶段1 INSERT reservation 在 ds0/ds1 —— 跨库非原子
t1 先写 consumed_event 成功(单库)
t2 阶段1 崩(分库超时 / 进程被杀)
t3 消息重投 或 pending-scanner 补投
t4 consumed_event 唯一键冲突 → 按"先写"规则 ACK 跳过
结果:该预约永不落库,Redis 桶已扣、用户已看到成功页 —— 直到 reinject-max 耗尽转人工
```

这直接击穿"不少约"。**按 consumer 分类钉死**:

| consumer | 时机 | 幂等真正靠什么 | 理由 |
|---|---|---|---|
| **persistence-consumer** | **成功后写**(阶段3 步骤1) | `reservation` **主键 rno**(阶段1 冲突即幂等)+ `id_card_route` PK + `state_log` PK | 主体写入自带唯一键,重投安全;先写幂等表反而会吞掉未完成的工作 |
| **rollback-consumer** | 不写(或成功后写) | 10.2a 脚本 `EXISTS occupy` 自幂等 | 脚本本身幂等,重投无副作用 |
| **reminder-consumer** | **发邮件之前写**(06 §3.3) | `consumed_event` **就是唯一防线** | 界外调用(SMTP)无 DB 唯一键可依,先写才能挡重发 |
| **timeout-consumer** | 成功后写 | `CAS status 0→3` 自幂等 | 同 persistence |
| **release-consumer** | 成功后写 | `released 0→1` CAS + 10.3 SET 覆盖 | 同上 |

> **判据(可推广)**:**下游动作本身有唯一键/CAS 可幂等 → 成功后写幂等表(它只是加速跳过,不是正确性来源);下游是界外调用无唯一键 → 必须先写(它是唯一正确性来源)。** 这正是 06 §4.6「界外调用是分水岭」的落地判据,06 §二 的通用表述已按此改为分类表述。

> ⚠️ 阶段1 主键冲突时**不能直接 ACK 跳过**,必须继续跑阶段2 —— 因为"reservation 已存在"可能是上次执行跑完阶段1 后 crash 留下的,阶段2 从未执行。这就是上面「主键冲突 → 跳到阶段2」的原因,漏了这条就是"reservation 有但 route/occupied 缺"的长期漂移(靠 06 §4.3 路由表对账兜,但不该依赖对账做常规收口)。

> ⚠️ D6 关键:reservation 分库,route/event/occupied 在单库,**跨库不能一个本地事务原子**。故分两阶段,靠幂等表 + 对账收口。occupied 的异步滞后由对账自然比对修复。
>
> ⚠️ **10.2a 触发边界(防幽灵预约)**:10.2a **仅**在 route 冲突(业务已判定不可成立)且原消息已 ACK 不会再重投时由 CompensateRollback 驱动。基础设施异常走重投+DLQ+人工,**绝不自主 10.2a**——自主放弃会与 pending-scanner 补投/MQ 重投竞态,致"桶已回补但预约仍落库"的幽灵预约(详见 04 §三·补)。route 冲突前先 CAS 清阶段1 孤儿 reservation,防 B 向对账误判"reservation 在 occupy 删"而重建 occupy 与 10.2a 冲突。

## 六、为何这套够可靠(B 方案诚门口径)

- **可重试**:MQ 重投 + pending-scanner 补投双通道。
- **可补偿**:创建失败 → 10.2a 原子撤销 Redis(桶+1/删occupy/删dup/ZREM pending)。
- **可对账**:对账任务比对 `redis_occupied = capacity − Σ桶余量` vs `db_occupied = Σ slot_bucket.occupied` vs `reservation_cnt`,差异收口。
- **降一档场景(诚实)**:Redis 崩 + AOF 丢 → 实时号源状态全丢,只能回 DB `occupied` 近似重建,窗口期 occupy 记录也丢。单机 AOF 下小概率,代价(牺牲招牌)不对称,故接受。

## 七、为何不用事务消息(决策依据,Q1-B)

面试常被追问"既然怕 Redis↔MQ 不一致,为何不用 RocketMQ 事务消息一把解决"。决策依据三层:

1. **事务消息的原子边界不对位**:RocketMQ 事务消息(半消息 + 本地事务 + 回查)解决的是「本地 DB 事务 ↔ 消息发送」的一致性——即"DB 写成功则消息必发,DB 回滚则消息不发"。而本项目抢号的关键原子边界在 **Redis Lua 扣减 ↔ 消息发送** 这一段:Redis 扣减发生在 MQ 发送之前,且 Redis 不是 DB 事务的一部分,**事务消息的本地事务回调管不到 Redis 这一步**。扣减已发生、消息才发,二者之间天然不是原子的——事务消息买不到这一段的可靠性。

2. **事务消息反而逼出"同步落主表"**:事务消息要求本地事务在 `executeLocalTransaction` 回调里同步执行。若用它落 `reservation` 主表,则抢号链路退化成"Redis 扣减 + 同步落主表"——DB 单行 insert 回到热路径,牺牲项目最大招牌「抢号只动 Redis,DB 异步刷扛写峰值」。换回的唯一收益是"用户抢完 DB 立刻有记录",而该收益用 Redis `occupy` 兜即可达(§四)。

3. **可靠性增益其实有限,代价不对称**:事务消息并不能消除 Redis↔MQ 的不一致窗口,仍需补偿 + 对账兜底(06)。既然该段本就要靠"可重试 + 可补偿 + 可对账"给到,事务消息的边际增益不足以抵消"牺牲招牌 + DB 写入回热路径"的代价。

故选 Q1-B(普通消息 + 补偿 + 对账),诚实口径:非严格原子,但在可重试/可补偿/可对账前提下达可控最终一致;Redis 丢失场景降一档,小概率+代价不对称接受。
