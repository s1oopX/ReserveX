# 03 · 数据库设计

> 分库分表演示形态:单 MySQL 实例多 schema。`reservex_ds0` / `reservex_ds1` 分库(用户/预约按 user_id 分);`reservex_single` 单库存路由/去重/号源/对账/流水/循环明细(全库唯一约束所在地)。

## 一、库划分

| schema | 存什么 | 为何 |
|---|---|---|
| `reservex_ds0` / `reservex_ds1` | `user`、`reservation`、`reservation_transition_outbox`(均按 user_id 对齐分库) | 高可用+水平扩展;查"我的预约"按 user_id 单库命中 |
| `reservex_single` | 全局身份/路由、`registration_outbox`、号源、状态/事件、对账、卡单、死信、核销与审计表 | 唯一约束不能分库(本地索引失效);号源/对账/流水全库视角 |

> ⚠️ D6 的根因:reservation 在分库,route/event/occupied 在单库,**跨库不能一个本地事务原子**。消费者落库分两阶段(见 02 §五)。

### 1.1 单库表用独立数据源,**不用广播表**(口径钉死)

⚠️ 早先 §八 曾写"单库表配成广播表(每个库一份)",**作废**。理由:

- 广播表把同一行写入 ds0 与 ds1 两份,无 XA 时**两库写入本身非原子**;
- 唯一约束语义退化成"每个库各自唯一",`id_card_route`/`email_route` 的全局唯一性**不再成立**——而这是 M6 存在的全部理由;
- D6「跨库不能一个本地事务原子」的推导前提被推翻(广播表下单库侧本身就已是跨库写)。

**落地**:ShardingSphere 配 **三个数据源** `ds0`/`ds1`/`single`。分片规则只管 `user`/`reservation`;`reservex_single` 的表**不纳入分片规则**,通过独立 `DataSource` + 独立 MyBatis mapper 包(`mapper/single/`)访问,单库侧本地事务用 `@Transactional(transactionManager="singleTxManager")` 显式指定。

> 代价(诚实):单库表与分库表**无法 join**(本就不该 join,跨库 join 是反模式);两个 TransactionManager 需显式指定,漏写 `transactionManager` 会挂到默认库上——**编码红线,须写集成测试覆盖**。

## 二、user 表(分库)

```sql
CREATE TABLE `user` (
  `user_id`            BIGINT       PRIMARY KEY,             -- Snowflake
  `email`              VARCHAR(128) NOT NULL,
  `phone`              VARCHAR(32)  NOT NULL,
  `password`           VARCHAR(128) NOT NULL,                -- BCrypt 加盐(盐在 hash 串内,无需列)
  `id_card_ciphertext` VARBINARY(256) NOT NULL,              -- AES-256-GCM,**存 iv(12B)+ct+tag(16B) 拼接**,见 §2.1
  `id_card_key_id`     VARCHAR(16)  NOT NULL,                -- ☑ 第十三轮补:加密时的密钥版本(= reservex.aes.key-id)
                                                             --    无此列则"支持轮换"是空话:换 key 后旧密文永久解不开
  `id_card_hash`       CHAR(64)     NOT NULL,                -- SHA-256(**全局固定 pepper** + 明文),见 §2.1
  `id_card_masked`     VARCHAR(32)  NOT NULL,                -- 脱敏展示
  `role`               VARCHAR(16)  NOT NULL DEFAULT 'USER', -- 注册接口写死 USER
  `status`             TINYINT      NOT NULL DEFAULT 0,      -- 0正常 1封禁
  `create_at`          DATETIME     NOT NULL,
  `update_at`          DATETIME     NOT NULL,
  KEY `idx_hash` (`id_card_hash`),
  KEY `idx_email` (`email`)                                  -- ☑ 第十三轮补:登录第 2 跳按 email 回查,见 §2.2
);
-- 唯一约束不在此表(分库失效),在单库 email_route/phone_route 承担
```

### 2.1 加密与哈希的**存储口径**(☑ 第十三轮 P0 补:原只写算法名,没写怎么存)

⚠️ **原缺口**:DDL 注释写 `AES-256-GCM(可逆,授权解密)` 与 `SHA-256(加盐)`,08 §七 yml 写 `aes.key-id: aes-v1  # 支持轮换`。三处都只有**算法名与承诺**,而落地必需的三件事全空:

| 缺什么 | 不定的后果 |
|---|---|
| **GCM 的 IV(nonce)存哪** | GCM 解密**必须**有加密时那 12 字节 IV。若代码里写死一个常量 IV → 同一明文得同一密文,**GCM 退化成可比对的确定性加密**,且 IV 重用在 GCM 下会泄露认证密钥流(这是 GCM 唯一的致命误用)。若随机生成而不存 → **永久无法解密**。 |
| **hash 的"盐"是什么盐** | 写「加盐」但 `id_card_hash` 要**跨用户可比对**(`id_card_route` PK 靠它做一人一天一次)。若用**每行随机盐**,同一身份证在两个用户下得到不同 hash → M6 全局唯一直接失效。这里要的其实是 **pepper(全局固定密钥),不是 per-row salt**——两个词混用是安全设计里最常见的踩雷。 |
| **`key_id` 没有列** | `key-id: aes-v1 # 支持轮换` 是**空承诺**:轮换到 `aes-v2` 后,存量密文用 v1 加密而解密时拿 v2 → `AEADBadTagException`,所有历史身份证**永久不可读**,且报错发生在"授权解密"这个低频路径,可能上线数月后才被发现。 |

**钉死(三条)**:

1. **密文格式 = `iv(12B) || ciphertext || tag(16B)`,整块存 `VARBINARY`**。IV 每次加密**随机生成**,与密文同行存储(IV 不是秘密,只要求不重用)。长度核算:身份证 18 字符 → ct 18B + iv 12 + tag 16 = **46B**,`VARBINARY(256)` 余量充足(留给未来护照等更长证件)。
   - 落地:`crypto/` 模块只暴露 `encrypt(plain) -> byte[]` / `decrypt(bytes, keyId) -> plain` 两个方法,**IV 的生成与拼接封在里面**,调用方拿不到 IV 也就无法误传常量。
2. **`id_card_hash = SHA-256(pepper || 明文)`,pepper 是全局固定值,来自独立环境变量 `ID_HASH_PEPPER`**(与 `AES_KEY`、`QR_HMAC_KEY` 三者分离,同 07 §3.4.1 的密钥分离纪律)。
   - **不是 per-row salt**——per-row 盐会让跨用户比对失效(见上表)。
   - **pepper 永不轮换**(v1):它进了 `id_card_route` 的 PK,轮换等于全表 hash 作废,需要一次全量重算 + PK 重建。**这条要在文档里认下**,别写"支持轮换"。
   - ⚠️ 因为不加 per-row 盐,`id_card_hash` 在**没有 pepper 的攻击者面前**仍然是彩虹表可攻的(身份证空间约 $10^{17}$ 但地区码+生日结构使实际空间小得多)。**pepper 泄露 = hash 可逆**,故它与 AES 密钥同级保护,不入代码、不入 git、只走环境变量。这是诚实口径,面试被追问"SHA-256 身份证不是能撞出来吗"要答得出"靠 pepper 保密,不靠算法"。
3. **`id_card_key_id` 列必建**,加密时写入当前 `reservex.aes.key-id`,解密时**按行取该列**去密钥集里找对应 key(yml 需从单 key 改为 `keys: {aes-v1: ${AES_KEY}, ...}` 形式,与 `qr.accepted-key-ids` 同构,08 §七已改)。轮换流程:加新 key → 改 `key-id` 为新版本(新写入用新 key)→ 旧行按各自 `key_id` 继续可解 → 需要时后台批量重加密。**不做重加密也不影响可用性**,这才叫"支持轮换"。

> ⚠️ **`id_card_masked` 不能由密文派生**,必须在注册时从明文算好落库(如 `110***********1234`)。原因:列表页脱敏展示是高频读(07 §2.2 窗口期列表也用它),若每次展示都要解密 → 每条列表行一次 AES + 拿到明文进内存,既慢又扩大明文暴露面。**冗余存脱敏串 = 让绝大多数读路径根本不接触密钥。**
>
> ⚠️ **明文身份证在整个系统里只出现在两处**:注册请求体(HTTPS 传输,不落日志)、授权解密的返回值(需 `audit_log` 记 `action='DECRYPT_IDCARD'`)。**抢号/核销/取消/对账全链路只用 `id_card_hash` 与 `id_card_masked`**,一次都不需要解密——这是 M6 用 hash 做唯一键(而非用密文)的真正收益,别在实现时图省事去 join 明文。

### 2.2 登录的读路径(☑ 第十三轮 P0 补:原只定义了注册的写路径)

⚠️ **原缺口**:§八·补 详尽定义了注册的**跨库两写**,但**登录一次都没被定义过**。而登录在本项目里是一个结构性难题:用户输入的是 **email**,`user` 表却按 **`user_id`** 分片 —— ShardingSphere 拿 email 无法定位分片,裸写 `WHERE email=?` 会触发**全分片广播查询**(ds0+ds1 都扫一遍再归并)。后果不是报错,而是:

- 每次登录 2 倍 DB 查询,且 `email` 在分库上**无唯一约束**(§二注释已声明),广播查询理论上可能返回两行 → 代码若 `getOne()` 会抛 `TooManyResultsException`,若 `list().get(0)` 则**随机登进其中一个账号**;
- 分片数从 2 涨到 N 时登录耗时线性劣化,而这恰是分库分表本该避免的反模式;
- 09 §一 的 token 池脚本要**批量登录 2000 用户**,广播查询会让这一步成为压测前置的瓶颈,并掩盖真实登录性能。

**钉死(两跳,与注册反向对称)**:

```
POST /api/sessions {email, password}
 ├─ 1. 单库:SELECT user_id FROM email_route WHERE email=?        ← PK 命中,route 表就是"email→分片"的路由器
 │       查无 → 返回 `LOGIN_FAILED`(**不区分"邮箱不存在"与"密码错"**,防用户枚举)
 ├─ 2. 分库:SELECT * FROM user WHERE user_id=?                   ← 分片键命中,单库单行
 │       查无 → 这是**孤儿 route**(§八·补 步骤 2 失败留下的)→ 返回 `LOGIN_FAILED` + 告警
 │              ⚠️ 不要在此处自愈:登录时手上只有 password,拿不到 id_card,补不出完整 user 行
 ├─ 3. BCrypt.checkpw(输入, user.password) → 失败返 `LOGIN_FAILED`
 ├─ 4. user.status=1(封禁)→ 返 `ACCOUNT_BANNED`
 └─ 5. Sa-Token 签发 access+refresh,`role` 从 **DB 行**取(不信任任何前端传值)
```

> ⚠️ **这就是 route 表的第二重价值**:它原本是为"分库下唯一约束失效"而存在(§三),现在同时充当**登录的分片路由器**。同理,若 v2 加"手机号登录",走 `phone_route` 同一模式,**不新增机制**。
>
> ⚠️ **禁止在 `user` 表上按 `email` 查询**(除运维排查)。编码红线:MyBatis mapper 里凡是 `WHERE email=` 出现在 `mapper/sharding/` 下即是错的,该查询属于 `mapper/single/` 的 route 表。
>
> ⚠️ **`idx_email` 仍要建**(见 DDL):不是给登录用,是给**孤儿排查与运维**用(`SELECT * FROM user WHERE email=?` 在单个 schema 内直查)。没有它,排查时的全表扫会打在生产库上。

## 三、全局路由表 + 去重表(单库)

```sql
CREATE TABLE `email_route` (
  `email`   VARCHAR(128) PRIMARY KEY,
  `user_id` BIGINT       NOT NULL,
  `create_at` DATETIME   NOT NULL
);

CREATE TABLE `phone_route` (
  `phone`   VARCHAR(32)  PRIMARY KEY,
  `user_id` BIGINT       NOT NULL,
  `create_at` DATETIME   NOT NULL
);

-- 一人一天配额去重(第二道防线,单库唯一索引才有效)
CREATE TABLE `id_card_route` (
  `id_card_hash`   CHAR(64) NOT NULL,                       -- 明文不入库
  `slot_date`      DATE     NOT NULL,
  `reservation_no` BIGINT   NOT NULL,
  `create_at`      DATETIME NOT NULL,
  PRIMARY KEY (`id_card_hash`, `slot_date`)                 -- 结构上即"一天一次",见 §3.1
);
```

### 3.1 配额语义:v1 **固定 1 次/天**(M7 措辞修正)

⚠️ **原 M7 写「默认 1 次/天,**可配**」与本表 PK + Lua `SET NX dup`(04 §10.1)结构性冲突**:PK `(id_card_hash, slot_date)` 与 `SET NX` 都只能表达"一天至多一条",把 `daily-per-idcard` 配成 2 时,**两道防线同时失效**——Lua 第一道直接返回 -1 拒掉第二次(用户根本约不到第 2 个),而若强行放开 dup,第二次必然撞 route PK → 走 route 冲突 → 10.2a 回滚,用户看到"抢号成功后又失败"。

**裁定(2026-08-09)**:v1 **固定 1 次/天,不可配**。

- `application.yml` 的 `reservex.quota.daily-per-idcard` **保留但校验**:启动时 `!= 1` 直接 fail-fast 拒绝启动(`@PostConstruct` 断言),避免"配了不生效"的静默错误——这比删掉配置项更安全,因为运维会先看到明确报错。
- 00 §M7 措辞改为「**固定 1 次/天**;多次配额是 v2 演进」。
- **v2 真支持 N 次/天的改法**(留口子,v1 不做):PK 改 `(id_card_hash, slot_date, reservation_no)` + 加 `uk` 或计数校验;`dup` 从 `SET NX` 改为 `INCR` 后比对上限(超限则 `DECR` 回退并返回 -1)。同时 04 §三·补·2「route 冲突正常不可能触发」的论证需重写(N>1 时 route 冲突从"病理态"变成"并发常态")。

> ⚠️ 面试口径:被问"配额可配吗"答「v1 结构上锁死 1 次/天(route PK + Lua SET NX 双防线都是一天一条的语义),真要可配需同时改 PK 语义和 Lua 判重方式——这是 v2 演进项,不是改个配置值的事」。**别答"配置项改一下就行"**,那会被追问出上面这条链子。

## 四、号源表(单库)

```sql
-- ☑ 第十三轮 P0 补:场次模板表(原全 docs 引用四处、定义零处,详见 §4.0)
CREATE TABLE `slot_template` (
  `template_id`   BIGINT   PRIMARY KEY,           -- Snowflake
  `slot_hour`     INT      NOT NULL,              -- 时段起始小时(9/11/14/16)
  `duration_min`  INT      NOT NULL DEFAULT 120,
  `capacity`      INT      NOT NULL DEFAULT 50,
  `bucket_count`  INT      NOT NULL DEFAULT 10,
  `release_offset_min` INT NOT NULL DEFAULT -1440, -- 放号时点相对 slot_date 00:00 的偏移(分钟)
                                                   --   -1440 = 前一日 00:00;见 §4.0 为何存偏移不存时刻
  `enabled`       TINYINT  NOT NULL DEFAULT 1,     -- 0 停用(生成任务跳过,不删行:历史 slot 仍引用它)
  `create_at`     DATETIME NOT NULL,
  `update_at`     DATETIME NOT NULL,
  `version`       INT      NOT NULL DEFAULT 0,
  UNIQUE KEY `uk_hour` (`slot_hour`)               -- v1 一个 hour 一个模板(不做多套模板并存)
);

CREATE TABLE `slot` (
  `slot_id`      BIGINT   PRIMARY KEY,
  `template_id`  BIGINT   NULL,                  -- ☑ 补:来源模板(手工建的 slot 为 NULL);只做溯源不做外键
  `slot_date`    DATE     NOT NULL,
  `slot_hour`    INT      NOT NULL,            -- 时段起始小时
  `valid_until`  DATETIME NOT NULL,            -- ☑ P0 补:时段截止(= slot_date + slot_hour + duration_min)
                                               --    抢号前置校验/占用有效期/到期扫描/slot:meta 均依赖此字段
  `duration_min` INT      NOT NULL DEFAULT 120,-- ☑ 时段时长(分钟),valid_until 由它派生后落库固化
  `capacity`     INT      NOT NULL DEFAULT 50, -- 生态承载量,管理端配
  `bucket_count` INT      NOT NULL DEFAULT 10, -- 分桶数(=1 不分桶),已放号禁改
  `released`     TINYINT  NOT NULL DEFAULT 0,  -- 0未放 1已放
  `release_at`   DATETIME NOT NULL,            -- 放号时间点
  `version`      INT      NOT NULL DEFAULT 0,  -- 乐观锁
  UNIQUE KEY `uk_date_hour` (`slot_date`, `slot_hour`)  -- ☑ P1 补:挡"次日slot生成"任务重跑造重复场次
);

CREATE TABLE `slot_bucket` (
  `slot_id`   BIGINT NOT NULL,
  `bucket_no` INT    NOT NULL,                 -- 0 ~ bucket_count-1
  `total`     INT    NOT NULL,                 -- 见 §4.1 余数分摊,非简单 capacity/bucket_count
  `occupied`  INT    NOT NULL DEFAULT 0,       -- 累计成功预约数(含取消/过期不返还故不减回)
  PRIMARY KEY (slot_id, bucket_no)
);
```

### 4.0 `slot_template`:原「引用四处、定义零处」(☑ 第十三轮 P0 补)

⚠️ **原缺口**:「模板」这个词在四个地方被当作既存事实使用,但**全 docs 没有任何表、字段或结构承载它**:

| 引用处 | 原文 | 原状 |
|---|---|---|
| 07 §3.1 场次发布闭环 | 「ADMIN 创建模板 → 次日 slot 生成任务」 | 模板存哪儿?未定义 |
| 06 §4.3 次日 slot 生成 | 检测条件「**按模板**次日无 slot 行」、修复动作「**按模板** INSERT slot」 | 任务读什么?无表可读 |
| 07 §四 管理端页面 | 「场次模板」独立一页(与「场次日历」并列) | 该页 CRUD 什么?无字段 |
| 08 §七 yml | `reservex.slot.template-hours: [9,11,14,16]` + `default-capacity` / `default-bucket-count` / `default-duration-min` | **用四个静态配置项冒充了模板表** |

**为什么"用 yml 冒充"不成立**(这是本条的关键,不是洁癖):

1. **运行期改容量不需要重启**。模板默认值只用于初始化；运营调整已生成场次走带 `ETag`/`If-Match` 的 `PATCH /api/admin/slots/{slotId}`，避免并发覆盖。而 07 §四 同时提供「场次模板」管理页和「场次日历」增容，模板只影响未来生成的场次。
2. **`template-hours` 是数组,而每个时段的容量本该不同**。上午 9 点与下午 16 点的生态承载量凭什么相同?yml 结构上只能给一个全局 `default-capacity`,**表达不了"按时段差异化"**——而这恰是"生态承载量"这个业务概念的全部意义。
3. **停用一个时段无处表达**。雨季停开 16 点场,yml 只能把 `16` 从数组里删掉;但**已生成的历史 slot 仍需溯源它来自哪个模板**,删数组等于丢历史。故需要 `enabled` 而非"从列表里删"。
4. **`release_at` 算不出来**。`slot` 的 `release_at NOT NULL`,而 06 §4.3 的生成任务必须给出它。yml 里没有任何项能表达"放号时点",这是一处**纯粹的 NOT NULL 无填充路径**(违反 README 纪律 #4)。

**裁定**:建 `slot_template` 表(见上 DDL);yml 的四个 `default-*` 与 `template-hours` **降级为"表为空时的初始化种子"**,只在 `init.sql` 里用一次(08 §4.1),运行期一律读表。

**`release_offset_min` 为何存偏移不存时刻**:模板是**跨日复用**的,存绝对时刻(如 `2026-08-09 10:00`)对次日无意义。存偏移则生成任务算:

```
release_at = slot_date 00:00 + release_offset_min 分钟
           例:slot_date=2026-08-10, offset=-1440 → 2026-08-09 00:00(前一日零点放号)
               offset=-840  → 2026-08-09 10:00(前一日 10:00 放号,对应 07 §2.3 的"10:00 开放预约")
valid_until = slot_date + slot_hour:00 + duration_min      (§4.1 固化)
```

> ⚠️ **偏移必须为负或 0**:`release_at >= valid_until` 的模板会生成"放号时该场次已结束"的死场次,发布对账(06 §4.3)会把它永久列入「发布异常」红色告警且补放无意义(06 §4.8 已有此例外口径)。**建模板时校验 `release_offset_min < slot_hour*60`**,否则拒绝保存(错误码沿用 07 §3·补·2 的参数校验分支)。

**生成任务(06 §4.3「次日 slot 生成」)的完整读写口径**:

```
每日 gen-cron(02:30)→ 抢 lock:slotgen:{date} → CHECK done:slotgen:{date}
  → SELECT * FROM slot_template WHERE enabled=1                    ← 读表,不读 yml
  → 逐 template:
       slot_date = today + gen-days-ahead
       INSERT slot(slot_id=Snowflake, template_id, slot_date, slot_hour=t.slot_hour,
                   duration_min=t.duration_min, capacity=t.capacity,
                   bucket_count=t.bucket_count, released=0,
                   release_at=派生, valid_until=派生)
         └─ uk(slot_date, slot_hour) 冲突 → 已生成,跳过该 template(不是整批退出)
       INSERT slot_bucket × bucket_count(余数规则 §4.2)
       投递 SlotRelease(event_id='sr-'+slot_id, deliverTime=release_at)
  → SET done:slotgen:{date}
```

> ⚠️ **uk 冲突要"跳过该 template 继续下一个",不是"整批 return"**:四个模板里第 2 个已存在(上次跑到一半 crash)时,整批退出会让第 3、4 个时段**永远不生成**——而 marker 未写、锁已释放,下个周期还会再撞同一个点,形成永久卡死。这与 06 §3.1 阶段1「主键冲突继续跑阶段2」(红线 #10)是**同一条纪律**:幂等跳过的粒度必须是"这一项",不是"这一批"。
>
> ⚠️ **模板改动不影响已生成的 slot**:`slot` 把 `capacity`/`bucket_count`/`duration_min` **复制**了一份而非引用 `template_id`。这是刻意的——已放号 slot 的 `bucket_count` 禁改(§4.3 hash 路由错位),若运行期从模板读取,改模板就等于隔空改已放号 slot 的桶数,直接破坏 §九 的锁定约束。**`template_id` 只做溯源,任何链路都不许通过它去取值。**
>
> ⚠️ **不建外键**:`slot_template` 与 `slot` 同在 `single` 库,技术上可建 FK,但停用/删除模板时会被 FK 挡住,而业务上"停用模板"本就不该影响历史 slot。用 `enabled` + `template_id NULL` 表达,比 FK 更贴业务。


### 4.1 `valid_until` 是**固化字段**,不是运行时派生(钉死)

`valid_until` 在**生成 slot 行时**由 `slot_date + slot_hour:00 + duration_min` 算出并落库,此后:

- 未放号:可随 `slot_hour`/`duration_min` 改而重算;
- **已放号:锁定**(与 §九 一致)。Redis `slot:meta.valid_until` 与 DB 同源,放号时一次性写入。

> ⚠️ 为何不运行时派生:抢号前置校验(05 §1.2)、Lua 写 occupy(04 ARGV[8])、到期对账(06 §4.3)三处都要它,任一处派生口径不一致就会出现"A 处认为已结束、B 处认为可约"。固化成字段 = 单一真理源。

### 4.2 桶容量分摊(余数规则,`C = A+R+V+X` 不变量前提)

`capacity` 不能整除 `bucket_count` 时(如 55/10),简单 `capacity/bucket_count` 会**丢余数**,导致 Σ桶初值 < capacity,库存不变量(01 §四)与库存对账(06 §4.3)永久带固定差值。

**规则(放号 10.3 与增容 §六 统一)**:

```
base = capacity / bucket_count      (整除部分)
rem  = capacity % bucket_count      (余数)
bucket[i].total = base + (i < rem ? 1 : 0)     -- 前 rem 个桶各多 1
```

即 capacity=55, bucket_count=10 → 桶 0~4 各 6,桶 5~9 各 5,Σ=55 ✅。

**增容同理**:`delta` 分摊 `d_base = delta/bucket_count`,`d_rem = delta%bucket_count`,前 `d_rem` 个桶多 1。故 10.3/增容 Lua **不能对所有桶传同一个 ARGV 值**,须逐桶传值(见 04 §四/§六已改)。

### 4.3 选桶路由函数(docs 原隐性缺口,钉死)

```
bucket_no = (hash(reservation_no) & 0x7fffffff) % bucket_count
```

- **用 `reservation_no` 而非 `user_id`**:user_id 分布长期固定,热点用户会永久打同一桶;rno 每次新生成 → 天然均匀,压测"各桶余量分布均匀"(09 §三)才有意义。
- **借桶顺序**:命中桶余量 ≤0 时,从 `bucket_no+1` 起**环形**扫 `bucket_count-1` 个桶(`(bucket_no+i) % bucket_count`),而非固定从 0 扫——固定从 0 扫会让低号桶被反复借空、余量分布倾斜。
- **这就是「`bucket_count` 已放号禁改」的依据**(§九):改桶数 → 同一 rno 的 hash 落点变化 → 已占用的桶与新路由错位,借桶扫描漏桶。

### 6.1 `state_log` 写入点(☑ P1 补:原 docs 定义了表但全链路无写入点)

⚠️ **原缺口**:01 §五/§六 用 state_log 讲 TCC 三防、06 §4.3 的 B 向对账检测条件写「state_log Try 未 Confirm」,但 02 §五 / 06 §3.1 的消费者只写 `route/event/slot_bucket`,**从不写 state_log** → B 向对账检测条件恒为空,三防表是纯叙事。**裁定:保留表,补齐写入点。**

`xid` 生成规则:`'rx-' + reservation_no`(单体无全局事务协调者,rno 已全局唯一;`branch_id = reservation_no`,单分支)。

| 阶段 | 写入者 | 动作 | 幂等保证 |
|---|---|---|---|
| **Try** | persistence-consumer 阶段2(**不在抢号热路径**) | `INSERT state_log(xid, branch_id, status=1)` | PK `xid` 冲突 → 说明已 Try 过,跳过(与消息重投幂等一致) |
| **Confirm** | 核销服务(CAS `status 0→1` 成功后) | `UPDATE state_log SET status=2 WHERE xid=? AND status=1` | 受影响 0 行 = 已 Confirm/已 Cancel,幂等 |
| **Cancel** | 取消服务 / timeout-consumer / route 冲突清孤儿 | `UPDATE state_log SET status=3 WHERE xid=? AND status IN (0,1)` | 同上 |
| **空回滚占位** | 窗口期取消(DB 还没 reservation)时 | `INSERT state_log(xid, branch_id, status=3) ON DUPLICATE KEY UPDATE status=3` | Try 后到时查到 status=3 → **拒绝 Try**(这才是"空回滚/悬挂"防护真正生效的地方) |

> ⚠️ **关键设计**:Try 写在**消费者阶段2**而非抢号线程内——抢号只动 Redis(Q1-B 招牌)不能加 DB 写。代价:窗口期内 state_log 无记录,故窗口期取消走上表第 4 行「空回滚占位」,消费者阶段2 的 Try `INSERT` 撞 PK 后须**查 status,若为 3 则整条消息转为落 CANCELLED**(与 02 §五 的 `occupy.cancelled` 标记双通道互为兜底,标记丢了还有 state_log)。
>
> ⚠️ 与 `reservation_event` 的分工不变:state_log 管**事务边界**(能否推进),reservation_event 管**业务审计**(谁改了什么)。两表都在单库,与阶段2 同一本地事务提交。

## 八·补 注册链路的跨库两写(☑ P1 补:与 D6 同构但原 docs 漏了)

⚠️ **原缺口**:`user` 在分库(§二)、`email_route`/`phone_route` 在单库(§三),注册**必须跨库两写**——与 D6 消费者落库是同一个问题,但全 docs 没给注册的口径。裸写的后果:

- route 写成功 + user 写失败 → **邮箱/手机号被永久占用且无对应账号**,该用户永远注册不上(且客服无从排查);
- user 写成功 + route 写失败 → 账号存在但唯一性无保护,同邮箱可注册第二个账号 → M6 全局唯一失效。

**落地顺序(先占位后落主体 + 补偿)**:

```
注册请求(email/phone/password/id_card)
 ├─ 1. 单库本地事务:INSERT email_route + INSERT phone_route  (user_id 用预生成的 Snowflake)
 │     任一 DuplicateKey → 事务回滚 → 返回"邮箱/手机号已注册"(不产生任何脏数据)✅
 ├─ 2. 分库:INSERT user(user_id 命中 ds0/ds1)
 │     成功 → 注册完成
 │     失败(基础设施异常/超时)→ 有限重试
 │        └─ 仍失败 → 补偿:DELETE email_route/phone_route WHERE user_id=?(单库本地事务)
 │              补偿也失败 → 记 audit_log + 告警,由「孤儿 route 清理任务」收口
 └─ 3. 幂等:同一 request_id 重复提交 → route PK 冲突 → 查 route.user_id 对应 user 是否存在
        ├─ 存在 → 幂等返回成功(重复提交)
        └─ 不存在 → 说明是上次失败留下的孤儿 → 复用该 user_id 重试步骤 2(自愈)
```

**为何先 route 后 user**(与 D6 的"先分库后单库"相反,刻意):

- route 是**唯一性守卫**,必须先抢占才能防并发同邮箱注册;若先写 user,两个并发请求都能写成功 user,再抢 route 时一个失败 → 留下一个无 route 的孤儿 user(比孤儿 route 更难清:user 已能登录但唯一性无保护)。
- 孤儿 route(有 route 无 user)**危害可控且可自愈**:步骤 3 的"复用 user_id 重试"让同一人再点一次注册就自动修复;而孤儿 user 无法自愈。
- `user_id` **预生成**(Snowflake 在步骤 1 之前生成),使 route 与 user 用同一 id,补偿/自愈可按 user_id 精确定位。

**孤儿 route 清理任务**(补 06 §4.3 任务清单,非核心级):

| 任务 | 分级 | 周期 | 检测条件 | 修复动作 | 幂等键 |
|---|---|---|---|---|---|
| 孤儿 route 清理 | 非核心 | 1h | `email_route.user_id` 对应分库 `user` 不存在 **且 `create_at` 早于 10min**(避开在途注册) | DELETE route(或告警后人工) | `DELETE WHERE user_id=? AND NOT EXISTS user`,天然幂等 |

> ⚠️ **`create_at` 早于 10min 的守卫必须有**,否则会删掉正在步骤 1→2 之间的在途注册的 route,导致并发注册穿透唯一性。这也是 §三 的 route 表补 `create_at` 字段的原因。
>
> 面试口径:「分库下唯一约束失效的解法在本项目出现**两次同构**——注册(email/phone route)和预约(id_card_route),都是'单库路由表抢占 + 主体分库写 + 失败补偿 + 孤儿清理'。区别在方向:注册先占位后写主体(唯一性优先),预约先写主体后占位(D6,因主体在分库且已有 Redis dup 做第一道)。」这是 10 §1.2「两处同构解法」的真实落地。

### 9.1 `slot_template` 的变更约束(☑ 第十三轮补)

模板改动**只影响此后生成的 slot**,已生成的一律不动(§4.0 已述"复制而非引用")。故模板侧约束比 slot 宽松得多:

| 字段 | 可否改 | 备注 |
|---|---|---|
| `capacity` / `duration_min` / `release_offset_min` | 随时可改 | 次日生成起生效;**改前提示运营"不影响已生成场次"**,否则会以为改了今天的容量 |
| `bucket_count` | 随时可改 | 模板层无 hash 路由问题(§4.3 的禁改只针对已放号 slot) |
| `slot_hour` | 可改,但撞 `uk_hour` 则拒 | 等价于"换一个时段",老时段的历史 slot 保持 `template_id` 指向不变 |
| `enabled` | 随时切 | 置 0 = 次日起不再生成该时段;**不删行**(历史 slot 的 `template_id` 仍要能解析) |
| 删除模板 | **禁止硬删**,只允许 `enabled=0` | 硬删会让历史 slot 的 `template_id` 变悬空引用,管理端「场次日历」点进去溯源即 500 |

> ⚠️ 管理端「场次模板」页保存时的两条校验:① `release_offset_min < slot_hour*60`(§4.0,否则生成死场次);② `capacity >= bucket_count`(否则余数规则下会出现 `total=0` 的桶,该桶永远借不出名额,虽不错但浪费一次 Lua 借桶扫描)。两条都在服务端校验,不只前端。
