# 09 · 压测与验收

> 压测靠真数据撑简历指标,引用必带环境。验收矩阵不只看吞吐,更看正确性(不超卖/不重复/库存守恒)。

## 一、工具与前置:token 池

固定单 token 压测会让「一人一天配额」规则把所有请求挡成拒绝,测的是拒绝速度不是抢号链路。正确做法:

```bash
# 1. 批量注册 2000 测试用户(脚本调注册接口,测试环境关闭验证码)
# 2. 批量登录导出 token 到 tokens.txt(每行一个)
# 3. wrk Lua 随机取 token
```

> ⚠️ 2000 用户每人每天 1 次配额:单 slot 50 号,2000 人抢只有 50 成功、其余 1950 被 dup/售罄拒。要测「成功链路」须 2000 个不同 id_card + 分配到不同 slot_date,或压测前重置 dup(测试环境脚本)。否则成功预约数恒等于 capacity,借桶/分布指标需靠多 bucket 多 slot 设计。

## 二、压测脚本

```lua
-- stress-test/scripts/grab.lua
math.randomseed(os.time())
local tokens = {}
for line in io.lines("stress-test/scripts/tokens.txt") do
    tokens[#tokens + 1] = line
end

request = function()
    local t = tokens[math.random(#tokens)]
    return wrk.format("POST", "/api/reservations", {
        ["Authorization"] = "Bearer " .. t,
        ["Content-Type"]  = "application/json"
    }, '{"slotId": 101}')
end
```

> ⚠️ **HTTP 2xx 不等于每个请求都抢号成功**:创建成功是 `201 + OK`，售罄、配额冲突、限流和降级分别使用 `409/429/503`，且都保留 JSON `code`。压测必须解析 body，不能只看 wrk 的吞吐或 `Non-2xx responses`:
>
> ```lua
> local ok, full, quota, other = 0, 0, 0, 0
> response = function(status, headers, body)
>     if     body:find('"code":"OK"')          then ok    = ok + 1
>     elseif body:find('"code":"SLOT_FULL"')   then full  = full + 1
>     elseif body:find('"code":"QUOTA_USED"')  then quota = quota + 1
>     else   other = other + 1 end
> end
> done = function() -- 打印四项,ok 必须 == capacity(§三 矩阵)
> end
> ```
>
> 漏了这段,§三 的「成功预约数 = capacity」「超卖数 0」两条**根本无从断言**——那是本项目验收的底线两条。

```bash
wrk -t8 -c2000 -d30s -s stress-test/scripts/grab.lua http://localhost:8080
```

## 六、故障注入测试

主动模拟(B 方案降一档场景须覆盖):
- Redis 主切换/重启(AOF 丢失)→ 验证降级表 + DB occupied 近似重建
- Lua 执行后客户端超时 → pending-scanner 补投不重复落库
- MQ 发送成功客户端认为失败 → 幂等表挡重复(**依赖 event_id 确定性派生**,02 §3.1)
- 同消息重复消费 → consumed_event 挡
- 消息乱序 → CAS from_status 挡
- 消费者 DB 成功 ACK 失败 → 幂等表挡重复
- 核销与取消并发 → CAS 只有 1 成功
- 增容与抢票并发 → INCRBY 不丢
- 场次发布重复执行 → released CAS + 锁选主挡
- **业务异常(route冲突)不抛只 ACK** → 不重投、触发 10.2a 补偿(06 §二·补)
- **基础设施异常(DB 超时)重投耗尽 → 进死信** → DLQ 监听告警 + 人工重投幂等
- **对账任务集群下双节点同时触发** → done-marker + CAS/唯一键保证效果只一次(06 §四)
- **对账任务中途 crash 重跑** → 无 done-marker,靠逐项幂等键挡重复写
- ☑ **Redis 内存打满**(`maxmemory` 临时调小)→ 写命令返 OOM → 抢号 `SERVICE_DEGRADED`、查询照常、`ping` 仍 PONG(§6.8 用例 2;08 §7.3)
- ☑ **滚动重启打断 D6 五阶段**(压测中 `docker stop backend`)→ 优雅停机 + 重投 + 幂等键收口,日志无 SIGKILL(§6.8 用例 6)
- ☑ **定时任务被慢任务占死**(mock 一个 sleep 5min 的对账)→ 其余任务(尤其 pending-scanner)照常执行(§6.8 用例 5)

### 6.1 route 冲突怎么构造(☑ 补:补偿链路是冷路径,不注入就永远没跑过)

⚠️ **问题**:dup TTL 修好后(04 §1.1),route 冲突在正常运行中**不可能触发** —— 而它是 10.2a 补偿的**唯一**触发源。这意味着:**不主动注入,整条补偿链路(约 100 行核心代码)在交付时是零执行覆盖的死代码。**

构造方法(测试环境,三选一):

| 方法 | 操作 | 验证什么 |
|---|---|---|
| **A. 手工删 dup**(最简) | 抢号成功后 `DEL dup:{slot_date}:{id_card_hash}`,用同一 id_card 再抢一次 | 第一道防线被绕开 → 第二道 route PK 冲突 → 全链路补偿 |
| **B. 关掉 Lua 的 dup 判重** | 测试 profile 用一份去掉 `SET NX dup` 分支的 grab.lua,并发同 id_card 打 2 请求 | 真并发下的 route 冲突(更接近病理态) |
| **C. 直接预插 route** | 抢号前手工 `INSERT id_card_route(hash, slot_date, 其它rno)` | 消费者阶段2 必撞 PK |

断言(五项副作用 + 三项状态,04 §三·补·3):

```
Redis:  桶余量 +1  /  occupy:{rno} 已删  /  dup 已删  /  pending:persist 已 ZREM  /  slot:full 已删
DB:     reservation.status = 2(CANCELLED,孤儿已被 CAS 清)
        state_log.status   = 3(Cancel)
        consumed_event 有 'cr-'+rno 记录(rollback-consumer 幂等)
不变量: C = A + R + V + X 仍成立(桶回补计入 A,该预约不计入 X —— 它从未成立)
```

> ⚠️ 断言里**最容易漏的是 `slot:full` 已删**(04 §1.2 P1 修)。漏了它测试照样"绿",但线上表现为"回补的名额被约满标记永久挡住"——只有在 slot 已满后再触发补偿才暴露。**故该用例必须在"slot 已约满"的前置状态下跑一遍。**

### 6.2 窗口期竞态的集成测试(☑ 补:D6 最难的一处,08 §9.2 已标"必写")

对位 02 §4.2 的三道收口,**至少四个用例**:

| # | 时序编排 | 期望 |
|---|---|---|
| 1 | 抢号成功 → **不启动消费者** → 用户取消 → 再启动消费者 | 落库直接为 CANCELLED(阶段0 读到 `occupy.cancelled`) |
| 2 | 消费者阶段2 提交后**挂起**(测试钩子)→ 用户取消(CAS 命中 DB 记录)→ 放行消费者阶段3 | 阶段3 复查发现已置位 → CAS 0→2;终态 CANCELLED,不出现 RESERVED |
| 3 | 手工删掉 `occupy.cancelled` 标记(模拟 Redis 丢 key)→ 消费者落库 | 阶段2 的 `state_log` Try 撞 PK 且 status=3 → 本条转 CANCELLED(双通道第二道生效) |
| 4 | 取消接口 CAS 返回 0 行但 DB 实际有记录(mock 一次 CAS 失败) | 按收口第2道先 SELECT → 查到记录 → 不走 Redis 标记路径,幂等返回或重试 CAS |

### 6.4 其它必测的正确性用例(☑ 补)

- **capacity 不整除**:capacity=55 / bucket_count=10 → Σ桶 = 55(非 50);增容 delta=5 到 10 桶 → Σ桶 +5(非 +0)。
- **增容后 slot:full 已删**:先把 slot 抢满(slot:full 置位)→ 增容 → 立刻能抢到。
- **10.3 不得在已放号 slot 上重跑**:手工把 `released` 改回 0 之外的任何路径都不许触发 10.3;直接调 release-consumer 两次 → 第二次 CAS 0 行 → 桶余量不变(不被 SET 重置回满)。
- **dup TTL 跨天**:为**次日** slot 抢号 → 检查 `dup` key TTL 应覆盖到次日 23:59:59,而非今夜 0 点。⚠️ 断言必须**精确到目标时刻**(±60s),不能只断言"TTL 够长"——UTC 时区下算出的秒数更大,`>=` 断言会假绿(§6.7 用例 5)。
- **valid_until 三处口径一致**:`slot` 表 / `slot:meta` / `occupy` 三处的 valid_until 完全相同(固化字段,03 §4.1)。
- **单库事务管理器**:故意在单库 mapper 上写不带 `transactionManager` 的 `@Transactional` → 集成测试应失败(03 §1.1 编码红线,08 §十 #1)。

### 6.5 QR 核销的安全用例(☑ 补:对位 07 §3.4.1)

| # | 用例 | 期望 |
|---|---|---|
| 1 | 改载荷里的 `rno` 后重算不了签名,直接提交 | 验签第 3 步失败 → `result=4` 无效码;`attempt_nonce` 有记录 |
| 2 | 同一 payload 在 60s 内**核销两次** | 第一次成功;第二次 CAS 0 行 → `result=1` 重复,返首次核销信息;**第二次的日志能落库**(靠 `attempt_nonce`,不撞 uk) |
| 3 | 61s 后用同一 payload | 验签第 4 步 `exp < now` → 「二维码已过期,请刷新」 |
| 4 | 用户 A 调 `GET /api/reservations/{B的reservationNo}/qr` | 403,不返回任何载荷(08 §十 #28) |
| 5 | 轮换密钥:`key-id` 改为 `qr-v2` 且 `accepted-key-ids: [qr-v2]`,用旧 `qr-v1` 载荷核销 | 验签第 2 步拒;把 `qr-v1` 加回 accepted 列表后同一载荷可通过(证明双 key 并存生效) |
| 6 | 手工核销同一 rno 两次 | 第一次成功(`qr_nonce=NULL`,写 `audit_log(MANUAL_VERIFY)`);第二次 CAS 0 行 → 重复;**两条 `verification_log` 都插入成功**(NULL 不撞 uk,08 §十 #26) |
| 7 | 窗口期(占位 occupy 存在、DB 未落库)扫码 | 返「预约正在确认,请稍候重试」,**不是**无效码,且**不核销**(08 §十 #29) |
| 8 | 扫码与手工核销的终态对比 | `reservation.status`、`state_log.status=2`、`reservation_event` 三处完全一致——差异只在 `method`/`qr_nonce`/`audit_log`(07 §3.4.1) |

### 6.6 接口契约的验收用例(☑ 补:对位 07 §3·补)

> 这组用例专挡"每个 controller 各发明一套返回格式"——它不会让功能测试变红,但会让前端在联调期反复改判断分支。

| # | 用例 | 期望 |
|---|---|---|
| 1 | 遍历所有失败分支(售罄/配额/未放号/已结束/降级/越权/未登录) | **每一个都返 `code` 字符串枚举**且在 07 §3·补·2 表内;没有裸 `{"msg":"..."}` 或裸 4xx |
| 2 | Redis 挂 + `degrade.grab=reject` 时抢号 | 返 `SERVICE_DEGRADED`,**不是** `SLOT_FULL`(否则 08 §6.1「库存不足率」被污染,D7 降级不可见) |
| 3 | 限流器拒绝 | HTTP **429** + `RATE_LIMITED`;业务失败分支**不得**用 429 |
| 4 | 任取一个成功响应与一个失败响应 | 两者都含 `requestId`,且与该请求日志的 MDC traceId 一致(08 §十 #34) |
| 5 | 用户 A 请求 `GET /api/reservations/{B的reservationNo}`(**详情**,非 /qr) | 403 `FORBIDDEN`,不泄露任何字段(尤其 `id_card_masked`,08 §十 #33) |
| 6 | 经 Caddy 访问 `http://localhost/actuator/prometheus` | 404;容器网内 `backend:8080/actuator/prometheus` 可达(08 §十 #35) |
| 7 | 制造一个未捕获异常(mock DAO 抛 RuntimeException) | 返 500 `INTERNAL_ERROR` + `requestId`;**响应体无堆栈/SQL/表名** |
| 8 | 核销已核销的 rno | `ALREADY_VERIFIED` 且 `data` 回带首次 `verifyTime`/`staffId`(§3.4「返首次信息」的落地检验) |

### 6.7 序列化 / 时区 / 求和的验收用例(☑ 第十一轮补:对位 07 §3·补·4 + 08 §7.2 + 05 §1.4.1)

> 这三类缺陷的共同特征:**功能测试全绿、HTTP 200、日志无异常**,只有拿真值逐位比对才看得见。它们不属于"业务分支漏了",而属于"承载层把对的值改错了"。**九个用例**(第 9 例是 Long→String 配置的连带面)。

| # | 用例 | 期望 |
|---|---|---|
| 1 | 抢号成功后,**逐字符比对** 响应 body 里的 `reservationNo` 与 DB `reservation_no` | 完全相同;body 里该字段是 **JSON 字符串**(带引号),不是数字 |
| 2 | 造一个末位为 `…899` 的 rno(或直接取真实 Snowflake),前端 `JSON.parse` 后再取码 | 取码成功;若 ID 序列化为数字则此例必挂(末位被改写 → `RESERVATION_NOT_FOUND`) |
| 3 | 遍历所有返回 ID 的接口(`grab`/`mine`/`{rno}`/`staff/today`/`admin/*`) | **无一处**返回裸数字 ID —— 用脚本正则扫响应体 `"(reservationNo\|userId\|slotId\|staffId)":\s*\d` 应零命中 |
| 4 | 容器内 `date` + `mysql -e "SELECT NOW()"` + 应用打一条 `LocalDateTime.now()` 日志,三者比对 | 三者一致(`Asia/Shanghai`),互差 **0**;差 8h 即 §7.2 三处有一处漏配 |
| 5 | 为**次日** slot 抢号,读 `TTL dup:{slot_date}:{hash}` | 换算出的到期时刻**精确等于** `slot_date 23:59:59`(±60s)。⚠️ 不能只断言"TTL 够长"——UTC 环境下算出的秒数更大,`>=` 断言会**假绿**(§6.4 那条要按此加强) |
| 6 | 把 slot 抢到只剩 3 个,读列表页「剩余名额」 | 等于 3;**同时** `redis-cli SLOWLOG GET` 里无 `KEYS` 命令记录(证明走的是 `MGET` 而非通配扫描,08 §十 #38) |
| 7 | 手工 `DEL` 掉某一个桶 key(模拟 TTL 清)后读列表 + 跑库存对账 | 列表按 0 计该桶正常展示;**对账 diff ≠ 0 并告警** —— 而不是"少一个 key 就当只有 n-1 个桶"从而 diff 假性为 0 |
| 8 | `bucket_count=1` 的 slot 走完抢号/列表/对账全链路 | 与多桶路径**走同一段求和代码**(无特例分支);结果正确 |
| 9 | 构造一条 `rno` 为**字符串**形式的 `ReservationCreated` payload 投给 persistence-consumer | 正常消费落库 —— 全局 ObjectMapper 配 `Long→String` 后 MQ payload 里的 ID 也会变成字符串,消费者 DTO 若不接受字符串,**上线该配置当天所有在途消息集体进 DLQ**(07 §3·补·4 末尾) |

### 6.8 运行期承载的验收用例(☑ 第十二轮补:对位 08 §7.3 + §7.4)

> 前十一轮问的是"东西在不在"与"值对不对";这一组问的是**"值都对,但运行时有资源把它跑完吗"**。这类缺陷的特征与承载层又不同:**功能测试全绿、并发低时压测也全绿**,只在放号瞬间/长时间运行后才显形,且现象全都指向错误的方向(像 MQ 故障、像 DB 挂、像 Lua 慢)。**八个用例**。

| # | 用例 | 期望 |
|---|---|---|
| 1 | `redis-cli config get maxmemory-policy` | 返 `noeviction`。**任何 `allkeys-*` 即验收不通过**(08 §7.3 / 红线 #39)——这是唯一一个"配错了整张故障覆盖矩阵有一行从 ✅ 变 ❌"的配置项 |
| 2 | 把 `maxmemory` 临时调到 `2mb` 制造内存打满,然后抢号 | 返 **`SERVICE_DEGRADED`**(不是 `SLOT_FULL`,红线 #40);`GET /api/slots` **仍正常返回**(读不受影响);`redis-cli ping` 仍 PONG(证明"Redis 挂"的第三种形态不会被健康检查发现,05 §五) |
| 3 | 同上内存打满态下,检查桶余量与 `occupy` | **一个 key 都没少**(`noeviction` 只拒写不删数据)。对照实验:临时改成 `allkeys-lru` 重跑 → 桶 key 被逐出、库存对账 diff 无规律漂移且**无任何异常日志** —— 这一步是为了亲眼看见"静默丢库存"长什么样 |
| 4 | `redis-cli config get appendfsync` | 返 `always`。库存是 Redis 真理源，成功响应前必须完成 AOF fsync；吞吐代价纳入安全水位压测 |
| 5 | 让一个对账任务人为 sleep 5min(mock 慢 SQL),观察其余定时任务 | **pending-scanner 与过期扫描照常执行**。若 `@Scheduled` 池未显式配 >1 则此例必挂:全部定时任务停摆 → 补投停止、卡单不被发现、过期不收口(occupy 无 TTL 故证据仍在,但在途预约会一直停在已扣未落库)(红线 #41 / 02 §3.2 / 04 §1.3) |
| 6 | 压测中途 `docker stop backend` 再起 | 在途 HTTP 请求正常完成(不出现连接被切断的 5xx);在途消息重投后落库正确;**日志里没有 SIGKILL**(证明 `stop_grace_period` 45s > 停机窗口 30s,08 §7.4) |
| 7 | 放号瞬间峰值压测,同时看 Hikari 三池 active 与 `persistence` 消费线程忙碌数 | `single` 池 active **不长期打满**;`persistence` 线程数 ≤ `single` 池大小。反例现象:线程 64 抢连接 30 → Hikari 等待超时 → 消息重投 → **死信虚高,看起来像 MQ 故障实为配置错**(红线 #42) |
| 8 | 4C8G 容器长跑(≥30min)压测后 `docker stats` + 容器是否重启过 | 内存不逼近 limit、容器**零重启**。若写死 `-Xmx` 或不设 `MaxRAMPercentage`,JVM 按宿主内存算堆 → OOMKilled,现象是"容器无声重启、查不到栈"(08 §7.4) |

### 6.9 初始化与运维承载的验收用例(☑ 第十三轮补:对位 08 §4.1–§4.6 + 03 §2.1/§2.2/§4.0)

> 前十二轮问的是"东西在不在""值对不对""跑得完吗";这一组问的是**"从零起一次,起得来吗"**。这类缺陷的特征最特殊:**它们在功能测试里根本跑不到测试**——因为测试环境是别人手工搭好的,而缺口在"搭"这一步。表现是接手者(或换台机器的自己)`docker compose up` 之后卡在第一分钟,而所有业务代码都是对的。**十个用例,全部属于阶段 0/2/3。**

| # | 用例 | 期望 |
|---|---|---|
| 1 | 全新机器:`cp .env.example .env` 填值 → `docker compose up --build` → 访问 `http://localhost` | **看到前端页面**(不是 404)。若 `frontend-build` 服务缺失则此例必挂:Caddy 托管空目录、后端接口全正常、现象与"前端没写"一模一样(08 §4.5) |
| 2 | 同上,用 `ADMIN_INIT_PASSWORD` 登录超管 | 登录成功 → 返 `PASSWORD_CHANGE_REQUIRED` → 改密后可进「场次模板」页。**这是阶段 0 的核心验收项**;失败时先查超管是否插进 `reservex_ds1`(`user_id=1`,红线 #43) |
| 3 | `SELECT * FROM reservex_ds0.user WHERE user_id=1` 与 `reservex_ds1.user WHERE user_id=1` | **只有 ds1 有行**。ds0 有行 = seed 插错库(登录会表现为"孤儿 route",排查方向被引向补偿链路,实为 seed 错) |
| 4 | 故意把 `.env` 里 `AES_KEY` 与 `ID_HASH_PEPPER` 填成同一个值,启动 backend | **fail-fast 拒绝启动**并明确报"四把密钥不可相同"(08 §4.2 / 红线 #47)。若能启动,则这条纪律只存在于文档里 |
| 5 | 注册一个用户 → 直接读 `user.id_card_ciphertext` 的字节长度与前 12 字节 | 长度 = 12(iv) + 18(ct) + 16(tag) = **46**;**两次注册同一身份证(不同用户不可能,故改测同一用户重复加密同值)前 12 字节不同**(证明 IV 随机而非常量,红线 #45) |
| 6 | 同一身份证经两个不同用户注册(第二次应被 route 挡),比对两次算出的 `id_card_hash` | **完全相同**(证明用的是全局 pepper 而非 per-row salt;不同则 M6 全局唯一失效,红线 #46) |
| 7 | 在 yml 加 `aes.keys.aes-v2` 并把 `key-id` 改为 `aes-v2`,重启后解密**旧用户**的身份证 | 解密成功(按行 `id_card_key_id=aes-v1` 取旧 key)。**无 `id_card_key_id` 列时此例抛 `AEADBadTagException`** —— 而它只在"授权解密"低频路径暴露,可能上线数月才发现(03 §2.1) |
| 8 | 批量登录 2000 用户(§一 token 池脚本),同时开 MySQL general log 或看 ShardingSphere 日志 | 每次登录**只查一个分片**(两跳:route → 分片键)。若出现 ds0+ds1 双查即是全分片广播,`email` 在分库无唯一约束,理论上可返两行 → 随机登进其中一个账号(红线 #44) |
| 9 | `slot_template` 四行中把第 2 行(11 点)对应的次日 slot **手工先插好**,再跑次日生成任务 | 9/14/16 三个时段**照常生成**(逐 template 跳过)。若整批 return 则 14/16 永远不生成,且 marker 未写、下周期再撞同一点 → **永久卡死无告警**(红线 #48) |
| 10 | 把 `maxmemory` 调到 `2mb` 后 `POST /api/sessions` | 返 **`SERVICE_DEGRADED`**,不是 `LOGIN_FAILED`。会话与库存共享同一 Redis 同一 `noeviction`(08 §4.6),refresh 写不进就是系统故障;返 `LOGIN_FAILED` = 告诉用户"密码错了",且会让登录失败率飙升被误判成撞库(07 §3·补·2) |

> ⚠️ **用例 1–3 必须在明确可丢弃的独立 Compose project 上做空库初始化**。已有业务环境不会重跑 `docker-entrypoint-initdb.d`,应由 `mysql-migrate` 验证增量迁移;禁止为初始化验收删除业务卷。
>
> ⚠️ **用例 4 的意义超出本条**:它检验的是「文档写的纪律有没有变成启动断言」。项目里已有三处同类断言(`daily-per-idcard != 1`、密钥两两不等、`maxmemory-policy`),**凡是"红线清单里有但代码里没断言"的条目,迟早会被违反**。动工时应把 48 条红线过一遍,标出哪些可以做成启动断言/集成测试,哪些只能靠人眼。

## 七、验收标准(正确性优先于吞吐)


- 不超卖(超卖数 0)
- 不重复预约(重复数 0)
- 不出现非法状态迁移
- 消息积压消退后最终一致(对账 diff 收敛 0)
- 故障恢复后库存守恒($C = A+R+V+X$)
- 限流开启时核心服务不雪崩
- Redis 故障按降级表行为可控
- 死信不静默丢失(DLQ 告警可达,人工可重投)
- 定时任务集群双触发下效果只一次(done-marker + CAS/唯一键验证)
- ☑ **补偿链路有执行覆盖**(§6.1 三种构造法至少跑通一种,含 slot 已满前置态)
- ☑ **窗口期五个竞态用例全绿**(§6.2)——这是 D6 唯一不可打折的门槛
- ☑ **注册五个用例全绿**(§6.3),孤儿 route 可自愈且不误删在途
- ☑ **capacity 不整除时 Σ桶 = capacity**(§6.4),放号与增容都成立
- ☑ **state_log 有真实数据**(四个写入点各至少一条),B 向对账能查出记录——原 docs 该表为空,是"叙事未落地"的检验点
- ☑ **QR 八个安全用例全绿**(§6.5),含篡改/过期/重放/越权取码/密钥轮换/手工双写日志
- ☑ **接口契约八个用例全绿**(§6.6),错误码无裸响应、降级与售罄可区分、`/actuator` 不上公网
- ☑ **序列化/时区/求和九个用例全绿**(§6.7):ID 全字符串、三处时区一致、Σ桶走 `MGET` 且以 `bucket_count` 为真理源、字符串形式 payload 可消费——这三类是"功能全绿但值被改错"的静默错,只能靠逐位比对抓
- ☑ **运行期承载八个用例全绿**(§6.8):`noeviction` 生效、内存打满返 `SERVICE_DEGRADED`、`appendfsync=always`、定时任务池 >1、优雅停机无 SIGKILL、消费线程 ≤ 连接池、容器零重启——这一类"值都对但运行时跑不完"的缺陷**在低并发压测下同样全绿**,必须在放号瞬间峰值与长跑下验
- ☑ **初始化与运维承载十个用例全绿**(§6.9):独立空库环境一键起得来(前端可见、超管可登、seed 落对分库)、四把密钥断言生效、IV 随机且同行存储、pepper 全局固定、密钥轮换后旧行可解、登录只查一个分片、生成任务逐项跳过、内存打满时登录返降级码——这一类缺陷**在功能测试里根本跑不到**,因为测试环境通常已有状态;必须在可丢弃的独立 Compose project 上验,不得删除业务卷
