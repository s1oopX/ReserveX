# 05 · 缓存与限流

> 穿透/击穿/雪崩与限流在本项目的真实落点。详细论证见 docs-old《Redis缓存与限流分析.md》,本文档为编码落地口径。

## 一、缓存穿透 + slot:meta + bug 修复(D3)

### 1.1 被修的 bug

docs-old §10.1 抢号 Lua **不判 slot 状态**,导致:
- 不存在的 slot_id → 桶 key nil → 返「已约满」(应为「不存在」)
- 未放号 slot → 桶未初始化 → 返「已约满」(应为「未放号+倒计时」)
- **已过期 slot → 桶还在有余量 → 能抢成功**(真 bug,M1 不返还但桶还在 → 抢到进不了园)

### 1.2 slot:meta 缓存设计

`slot:meta:{slotId}` Hash,字段(与 03 §四 `slot` 表一一对应):

| 字段 | 来源 | 用途 |
|---|---|---|
| `released` | slot.released | 抢号前置校验:0 → "未放号" |
| `release_at` | slot.release_at | ☑ **P2 补**:未发布倒计时(07 §2.3),原字段表漏了它 → 每张卡片都得回源打 DB,正是 D3 要消除的 |
| `slot_hour` | slot.slot_hour | occupy 满载荷 ARGV[7] + 卡片展示 |
| `valid_until` | slot.valid_until(03 §4.1 固化字段) | 抢号前置校验:< now → "已结束";occupy ARGV[8] |
| `capacity` | slot.capacity | 余量百分比展示;增容时刷新 |
| `bucket_count` | slot.bucket_count | **抢号路由必需**:算 `hash(rno) % bucket_count`(03 §4.3)与拼借桶 KEYS 序 |
| `slot_date` | slot.slot_date | dup key 拼装 + occupy ARGV[6] |

> ⚠️ `bucket_count` 与 `slot_date` 必须在 meta 里 —— 抢号线程要靠它们拼 Lua 的 KEYS/ARGV,若回源查 DB 就等于每次抢号打一次库,Q1-B「只动 Redis」直接破产。原字段列表漏了这两个,是同类缺口。

**抢号前置校验**(应用层,不进 Lua):

```
读 slot:meta:{slotId}(一次 HGETALL,拿全 7 字段)
  ├─ 不存在 /= NULL 空值缓存 → 返回"场次不存在"
  ├─ released=0                → 返回"未放号 + 倒计时"(取 release_at)
  ├─ valid_until < now         → 返回"已结束"(修复过期能抢号)
  └─ 合法                      → 用 bucket_count 算路由 + 用 slot_date/slot_hour/valid_until 拼 ARGV → 进 10.1 Lua
```

校验前置在应用层而非 Lua 内:**业务分支清晰**(三种返回带倒计时)、**不污染原子扣减脚本**(状态校验与扣减解耦)。非「Lua 短小」(HGET 成本可忽略,那借口站不住)。

> ⚠️ **一次 HGETALL 拿全**,不要分多次 HGET —— 抢号路径每多 1 次 round-trip 就多占 Redis 单线程一次时间片(05 §4.3 已标限流占 2 次,再加校验就是 3 次,09 §三"限流 round-trip 占比 < 20%"会挂)。

### 1.3 空值缓存兜底

查 DB `slot` 表为空 → 写 `slot:meta:{slotId}=NULL`(短 TTL 60s)挡反复查。

⚠️ **与 `slot:full:{slotId}` 是两种空值,不可复用同 key**:slot:full 挡"约满"(当日结束 TTL)、slot:meta=NULL 挡"不存在"(60s TTL),语义/存活期均不同。

### 1.4 附带收益

`/slots` 列表页高频读:余量读 Redis 桶求和,场次元数据读 `slot:meta`,都不打 DB。

#### 1.4.1 "Σ桶余量"怎么读(☑ 第十一轮补:原全 docs 只说"桶余量和",未定读法)

⚠️ **原缺口**:"Σ桶余量"在四处被当成一个现成的数用 —— 07 §2.3 卡片「剩余 N 个名额」、07 §4.2 发布监控水位条、06 §4.3 库存对账的 `capacity − Σ桶余量`、09 §三「各桶余量分布均匀」指标。但**没有一处定义它怎么取**,而最自然的写法恰好是最坏的写法。

**钉死**:

```
bucket_count = slot:meta.bucket_count          # 已在 meta 里(§1.2),不回源
keys = [ "slot:{slotId}:b:0", ... "slot:{slotId}:b:{n-1}" ]   # 逐个拼
MGET keys                                       # 一次 round-trip
A = Σ max(0, tonumber(v) or 0)
```

- **禁用 `KEYS slot:{id}:b:*`**:`KEYS` 是 O(N) 全库扫描且**阻塞 Redis 单线程**——与抢号 Lua 争的是同一根线程(§4.3),列表页高频调用等于自己给抢号制造毛刺。
- **禁用 `SCAN` 通配**:游标遍历期间若发生增容(§六 逐桶 INCRBY,不新增 key)虽不改桶数,但 `SCAN` 的**弱一致保证**本身不适合做对账的求和基准——对账要的是"这一刻的 n 个桶",而 `MGET` 是单次原子读。
- **`bucket_count` 是唯一真理源**:桶 key 不存在(未放号/已过期被 TTL 清)时 `MGET` 返 nil,按 0 计;**不能反过来"有几个 key 就算几个桶"**,那会把"某桶被 TTL 清掉"误读成"该 slot 只有 n-1 个桶",库存对账的 diff 直接错。
- **负值要夹到 0**:`DECR` 在极端并发下可能瞬时为负(Lua 内 `cur > 0` 判据已挡,但 10.2a 回补与 TTL 过期交叠时理论仍可见),展示层夹 0,**对账层不夹**——对账看到负数就该告警,那是真异常。

> ⚠️ 桶数=1 时(平日配置,00 §M3/03 §四)同样走这条路径,**不要给"不分桶"写一条特例分支**:特例分支意味着两套求和逻辑,其中一套永远缺测试。

## 二、缓存击穿:单飞只用在 slot:meta

### 2.1 各 key 击穿威胁分级

| key | 击穿威胁 | 原因 |
|---|---|---|
| `slot:meta:{slotId}` | ✅ 受 | 2000 并发读同一 slot,key 过期瞬间同时回源查 DB slot 表那行 |
| 桶余量 `slot:{slotId}:b:{n}` | ❌ 不受 | 原子**写**对象,不存在回源重建,套锁反破坏 Lua 原子性 |
| `slot:full:{slotId}` | ❌ 不致命 | 过期最坏多跑一次 Lua 发现已满写回 |
| `dup:*` | ❌ 不受 | SET NX 写,无回源 |

### 2.2 主路径:主动维护(逻辑过期)

slot:meta 是低频元数据(放号 0→1、增容时变)。故:
- 放号(§7.1)成功 → `HSET slot:meta released 1` + 重置长 TTL
- 增容(§9.3)后 → `HSET slot:meta capacity {新值}`
- 抢号高峰期 slot:meta 几乎不过期,击穿概率极低

### 2.3 兜底:单飞重建(Redisson 锁 + 双重检查)

```
读 slot:meta miss → 抢 Redisson 锁 lock:meta:{slotId}
  ├─ 抢到 → 双重检查(再 GET 防排队期间已建)→ 仍 miss → 查 DB → 写 Hash+长TTL → 解锁
  └─ 没抢到 → 短暂等待 → 重读
```

⚠️ **单飞锁只用在 slot:meta**。桶余量/dup/slot:full 不套。

## 三、缓存雪崩:伪命题 + TTL 抖动

本项目 key 基数小(几十个 slot:meta、几十组桶)、元数据低频变、放号分批削峰 → 雪崩风险本身低。

唯一免费动作:`slot:meta` 与 Sa-Token token 的 TTL 加随机抖动(`base + random(0,300s)`),消除集体同时过期理论可能。

面试诚门口径:"key 基数小/变更低频/放号分批,雪崩风险低;TTL 抖动+slot:meta 主动维护进一步消除。未硬编雪崩方案因场景不匹配,非省事。"

> ⚠️ **反例对照(桌面雪崩复盘)**:大促雪崩故障的演进链是「容量按预期峰值压测→真实流量数倍→Redis key 批量同时过期(TTL 无抖动)→miss 风暴打 DB→连接池打满→订单硬失败」。ReserveX 不踩这条链的原因是**三处都对位防御**:① 抢号主路径只动 Redis 不打 DB(02),DB 不在热路径,miss 风暴无 DB 可打;② slot:meta 主动维护+逻辑过期(§2.2),高峰期几乎不过期;③ TTL 加抖动(本节)。**雪崩不是靠"加个熔断"防的,是靠"DB 不在热路径 + 缓存不过期 + TTL 抖动"从结构上规避**——这正是复盘里说的"先纠根因,再谈限流熔断"。

## 三·补 容量规划与限流阈值定法(雪崩复盘根因补强)

桌面复盘指出雪崩第一因是「容量按预期峰值压测,真实流量数倍」。本项目对应的问题是:**压测容量怎么定、限流阈值怎么定,才不重蹈"按预期拍脑袋"覆辙。**

### 3.1 限流阈值不是拍脑袋,按"保护最稀缺下游资源"定

| 定法 | 说明 | ReserveX 落点 |
|---|---|---|
| **基线靠压测** | 单机找"安全水位"——p99 RT 不破 SLO、CPU<70%、零错误时的 QPS。**不是压到挂的值,是压到"刚要变形"前留余量的值** | 09 §三新增"单机安全水位 QPS"指标 |
| **集群容量** = 单机安全QPS × 节点数 × **安全系数(0.7~0.8)** | 留余量防突发 | 09 §三新增 |
| **按瓶颈资源限,不只按 QPS** | 若 DB 连接池是瓶颈,用并发信号量限并发而非限 QPS——QPS 限不住慢请求堆积 | ReserveX 抢号主路径不打 DB(只动 Redis),瓶颈是 Redis 单线程 → 按 Redis 容量限(09 已标限流 round-trip 占比) |
| **双层** | 网关/集群级 + 单机级(网关挂了也自保) | D4-A 本地+Redis 双层(05 §4.1) |
| **动态自适应** | 按 CPU/RT 动态收放,静态阈值定高没保护、定低误杀 | v2(Sentinel 系统自适应);v1 静态阈值配 yml(08 §七) |

### 3.2 压测必须覆盖"非正常态"(雪崩复盘的教训)

只压正常态=复盘里的"压测时一切正常,大促当天崩"。ReserveX 压测须覆盖:

- **缓存失效场景**:强制 `slot:meta` 过期后压测,验单飞重建(§2.3)真生效而非打穿 DB;
- **Redis 故障场景**:Redis 挂时按 D7 降级表(§五)行为可控;
- **限流触发场景**:超限后核心链路(核销)不断、非核心(抢号)按策略拒绝;
- **落库积压场景**:MQ 消费积压时 occupy 兜底查询不断、最终一致收敛。

> 这四条已在 09 §五压测场景 + §六故障注入覆盖,本节只点明它们是"防雪崩复盘"的直接对位——不是可选增强,是必做。

## 四、限流分层(D4-A,简历密度优先)

### 4.1 双层

| 层 | 实现 | 维度 | Redis 开销 |
|---|---|---|---|
| 本地(第一层) | Guava RateLimiter / Sentinel 进程内 | 接口级、STAFF 核销级 | 零 |
| Redis(第二层) | Redisson RRateLimiter | 用户级(`rl:user:{id}`)、场次级(`rl:slot:{slotId}`) | 1 round-trip |

抢号路径:本地限流削过载 → Redis 用户/场次限流(精准)→ slot:meta 校验 → Lua 抢号。共 2 round-trip(限流取令牌 + Lua)。

### 4.2 诚实标注(D4-A 的张力)

⚠️ demo **单实例**下,纯本地 Guava(D4-C)+ ZSet 风控路径更短(少 1 round-trip),单实例 perf 更优。**选 D4-A 的真实动机是简历展示 RRateLimiter**,非单实例 perf 最优。多实例水平扩时 A 才技术占优(接口/STAFF 本地各自不精准可接受,用户/场次靠 Redis 全局)。

D4-C 备选:本地 Guava 全维度 + 用户级防刷改用 60s 滑窗 ZSet(persist via Redis 跨重启)。更简单但少一个 RRateLimiter 简历点。

### 4.3 限流与抢号争同一 Redis(M3 连带)

单机 Redis 下,RRateLimiter 取令牌与抢号 Lua 抢同一单线程时间片。D4-A 下每请求 2 round-trip 是**已知开销**,非致命瓶颈:令牌桶取令牌(1 GET/INCRBY)远轻于抢号 Lua(判重+扣减+多 HSET+ZADD)。压测须验证此开销占比(09)。

### 4.4 令牌桶 vs 滑动窗口职责别混

| 机制 | 用途 | 判据 |
|---|---|---|
| 令牌桶(RRateLimiter) | 限流:管"放多少进来" | 平均速率+突发容忍 |
| 滑动窗口(Redis ZSet) | 风控:管"识别谁像机器" | 高频特征→弹图形验证码 |

## 五、Redis 故障降级表(D7)

M3 单机的连带单点风险:Redis 挂 = 抢号不可用 + 限流不可用 + slot:meta 失效 + Sa-Token 会话掉线。

| 接口 | Redis 挂策略 | 理由 |
|---|---|---|
| 抢号 | 默认**拒绝**(或 DB 乐观锁受控模式,更严限流) | 保不超卖优先于可用性 |
| /slots 查询 | 放行 + 本地缓存 + DB slot 表硬扛 | 影响面小 |
| STAFF 核销 | **保可用** + 本地限流兜底 | 核销可用 DB CAS 兜住 |
| 管理/注册 | 低频 + 告警 | 非核心 |

> ☑ **"Redis 挂"包含第三种形态**(第十二轮补,08 §7.3):除了"连不上"(进程死)与"超时"(慢),还有 **`noeviction` 下内存到顶** —— 此时 Redis 活着、读命令全部正常、只有**写命令**返 `OOM command not allowed`。判据与处置:抢号(写)按本表**拒绝**并返 `SERVICE_DEGRADED`(07 §3·补·2,**不是** `SLOT_FULL`);`/slots` 查询(读)**不受影响照常放行**;核销走 DB CAS 本就不依赖 Redis 写。**这种形态最容易被误判**——健康检查 `redis-cli ping` 返 PONG、连接数正常、只有抢号在失败,若把它归到 `SLOT_FULL` 就成了"全场次同时售罄"的假象。

> 简历/面试诚实:单机 Redis 演示,水平扩容可迁 Cluster/Sentinel,**别吹高可用**。被问"Redis 挂了"答此表,别答"不会挂"。

> ⚠️ **核心链路降级设计(雪崩复盘 Q4 对位)**:降级不是"全挂了怎么办",而是"保核心链路不断"。ReserveX 的核心链路分级:
> - **核心**(不可断):核销入园(游客已在闸口)、抢号主链路(放号瞬间)。核销保可用靠 DB CAS;抢号 Redis 挂时按上表拒绝(宁可约不到,不可超卖)——**拒绝是降级,不是故障**,因抢号有下一批放号可重试。
> - **非核心**(可降级):/slots 查询(本地缓存兜底)、提醒邮件(可延后)、统计分析(可停)。
> - **舱壁隔离**:抢号与核销走不同 Redis key 命名空间 + 不同限流维度(`rl:slot` vs `rl:staff`),核销高峰不与抢号争 Redis 时间片。v1 单进程下用线程池隔离(☑ **具体池大小/拒绝策略见 08 §7.4**——原本这里只写"(08)"而 08 从未定义),v2 可拆独立 worker。
> - ⚠️ **抢号/核销本身不放异步池**:它们是同步返回的 Tomcat 请求线程,舱壁体现在"各自的限流维度 + 各自的 key 命名空间";08 §7.4 定义的独立池是**旁路任务**(邮件/对账/定时),防它们把 Tomcat 与 DB 连接吃干。别把"舱壁"理解成"每条链路都要一个 `@Async` 池"。
> - **异步接单(极端降级)**:ReserveX 的 B 方案本身就是"先 Redis 预占(接单)后 MQ 异步落库(处理)"——与复盘 L3「先接单后处理」同构,只是我们常态就这么做,不是降级才切。

## 六、单机 Redis 诚门口径(M3 连带)

- §10.1 判重+扣减合并 Lua 成立前提是单机(无跨槽);Cluster 下 dup key 与桶 key 落不同槽需拆两步——M3 选项的真实代价,已在 00 记。
- B 方案(02)下 Redis 崩+AOF 丢:号源实时状态全丢,回 DB `occupied` 近似重建;窗口期 occupy 也丢。小概率+代价不对称,接受。
- ☑ **"丢多少"要给得出数**(08 §7.3):`appendfsync everysec` 下崩溃最多丢**最近 1 秒**的写。这是"小概率+损失有界"的量化依据——答"开了 AOF 就不丢"是错的(`everysec` 本身就有 1s 窗口),答"配 `always`"也是错的(每次抢号等 fsync,与"只动 Redis 扛写峰值"直接冲突)。
- ☑ **桶余量/`occupy`/`dup`/`pending:persist` 是库存真理源,不是缓存** → `maxmemory-policy` 必须 `noeviction`(08 §7.3 / 红线 #39)。配成 `allkeys-lru` 时 Redis 会在内存到顶后**静默逐出**它们:桶被逐出=库存凭空消失,`occupy` 被逐出=窗口期预约被 scanner 按 `EXISTS occupy` 判成"已回滚"而 `ZREM` 清掉(D2)。**全程 HTTP 200、无异常、无日志** —— 与第十一轮那三条同类,属"承载层把对的值弄没了"。
